# Tech-Debt — CLI: 61 v2.2 ROM built-ins unreachable from the live keyboard

**Status:** OPEN — needs architecture decision before plan-phase
**Discovered:** 2026-05-23, while answering the user question "how do I invoke PI in the CLI?". The PI fix (commit `53bff2f`, a single resolver arm in `xeq_by_name_local_resolve`) surfaced a much larger class of the same bug.
**Affected surface:** `hp41-cli` only — the engine (`hp41-core`) dispatches every Op cleanly, the GUI (`hp41-gui`) reaches the Ops through the React frontend (`src/key_map.rs`). Only the TUI keyboard layer is affected.
**Severity:** HIGH for user-math ops (SIN/COS/TAN, LN/LOG, SQRT, …), MEDIUM for programming primitives, LOW for display/alpha secondaries.

## Symptom

After `XEQ <name>` in the CLI, any built-in that is not in the resolver chain surfaces as `Err(InvalidOp)`:

```
> X      (= f-N opens the XEQ modal)
XEQ _
> SIN
invalid operation
```

Workaround today: write a program (`PRGM → LBL "S" → SIN → RTN`) and call it via `XEQ "S"`. Works, but is unacceptable for interactive calculation.

**Reachable in the current v3.1 mid-Phase-34 build (commit `53bff2f`):**

- Direct keys via `key_to_op` (~14 keys): `+ - * / %`, `Enter`, `Backspace` (Clx), `n`/`r`/`x`/`l`/`p`/`u` (Chs/Rdn/X⟷Y/LastX/PRGM/USER), digits 0–9
- Modal openers: `S` (STO), `R` (RCL), `F` (FmtDigits), `P` (Print), `X` (Hex, PRGM mode), `C`/`D`/`T`/`N` (CLP/DelCount/Tone/XeqByName)
- `f`-prefix shifted: 4 conditional tests (`f-`/`f+`/`f*`/`f/`), 6 flag prompts, 5 register prompts
- XEQ-by-name resolver: 8 conditional-test mnemonics + **PI** (new in `53bff2f`) + Math 1 Pac XROM (≈45 functions, only when `xrom_modules & 0b1 != 0`) + Stat 1 Pac XROM (Phase 33, `xrom_modules & 0b10 != 0`)
- Program path: user `LBL` → `XEQ "<LBL>"`

**NOT reachable** (61 ops, see audit below).

## Audit — 61 PI-class gaps

Source: `docs/hp41cv-functions.json` × live resolver chain in `hp41-cli/src/keys.rs` + `hp41-cli/src/app.rs` + `hp41-core/src/ops/program.rs::builtin_card_op` (with `#[cfg(test)]` modules stripped). Audit script preserved in the PR thread for commit `53bff2f` (conversation log).

### HIGH — user math (38)

| Family | Ops |
|---|---|
| Trig | `SIN COS TAN ASIN ACOS ATAN` |
| Log/exp | `LN LOG E^X 10^X` |
| Power/root | `SQRT X² Y^X 1/X` |
| Basic | `ABS INT FRC SIGN N! MOD RND` |
| Conversion | `P→R R→P HMS→H H→HMS HMS+ HMS-` |
| Statistics | `Σ+ Σ- MEAN SDEV L.R. YHAT CORR CL Σ` |
| Stack/reg | `R^ CLST CLREG` |

### PROGRAMMING — PRGM mode primarily (12)

`LBL GTO RTN STOP PSE INS PACK SIZE ASN CATALOG`, indirect: `GTO IND XEQ IND`

### SECONDARY — display/alpha/sound (10)

`AVIEW PROMPT AON AOFF CLD`, alpha: `ATOX XTOA AROT POSA`, sound: `BEEP`

### OTHER (1)

`NULL` (synthetic, no user-facing path required)

## Root cause

Phase 25 / **D-25.3** stripped the v1.x letter shortcuts (see `hp41-cli/src/keys.rs:138-140`):

> "All other keys — including every v1.x letter binding stripped per D-25.3 (C, T, L, G, E, H, I, W, Y, q, a, c, k, s, g, z, Z, m, D, y, b, O, V, h, j, J) — are silently unmapped."

Rationale at the time: HP-41-faithful interface. The original v1.x letter mappings (`s → SIN`, `c → COS`, etc.) diverged from the HP-41 hardware layout.

**What was missing:** a compensating path. On the real HP-41 these functions sit on physical keys (e.g. SIN on row 2 col 5, CLST on Shift-Σ+, SQRT on row 1 col 3, etc.). The CLI, however, has no 35-key layout — a PC keyboard cannot map 1:1 to HP-41 positions. The obvious compensation would have been: allow XEQ-by-name for the ROM built-ins too. Instead, `xeq_by_name_local_resolve` (Plan 03, Phase 25) was scoped narrowly to the 8 conditional tests + 4 card-reader names; the ROM built-ins fell through the cracks.

`builtin_card_op` in `hp41-core/src/ops/program.rs:1166` is explicitly documented: "Deliberately *not* a general built-in dispatcher — Spec §'Out of Scope'." — that was a deliberate scope decision in Phase 25, but it created the HIGH gap class.

## Why this slipped through

- **`key_coverage.rs`** only checks entries with `key_path != null`. PI-class ops have `key_path: null` by definition → they fall through.
- **`function_matrix_parity.rs`** verifies Op ↔ JSON bidirectionally, but not reachability through the resolver chain.
- **The GUI path works differently:** `hp41-gui/src-tauri/src/key_map.rs` resolves string IDs (`"sin"`, `"clst"`) directly to `Op::Sin` / `Op::Clst` because the React frontend renders explicit buttons. The CLI has no analogous UI surface for discoverability → the CLI ↔ GUI symmetry drift was not obvious.
- **Manual dogfooding:** v3.0 / v3.1 were primarily verified through the GUI (E2E smoke + `verifying-card-reader.md`). The CLI was used for program entry and CV built-in smoke, not for interactive math.

## Architecture trade-offs

### Option A — Generic XEQ-by-name resolver for ROM built-ins

**Diff shape:**
```rust
// hp41-cli/src/keys.rs::xeq_by_name_local_resolve  (or a new helper fn)
"SIN"  => Some(Op::Sin),
"COS"  => Some(Op::Cos),
"CLST" => Some(Op::Clst),
// … 58 more arms
```

**Pros:**
- Symmetry with the just-fixed PI gap — same path, same test pattern.
- The resolver chain stays uniform: user LBL → builtin_card_op (12 names) → xeq_by_name_local_resolve (8 tests + PI + 61 built-ins) → xrom_resolve (Math 1 + Stat 1) → Err.
- No keyboard-layout decisions required (no UX argument about "where should SIN go?").
- Symmetric with real HP-41 program semantics: a stored `Op::Sin` is laid out as the 1-byte opcode 0x59; `XEQ "SIN"` is NOT a real call path on the hardware. **Symmetry caveat:** programs containing `Op::Xeq("SIN")` would currently call `builtin_card_op("SIN")` in `execute_op` — None today. Full CLI/program symmetry would require extending `builtin_card_op` too (12 → 73 names). The doc comment there ("Deliberately *not* a general built-in dispatcher") makes this a deliberate engine decision — Option A is explicitly CLI-only, "compatibility shim" in character.

**Cons:**
- A user on the real HP-41 would never type `XEQ "SIN"` — they press the SIN key. The solution is "ergonomically sound, hardware-divergent".
- 61 new arms × test coverage = ~120 LOC resolver + ~180 LOC tests.

### Option B — Restore key bindings for the HIGH-38

**Diff shape:**
```rust
// hp41-cli/src/keys.rs::key_to_op  +  shifted_key_to_op
KeyCode::Char('q') => Some(Op::Sin),    // as in v1.x
KeyCode::Char('c') => Some(Op::Cos),
// …
```

Plus on-screen discoverability via `key_ref_entries()` (right TUI pane).

**Pros:**
- Interactive math entry becomes "real HP-41-like" — press `q` for SIN, no modal keystrokes.
- 1-key path, lower latency than `f-N S I N <Enter>` (4 keys).

**Cons:**
- Reverses D-25.3 — politically sensitive, because D-25.3 was a deliberate architectural decision ("HP-41-faithful, no v1.x legacy mappings").
- There is no canonical "PC keyboard → HP-41 position" mapping (see discussion of `keycode_to_hp41_code` comments "[ASSUMED — row N column assignments]"). Every choice is a UX compromise.
- Covers only ~20–30 of the 61 ops (a PC keyboard does not have 61 ergonomically free keys). PROGRAMMING + SECONDARY would still need to be reachable through XEQ-by-name (Option A) → Option B is additive to A, not an alternative.

### Option C — Hybrid: Option A mandatory, Option B selectively for the HIGH top 15

Trig + log + power + 1/X + SQRT on keys (15 ops), the rest through XEQ-by-name. Best UX/effort ratio, but highest complexity (UX decisions + resolver arms + discoverability updates).

## Recommendation

**Option A for a standalone Phase 38** (or v3.1.1 quick task, depending on scope).

Rationale:
1. Closes all 61 gaps with a consistent, tested pattern (replica of the PI fix).
2. Does not reverse D-25.3 — the keyboard stays HP-41-faithful, only the discoverability through XEQ "name" is completed.
3. Clear symmetry with the GUI: `hp41-gui::key_map::resolve` already does this — the CLI catches up.
4. Option B can be added later if UX feedback warrants it — Option A is a prerequisite, not a trade-off against it.

**Symmetry question** (symmetry with programmatic `Op::Xeq("SIN")`): keep CLI-local-only routing by default, do not expand builtin_card_op. A real HP-41 program dump contains `Op::Sin` as a 1-byte opcode, never as `XEQ "SIN"`. CLI-only XEQ-by-name symmetry is a compatibility shim for interactive users, not an engine contract.

## Test-coverage strategy

For the Phase 38 plan:

- 1 resolver direct-call test per op (`assert_eq!(xeq_by_name_local_resolve("SIN", _), Some(Op::Sin))`) — verifies the 61 arms.
- 1 end-to-end test per op family via `type_name_and_enter("SIN")` (analogous to the PI test in `phase25_xeq_by_name.rs`). Trig × 6, log/exp × 4, power/root × 4, basic × 7, conversion × 6, statistics × 8, stack/reg × 3 = ~38 end-to-end tests for HIGH; PROGRAMMING + SECONDARY analogous.
- Case-sensitivity test (one shared test, not per op): `xeq_by_name_local_resolve("sin", _) == None`, etc.
- Extend `key_coverage.rs` with a second test function `xeq_by_name_implemented_entries_resolve()` that walks JSON `key_path: null && status: implemented && !xrom` entries against the resolver — this would automatically catch the next PI-class gap.

## Open questions for the discuss-phase

1. **Naming canon:** the HP-41 shows `R↓` on the display, but JSON `display_name` is `"R^"` (Rup). Should the resolver accept both spellings (`"R^"` AND `"R↓"` AND `"Rdn"`)? Analogously for `"X²"` vs `"XSQ"` vs `"X^2"`, `"1/X"` vs `"RECIP"`, `"E^X"` vs `"EXP"`.
2. **Whitespace/special characters:** does the XEQ modal accept `↑` / `²` as character input today? If not, ASCII spellings only → the Σ-character path for the `Σ+` / `Σ-` / `MEAN` family needs a separate decision.
3. **PROGRAMMING family (LBL/GTO/RTN):** these behave differently in PRGM mode (they modify `state.program`, not the stack). `XEQ "LBL"` outside PRGM mode would be semantically meaningless → either a mode check or explicit exclusion from Option A.
4. **CATALOG / ASN / PACK / SIZE:** these require parameters (`CATALOG 1`, `SIZE 100`). The current XEQ modal has no follow-up prompt path — if these ops had prompts as CV cards (Plan 02), the same modal-opener pattern should be reused.
