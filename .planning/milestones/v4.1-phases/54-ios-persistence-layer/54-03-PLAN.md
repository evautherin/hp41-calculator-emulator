<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| iOS sandbox ACL ↔ std::fs write | The device determines whether the resolved Application Support path is actually writable; a wrong disposition silently loses state at rest |
| iCloud backup ↔ Application Support (D-54.1) | On-device, the file is iCloud-backed by default |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-54-09 | Denial of Service | sandbox EPERM on Application Support write | mitigate | Task 3 outcome C adds the AppDataWrite capability if std::fs is ACL-blocked; the 54-01 fallback + 30s thread prevent a hard crash in the interim |
| T-54-10 | Information Disclosure | data-at-rest written to the wrong container path | mitigate | Task 2 step 1 explicitly observes the resolved path (console log) before trusting the round-trip; wrong-path writes are caught by the absent-restore signal |
| T-54-11 | Tampering | absolute path persisted across container-UUID change (P-iOS-29) | mitigate | Already audited clean in 54-01 Task 3; the device round-trip after a fresh install would surface any latent path-string breakage |
| T-54-05 | Information Disclosure | iCloud backup of Application Support | accept | D-54.1 explicitly accepts iCloud-backup-by-default for app-managed RPN state; no PII/secrets |
| T-54-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages; the only possible change (capability TOML/JSON) adds no dependency |

No `high`-severity threats. T-54-09/10 are the data-at-rest-correctness threats flagged in the phase threat model; both are mitigated by the explicit device observation in Task 2 plus the Task 3 conditional fix.
