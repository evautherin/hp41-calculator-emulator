<objective>
Wire the GUI frontend to the new Tauri dialog commands and build the multi-program picker overlay component.

Purpose: This plan connects the Tauri backend commands (Plan 02) to the React frontend. Users trigger import/export through existing Ctrl+R/W/D/F keyboard shortcuts (when ALPHA is empty, the backend opens a file dialog instead of using ~/.hp41/cards/). The multi-program picker (D-50.4/D-50.6) lets users select which programs to import from an archive. Toast messages provide feedback per D-50.3.

Output: App.tsx handles dialog command responses (single-program, multi-program, data card), RawPickerOverlay.tsx renders the multi-select picker, and App.css provides the overlay styling.
</objective>

    b) Add state for the multi-program picker near other state declarations:

    importRawDialog: async function. Guard with busyRef. Call invoke('import_raw_dialog'). Parse the response:
      - If response has "view" + "message": single-program imported. setCalcState(response.view), showToast(response.message), setErrorMessage(null).
      - If response has "multi": multi-program archive detected. setPickerData({ programs: response.multi.programs, filePath: response.multi.file_path }). Do NOT set busyRef to false yet (picker is open). Actually, DO set busyRef false so the picker can dispatch.
      - If response has "view" only (user cancelled): setCalcState(response.view) to refresh.
      - Catch errors: showToast(extractErrMessage(err)).

    exportRawDialog: async function. Guard with busyRef. Call invoke('export_raw_dialog'). If response has "message": showToast(response.message). If "cancelled": no feedback (silent per UI-SPEC).

    importDataDialog: async function. Same pattern as importRawDialog but calls invoke('import_data_dialog'). Always single-result (no multi-program for data cards). showToast(response.message).

    exportDataDialog: async function. Same pattern as exportRawDialog but calls invoke('export_data_dialog').

    handlePickerConfirm: async callback receiving selectedIndices (number[]). Guard with busyRef. Call invoke('import_selected_programs', { filePath: pickerData.filePath, indices: selectedIndices }). setCalcState(result), showToast("Imported " + selectedIndices.length + " programs"), setPickerData(null), setErrorMessage(null).

    handlePickerClose: callback. setPickerData(null). No state change, no toast (UI-SPEC: silent dismiss).

    d) Modify the handleKey function's card reader key handling. The import/export dialog commands are SEPARATE paths from the existing card reader ops. In the frontend, intercept 'xeq_RDPRGM' / 'xeq_WPRGM' / 'xeq_WDTA' / 'xeq_RDTA' key IDs. If alpha annunciator is NOT active (meaning no ALPHA content), call the dialog command. If alpha IS active, dispatch through the normal path (which uses the name from alpha register via cards_dir). This exactly implements D-50.1.

    Add the intercept in handleKey, right after the __save_state__ intercept block (around line 728):
    - if keyId is 'xeq_RDPRGM' and alpha annunciator is false: e.preventDefault(); importRawDialog(); return;
    - if keyId is 'xeq_WPRGM' and alpha annunciator is false: e.preventDefault(); exportRawDialog(); return;
    - if keyId is 'xeq_RDTA' and alpha annunciator is false: e.preventDefault(); importDataDialog(); return;
    - if keyId is 'xeq_WDTA' and alpha annunciator is false: e.preventDefault(); exportDataDialog(); return;
    - Otherwise: fall through to normal dispatch (existing behavior with ALPHA name).

    Also add the same intercept in handleClick for on-screen card reader buttons, if they exist as click targets. Check if the on-screen keyboard has card reader keys -- if not, the physical keyboard path is sufficient.

    e) Render the RawPickerOverlay conditionally in JSX:
    {pickerData && <RawPickerOverlay programs={pickerData.programs} onConfirm={handlePickerConfirm} onClose={handlePickerClose} />}
    Place it alongside the other overlays (help, settings, onboarding) inside the .calculator div.
