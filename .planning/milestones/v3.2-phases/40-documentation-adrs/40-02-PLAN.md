    **ADR v3.2-001: Clock Access Pattern**
    - Title: `ADR-v3.2-001: Clock Access Pattern -- Direct SystemTime in hp41-core`
    - Status: `Locked 2026-05-24`
    - Owner: `Plan 38-03`
    - Requirement refs: `TIME-CLK-01, TIME-CLK-02, TIME-FW-04, Pitfall 34 (clock in core)`
    - Downstream consumer: `hp41-core/src/ops/time/clock.rs` (TIME/DATE/T+X/CORRECT/SETIME/SETDATE); `hp41-core/src/state.rs` (`time_offset_secs: i64`)
    - ADR write-up prose: `Phase 40 / TIME-DOC-03`
    - Context section (~400-600 words): describe the design problem -- hp41-core has a zero-I/O principle (no console/filesystem/network), but TIME/DATE need a clock source. SystemTime is a value-returning syscall, not console I/O. Precedent: core already uses `Arc<AtomicBool>` (cancel_requested) and `Instant`.
    - Decision section: direct `std::time::SystemTime::now()` in hp41-core. Single `time_offset_secs: i64` persistent field. OS local time via `libc::localtime_r` / `GetLocalTime`. All time/date reads apply SystemTime::now() + offset.
    - Consequences: Positive (zero new deps, simple testability via offset), Negative (core depends on system clock availability), Neutral (no timezone support matches real HP-41CX).
    - Alternatives Considered (quote D-38.1 verbatim): trait injection (clock trait abstraction), frontend callback (core requests time from caller), `no_std` clock abstraction. For each: quote the relevant 38-CONTEXT.md text verbatim, then a "Why rejected:" line.
    - Footnotes: OM 00041-90035 reference.

    **ADR v3.2-002: Live Display Architecture**
    - Title: `ADR-v3.2-002: Live Display Architecture -- Pull-on-Redraw Pattern for Clock/Stopwatch`
    - Status: `Locked 2026-05-24`
    - Owner: `Plan 38-03 + Plan 39-02`
    - Requirement refs: `TIME-DSP-01, TIME-DSP-05, TIME-SW-08, Pitfall 32 (live display)`
    - Downstream consumer: `hp41-cli/src/app.rs` (16ms poll loop); `hp41-cli/src/ui.rs` (`get_display_string()` priority chain); future `hp41-gui/src/App.tsx` (conditional setInterval)
    - ADR write-up prose: `Phase 40 / TIME-DOC-03`
    - Context section: describe the design problem -- the emulator was purely event-driven until v3.2. Clock/stopwatch need continuous display updates. The existing ratatui 16ms poll loop already redraws ~62 times/second.
    - Decision section: pull-on-redraw pattern. Core remains thread-free and async-free. Frontend redraw cycle computes time-dependent display state on-demand. Clock display and stopwatch display take highest priority in `get_display_string()`. No new timer infrastructure.
    - Consequences: Positive (zero architectural debt, uses existing poll loop), Negative (GUI needs conditional setInterval -- D-11 exception), Neutral (display update frequency tied to frontend redraw rate).
    - Alternatives Considered (quote D-38 carried.7, D-39.1, D-39.2 verbatim): async timer in core, push-from-core event system, dedicated polling thread. For each: verbatim quote + "Why rejected:" line.
    - Footnotes: OM 00041-90035 reference, D-11 no-polling discipline.

    **ADR v3.2-003: Alarm Catalog Design**
    - Title: `ADR-v3.2-003: Alarm Catalog Design -- Vec<AlarmEntry> on CalcState with event_buffer Drain`
    - Status: `Locked 2026-05-24`
    - Owner: `Plan 38-05`
    - Requirement refs: `TIME-ALM-01, TIME-ALM-02, TIME-ALM-03, TIME-ALM-04, TIME-ALM-05, TIME-ALM-06, TIME-ALM-07, TIME-ALM-08, TIME-ALM-09, TIME-ALM-10, TIME-ALM-11, TIME-ALM-12, Pitfall 37 (alarm state machine)`
    - Downstream consumer: `hp41-core/src/ops/time/alarm.rs` (XYZALM/RCLALM/ALMCAT/CLALMA/CLALMX/CLRALMS/ALMNOW/check_alarms); `hp41-core/src/state.rs` (`alarms: Vec<AlarmEntry>`, `AlarmEntry`, `AlarmType`)
    - ADR write-up prose: `Phase 40 / TIME-DOC-03`
    - Context section (~400-600 words): describe the alarm system design problem. HP-41CX supports up to 253 alarms (hardware limit from catalog indexing), with message alarms (display text) and control alarms (execute program label). Alarms can repeat. Past-due detection must fire on each dispatch cycle. The emulator's I/O-free core cannot beep or display -- it needs a drain pattern.
    - Decision section: `AlarmType` enum with `Message(String)` and `Control { label: String, interrupting: bool }` variants. Direct `alarms: Vec<AlarmEntry>` on CalcState with `#[serde(default)]`. `check_alarms()` called by frontend after every dispatch via the drain pattern. Alarm notifications pushed into `event_buffer`. Repeat interval stored as `i64` seconds. Interrupting control alarms stored but execution deferred (D-38.4).
    - Consequences: Positive (simple serialization, matches existing patterns for regs/programs), Negative (Vec linear scan for check_alarms, alarm catalog O(n) for large catalogs), Neutral (253-alarm practical limit matches OM).
    - Alternatives Considered (quote D-38.8-11 verbatim): separate alarm state struct (not on CalcState), channel-based notification (mpsc channel), trait-based alarm handler (AlarmObserver trait). For each: verbatim quote from 38-CONTEXT.md + "Why rejected:" line.
    - Footnotes: OM 00041-90035 alarm chapter reference, go41cx alarm bugs lesson.
