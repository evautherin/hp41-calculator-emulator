RESOLVER CHAIN (the load-bearing fact for tap-to-run):
- The GUI dispatches a string id via `invoke<CalcStateView>('dispatch_op', { keyId })`.
- hp41-gui/src-tauri/src/key_map.rs:427 — `if let Some(rest) = key_id.strip_prefix("xeq_")
  { return Ok(Op::Xeq(rest.to_string())); }`. So `xeq_<TOKEN>` → `Op::Xeq("<TOKEN>")`
  with the label = the verbatim substring after `xeq_`.
- hp41-core/src/ops/program.rs:68 `op_xeq(state, label)` (the !is_running path):
    `builtin_card_op(label)` → else `xrom_resolve(label, state.xrom_modules)` → else
    `Err(InvalidOp)`. **Both resolvers are EXACT-MATCH, CASE-SENSITIVE** (program.rs
    doc-comment at ~line 1355 states "Case-sensitive").
- PRECEDENT already in App.tsx: stopwatch dispatches `'xeq_STOPSW'` / `'xeq_RUNSW'`
  (App.tsx:701, :945) through `invoke('dispatch_op', { keyId })`. Tap-to-run reuses
  this exact mechanism.

PRGM-MODE INSERT (proves the PRGM path needs NO special handling):
- hp41-core/src/ops/mod.rs:1612-1628 — `dispatch()` has a PRGM gate BEFORE the op match:
    when `state.prgm_mode == true`, the op (except PrgmMode / Clp / Del / Ins) is
    `state.program.push(op)` and returns WITHOUT executing. So `Op::Xeq("CLRG")`
    dispatched in PRGM mode is recorded as a program step; it renders via
    prgm_display.rs:133 `Op::Xeq(s) => format!("XEQ {s}")` → "XEQ CLRG". This is the
    authentic alpha-XEQ program-step representation. NO frontend branching on prgm
    is required for the dispatch itself — the SAME `xeq_<TOKEN>` id runs in normal
    mode and inserts in PRGM mode. (PRGM state is observable at App.tsx:657
    `calcState?.annunciators.prgm` — used only to decide whether to fire success
    haptics / leave a toast, NOT to change the dispatched id.)

DISPLAY_NAME → DISPATCH-TOKEN RISK — RESOLVED (the core design decision):

  resolver token set found: **303 entries have `display_name` === a resolvable
