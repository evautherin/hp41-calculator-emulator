## ADV-DOC-02: Divergence Catalog — Source Material

`docs/hp41-advantage-divergences.md` must follow the D-30.5 five-field shape established for Math Pac I and extended through Time Pac:

- **OM citation** — HP 00041-90482 page/example, or `"N/A — emulator extension"`

- **See** — cross-references to ADRs, CONTEXT decisions, source files, test files

Entry identifiers follow the phase-origin convention: `D-45-NN` (tied to Phase 45).

**Three-bucket structure:**

1. OM Divergences — numerical/behavioral mismatches with OM-quoted examples
2. Emulator Extensions — features we added not present in HP 00041-90482
3. Behavioral Policies — intentional implementation choices with OM basis

**Mandatory topics from Phase 45 success criteria:**

### Topic 1: Named-Matrix vs. R14/R15+ Incompatibility

The HP-41 Advantage Pac uses named-matrix storage via the ALPHA register and X-MEM file slots. The Math Pac I (XROM 7) uses a register-based matrix model: `matrix_dim` (via R14/R15) and `matrix_active_reg`. These two matrix systems are completely incompatible at the storage level.

Decision source: D-43.5 (CONTEXT.md) — "Named-matrix storage MUST NOT touch `state.matrix_dim` or `state.matrix_active_reg`. Complete isolation between the two matrix systems."

Implementation: `state.adv_matrices: Vec<AdvMatrix>` vs. `state.matrix_dim` / `state.matrix_active_reg`. No data sharing, no cross-system calls. Verified by grep in Phase 43 Plan 10: zero code references to `matrix_dim`/`matrix_active_reg` in `advantage/` executable code.

Bucket 3 (Behavioral Policy) — the OM does not explicitly describe this incompatibility because the HP-41 hardware used XEQ-by-name dispatch and the two modules never shared register space in practice.

### Topic 2: FROOT Laguerre vs. Math Pac I Bairstow Coexistence

Math Pac I (XROM 7) implements `ROOTS` using Bairstow's method, handling polynomials of degree 2–5. The Advantage Pac (XROM 24) implements `FROOT` using Laguerre's method with arbitrary degree (1–100).

Decision source: D-43.8 resolution (RESEARCH.md) — FROOT reads degree from X register, coefficients from R01..R(n+1). The two polynomial-root finders coexist because they use different mnemonics (`ROOTS` vs. `FROOT`) and different register conventions.

ADR-v3.3-002 covers the Laguerre algorithm choice over alternatives (Bairstow, Jenkins-Traub).

Bucket 3 (Behavioral Policy) — documented so users understand the two root-finders have different capabilities and register conventions.

### Topic 3: TVM Register Persistence Policy

`adv_tvm_state: Option<TvmState>` is persistent — `#[serde(default)]` WITHOUT `#[serde(skip)]`. TVM register values (N, I, PV, PMT, FV, BEGIN/END mode) survive save/load cycles.

Decision source: D-43.11 (CONTEXT.md) — "TVM state is persistent (`#[serde(default)]`, not `skip`)."

This is an emulator extension relative to the OM's behavior (the HP-41 stored TVM values in numbered storage registers R00–R05, which always persisted). The emulator uses a dedicated `TvmState` struct — same persistence guarantee, different storage model.

The unique serde shape (default WITHOUT skip) follows the `rand_seed` precedent (ADR-v3.1-001 / D-33.4a) to avoid the Pitfall 20 muscle-memory trap.

Bucket 3 (Behavioral Policy).

### Topic 4: Matrix Size Cap

`ADV_MATRIX_MAX_ROWS: u8 = 255` and `ADV_MATRIX_MAX_COLS: u8 = 255` — the `u8` type enforces a 255-element maximum per dimension.

Decision source: D-43.2 (CONTEXT.md, Claude's Discretion) resolved during Phase 43 implementation. The 14×14 cap mentioned in REQUIREMENTS.md `## Out of Scope` was for consistency with Math Pac I. The actual implementation uses `u8` (255 max) since the Advantage Pac OM 00041-90482 Section 2 does not specify a fixed row/column cap — only an X-MEM file slot limit that does not apply to the emulator's `Vec<AdvMatrix>` model.

Document as: matrix size cap is 255×255 per dimension (u8 type constraint); hardware X-MEM slot limits do not apply to the emulator's named-matrix storage model (emulator extension).

Bucket 2 (Emulator Extension) — the emulator's unlimited matrix count (`Vec<AdvMatrix>` grows without cap per D-43.1) and 255×255 per-dimension cap are both documented here.

### Additional Candidate Topics

These are strongly implied by the implementation and should be included:

- **ADV_WORD_MASK 36-bit truncation** (D-43.9, D-43.10): NOT/AND/OR/XOR/ROTXY/BIT? mask to lower 36 bits; silent truncation on overflow. Bucket 3.
- **Solver self-nesting guard / cross-nesting allowance** (D-43.7): FSOLVE inside FINTG and vice versa are allowed (D-43.7); FSOLVE inside FSOLVE returns InvalidOp (self-nesting guard). Bucket 3.

### ADR-v3.3-001: Named-Matrix Storage Model (Vec<AdvMatrix>)

**Decision:** `adv_matrices: Vec<AdvMatrix>` on CalcState with `#[serde(default)]`. ALPHA register names the active matrix at op-call time. I/J indices (`adv_matrix_i`, `adv_matrix_j`) are global 1-based counters, persistent. Complete isolation from Math Pac I's `matrix_dim`/`matrix_active_reg` (D-43.5).

**Alternatives to document:**
- A: Map-based storage (`HashMap<String, AdvMatrix>`) — rejected for non-deterministic serialization order
- B: Register-based storage (using R14/R15+ like Math Pac I) — rejected per D-43.5 (incompatibility)
- C: File-based X-MEM model (full EMDIR/EMROOM) — rejected as post-v3.3 scope (XMEM-01)
- D: Per-matrix I/J indices (field inside AdvMatrix) — rejected because OM 00041-90482 treats I/J as calculator-global pointers

**Key context quote from 43-CONTEXT.md:** "Named-matrix storage MUST NOT touch `state.matrix_dim` or `state.matrix_active_reg`. Complete isolation between the two matrix systems."

### ADR-v3.3-002: FROOT Algorithm Choice — Laguerre's Method with Quadratic Deflation

**Decision:** Laguerre's method with initial guess (0.4, 0.9), quadratic deflation for complex conjugate pairs, linear deflation for real roots, root polishing against original polynomial. All arithmetic in f64 for numerical stability; converted to HpNum at final root output.

**Alternatives to document:**
- A: Bairstow's method (used by Math Pac I ROOTS) — rejected because it is degree-limited (2–5) and FROOT must handle arbitrary degree up to 100
- B: Jenkins-Traub algorithm — more robust convergence but significantly more complex (~300 LOC); Laguerre sufficient for HP-41 emulation use cases
- C: Companion matrix eigenvalue — requires dense linear algebra stack not otherwise needed in hp41-core; heavy implementation cost
- D: Durand-Kerner (Weierstrass) — requires all roots simultaneously, higher memory; Laguerre + deflation is sequential and simpler

**Bug discovered during implementation (relevant context):** Initial guess (0, 0) causes convergence failure for purely imaginary roots (x²+1 = 0) because G=0 at origin makes the Laguerre denominator degenerate. Resolved by using (0.4, 0.9) as starting point (43-07-SUMMARY.md).

**Source citation per ADR-v3.1-002 Free42 disclaim discipline:** "Algorithm independently re-derived from primary literature (Numerical Recipes §9.5 Laguerre's method); Free42 source consulted only as sanity-check oracle, not copied."

### ADR-v3.3-003: Dual-XROM-ID Design (XROM 22 + XROM 24)

**Decision:** Advantage Pac uses two XromModule constants: `ADV_MATH_A` (id=22, bit-3, covers ADV CONV + ADV MTRX, 63 ops) and `ADV_MATH_B` (id=24, bit-4, covers ADV MATH + ADV TVM, 51 ops). Resolver chain gains two new arms: bit-3 fires before bit-4.

**Key context:** The HP Advantage Pac (HP 00041-90482, 1985) ships on two ROM chips using XROM 22 and XROM 24 hardware IDs. This is a hardware constraint, not an emulator design choice.

**Alternatives to document:**
- A: Single XROM ID with unified 114-entry module — rejected because it violates hardware accuracy (the real Advantage Pac uses two distinct module IDs that XEQ-by-name dispatches independently)
- B: XROM 22 + XROM 23 — rejected; hardware uses 22 + 24 (HP's own module assignment)
- C: Flattened op namespace in one module — rejected; XROM shadowing test (Phase 44) confirmed 12 intentional MATH_1 overlaps in ADV_MATH_B that require independent resolver isolation (the bit-4-only resolver test uses `0b0001_0000` specifically to bypass MATH_1)

**Known architectural consequence:** ADV_MATH_B (XROM 24) has 12 intentional mnemonic overlaps with MATH_1 (XROM 7): E^Z, LNZ, LOGZ, Z^N, Z^1/N, Z^W, |Z|, SINZ, COSZ, TANZ, A^Z, CINV. When both modules are loaded (`xrom_modules = 0b0001_1111`), MATH_1 wins these names (resolver bit-0 fires first). This is hardware-faithful behavior per HP 00041-90482.

### ADR-v3.3-004: math1/ Visibility Promotion Policy (complex_atan2 pub(crate))

**Decision:** `complex_atan2` in `hp41-core/src/ops/math1/complex.rs` promoted from `pub(super)` to `pub(crate)`. This is a freeze carve-out consistent with ADR-v3.1-004 (math1-freeze-second-carve-out). No other math1/ file modified in Phase 43.

**Alternatives to document:**
- A: Re-implement `complex_atan2` in `advantage/complex_ext.rs` — rejected because it would duplicate logic that the freeze specifically protects; duplication is exactly what the freeze boundary prevents
- B: Move `complex_atan2` to a shared utility module — rejected as over-engineering; `pub(crate)` visibility promotion is the minimal surgical change per ADR-v3.1-004 precedent
- C: Keep `pub(super)` and call via a wrapper in math1/mod.rs — rejected; introduces unnecessary indirection without isolation benefit

**Freeze boundary status after v3.3:** `math1/` contains five sanctioned carve-outs now:
1. `xrom.rs` (ADR-v3.1-004, D-33.3) — XROM registry, bit-0/1/2 original + bit-3/4 Phase 43 extension
2. `modal.rs` (ADR-v3.1-004, D-33.3b) — ModalProgram dispatch, fourth `Advantage` variant added Phase 43
3. `complex.rs` — single visibility promotion `pub(super)` → `pub(crate)` for `complex_atan2` (Phase 43)

No other math1/ files were touched in Phase 43. All other math1/ files remain frozen per ADR-v3.1-004.

## Common Pitfalls

### Pitfall 1: ADV-DOC-01 is Already Done
**What goes wrong:** Plan adds a task to generate the function matrix or extend justfile.
**Why it happens:** Phase 45 success criteria says "generated by `just docs-matrix` (fifth invocation)" — could be read as future work.
**How to avoid:** Verify at plan-time: `just docs-matrix-check` exits 0, `docs/hp41-advantage-function-matrix.md` exists. The fifth invocation was added in Phase 44 Plan 01 (commit 919f1e1). No justfile changes needed in Phase 45.
**Warning signs:** Any plan task mentioning justfile or docs-matrix in Phase 45.

### Pitfall 2: Wrong ADR Identifier Range
**What goes wrong:** ADRs numbered `v3.3-001` through `v3.3-004` conflict with future phases' ADRs (Phase 46+ may need their own).
**Why it happens:** Phase 45 documents the first four decisions; future phases may add more.
**How to avoid:** Reserve `v3.3-001` through `v3.3-004` for Phase 45. Phase 47 (test hardening) should use `v3.3-005+` if any ADRs are needed there.

### Pitfall 3: Hard-Claim Language in README Soft-Claim
**What goes wrong:** README bullet says "feature-complete per Owner's Manual 00041-90482".
**Why it happens:** v3.0/v3.1/v3.2 soft-claims are conservative; the hard-claim is a graduation event.
**How to avoid:** Phase 47 graduates the hard-claim per the D-30.9 → D-32.5 → D-35.3 → D-37.11 cadence. Phase 45 uses soft-claim language only (~117 XEQ entry points, documented divergences).

### Pitfall 4: CLAUDE.md Block Includes Phases 46 and 47 as if Complete
**What goes wrong:** Plan writes full content for Phases 46 (GUI) and 47 (test hardening) in the CLAUDE.md block.
**Why it happens:** The v3.2 additions block in CLAUDE.md covers all five phases 38–42 in detail.
**How to avoid:** Write Phase 43 and 44 content in full detail. Write Phase 45 content (this phase). Write Phase 46 and 47 as forward stubs ("in progress — Phase 46 planned" / "Phase 47 planned"). The CLAUDE.md block will be updated when Phases 46 and 47 ship.

### Pitfall 5: Missing MATH_1 Alias Overlap Documentation
**What goes wrong:** ADR-v3.3-003 or the architecture narrative omits the 12 intentional MATH_1 alias overlaps in ADV_MATH_B.
**Why it happens:** This was discovered during Phase 44 execution (not in Phase 43 CONTEXT) and is easy to miss.
**How to avoid:** The 12 overlapping mnemonics (E^Z, LNZ, LOGZ, Z^N, Z^1/N, Z^W, |Z|, SINZ, COSZ, TANZ, A^Z, CINV) are documented in 44-02-SUMMARY.md and are hardware-faithful behavior. They MUST be documented in ADR-v3.3-003 and the divergences catalog.

### Pitfall 6: D-43.7 Cross-Nesting Not Documented
**What goes wrong:** The solver nesting policy (FINTG inside FSOLVE allowed; FINTG inside FINTG blocked) is omitted from the divergences catalog and ADR-v3.3-002.
**Why it happens:** D-43.7 is a CONTEXT.md decision that became a behavioral policy, not obviously a "divergence."
**How to avoid:** D-43.7 cross-nesting design belongs in bucket 3 of the divergences catalog. The OM does not explicitly specify whether FINTG inside FSOLVE works; the emulator's documented policy is that one level of cross-nesting is supported.

### Pitfall 7: adv_tvm_state Serde Shape Documentation
**What goes wrong:** CLAUDE.md or ADR documents `adv_tvm_state` as `#[serde(default, skip)]` instead of `#[serde(default)]` without skip.
**Why it happens:** The Pitfall 20 muscle-memory trap (every transient field uses skip) applies here — TVM state is intentionally NOT transient.
**How to avoid:** `adv_tvm_state` follows the `rand_seed` pattern (ADR-v3.1-001 / D-33.4a): `#[serde(default)]` WITHOUT skip. This is explicitly documented in `state.rs` lines 376–382 with a warning comment. Reproduce this warning in the CLAUDE.md block.

## Open Questions

1. **Matrix size cap in divergences catalog**
   - What we know: D-43.2 was Claude's Discretion; implementation uses `u8` (255 max). REQUIREMENTS.md out-of-scope table mentions 14×14 as a cap "for consistency with Math Pac I."
   - What's unclear: Whether 255 or 14 is the correct cap to document. The actual code uses u8 (255), not 14.
   - Recommendation: Document the u8 constraint (255×255) as the actual behavioral policy. The 14×14 was an out-of-scope design note in REQUIREMENTS.md, not the implementation. Verify by checking `ADV_MATRIX_MAX_ROWS` constant in `ops/advantage/mod.rs`.

2. **FROOT input register convention vs. OM**
   - What we know: Implementation uses X register for degree, R01..R(n+1) for coefficients (D-43.8 resolution). OM 00041-90482 Section 3 may specify a different convention.
   - What's unclear: Whether the emulator's register convention matches OM exactly (OM may use different register indexing).
   - Recommendation: This is a candidate for bucket 1 (OM Divergence) or bucket 3 (Behavioral Policy). Inspect the OM citation during Plan 45-01 execution. If register convention differs from OM, document as D-45-NN in bucket 1.
