**Bucket 1 — OM Divergences:** If no OM numerical divergences were identified during Phase 43-44 implementation, state that explicitly (same pattern as Time Pac bucket 1 which had no entries).

**Bucket 2 — Emulator Extensions (2 entries):**

- D-45-01: Unlimited named-matrix count. OM citation: "N/A -- emulator extension". Our behavior: `adv_matrices: Vec<AdvMatrix>` grows without artificial cap; any number of named matrices can coexist. OM behavior: HP-41 hardware limited by X-MEM file slot capacity (physical memory constraint). Rationale: The emulator's `Vec`-backed storage has no practical memory constraint analogous to X-MEM slots. Capping arbitrarily would reduce usability without emulating a meaningful hardware limit. See: D-43.1 (43-CONTEXT.md); `hp41-core/src/state.rs` (`adv_matrices` field).

- D-45-02: 255x255 per-dimension matrix size cap. OM citation: "N/A -- emulator extension". Our behavior: `ADV_MATRIX_MAX_ROWS: u8 = 255` and `ADV_MATRIX_MAX_COLS: u8 = 255` -- the `u8` type enforces a 255-element maximum per dimension. OM behavior: Hardware X-MEM slot limits constrained practical matrix sizes (typically much smaller). Rationale: The `u8` type provides a natural upper bound without artificial restriction. The OM does not specify a fixed row/column cap; the hardware limit came from available X-MEM file slots which do not apply to the emulator's `Vec<AdvMatrix>` model. See: D-43.2 (43-CONTEXT.md, Claude's Discretion); `hp41-core/src/ops/advantage/mod.rs` (`ADV_MATRIX_MAX_ROWS`, `ADV_MATRIX_MAX_COLS`).

**Bucket 3 — Behavioral Policies (7 entries):**

- D-45-03: Named-matrix vs. Math Pac I register model isolation. OM citation: OM 00041-90482 Section 2 (matrix operations). Our behavior: `adv_matrices: Vec<AdvMatrix>` is completely isolated from `state.matrix_dim` / `state.matrix_active_reg` (Math Pac I R14/R15+ register model). Zero code references to `matrix_dim`/`matrix_active_reg` in `advantage/` executable code. OM behavior: The two modules used different addressing mechanisms on hardware (XEQ-by-name dispatch; X-MEM file slots vs. numbered storage registers). Rationale: Complete isolation prevents silent data corruption between the two matrix systems. D-43.5 mandates this. See: D-43.5 (43-CONTEXT.md); ADR-v3.3-001; `hp41-core/src/ops/advantage/matrix.rs`.

- D-45-04: FROOT Laguerre vs. Math Pac I Bairstow coexistence. OM citation: OM 00041-90482 Section 3 (FROOT). Our behavior: FROOT uses Laguerre's method with quadratic deflation, supporting arbitrary degree (1-100); ROOTS (Math Pac I) uses Bairstow's method for degree 2-5. Both coexist via different mnemonics and different register conventions. OM behavior: The Advantage Pac FROOT and Math Pac I ROOTS were independent programs on hardware. Rationale: Two different polynomial root-finders with different capabilities and calling conventions. No conflict because they use different Op variants and different register layouts. See: D-43.8 (43-CONTEXT.md); ADR-v3.3-002; `hp41-core/src/ops/advantage/froot.rs`.

- D-45-05: TVM register persistence. OM citation: OM 00041-90482 Section 4 (TVM). Our behavior: `adv_tvm_state: Option<TvmState>` is persistent -- `#[serde(default)]` WITHOUT `#[serde(skip)]`. TVM register values (N, I, PV, PMT, FV, BEGIN/END mode) survive save/load cycles. OM behavior: The HP-41 stored TVM values in numbered storage registers (R00-R05) which always persisted. Rationale: Same persistence guarantee as hardware, different storage model (dedicated `TvmState` struct instead of numbered registers). The unique serde shape (default WITHOUT skip) follows the `rand_seed` precedent (ADR-v3.1-001 / D-33.4a). See: D-43.11 (43-CONTEXT.md); `hp41-core/src/state.rs` lines 376-382.

- D-45-06: `adv_current_matrix` transient -- clears on save. OM citation: OM 00041-90482 Section 2. Our behavior: `adv_current_matrix: Option<String>` is transient (`#[serde(default, skip)]`). The active matrix name clears to `None` on save/load. Users re-select the active matrix via ALPHA register on reload. OM behavior: On hardware, the current matrix was determined by the ALPHA register contents at call time (no persistent "current matrix" field). Rationale: Matches hardware semantics -- the ALPHA register is volatile across power cycles. See: D-43.3 (43-CONTEXT.md, Claude's Discretion); `hp41-core/src/state.rs`.

- D-45-07: ADV_WORD_MASK 36-bit truncation for bitwise ops. OM citation: OM 00041-90482 Section 1 (Base Conversion). Our behavior: NOT/AND/OR/XOR/ROTXY/BIT? mask all operands and results to lower 36 bits via `ADV_WORD_MASK = 0x0000_000F_FFFF_FFFF`. Overflow is silently truncated. OM behavior: The HP-41's 10-digit BCD mantissa provides exactly 36 bits of integer capacity; truncation is implicit in hardware. Rationale: Silent truncation matches hardware behavior per D-43.9/D-43.10. See: D-43.9, D-43.10 (43-CONTEXT.md); `hp41-core/src/ops/advantage/conv.rs`.

- D-45-08: Solver cross-nesting allowance. OM citation: OM 00041-90482 Section 3 (FSOLVE, FINTG). Our behavior: FINTG inside FSOLVE's callback (and vice versa) is allowed -- each solver guards only its own state field (`adv_fsolve_state`, `adv_fintg_state`). FSOLVE inside FSOLVE returns InvalidOp (self-nesting guard). Deeper mutual nesting (NEST-01) is deferred to post-v3.3. OM behavior: The OM does not explicitly specify whether solvers can be nested. Hardware behavior was constrained by the 4-level subroutine return stack. Rationale: One level of cross-nesting is the most common real-world use case (D-43.7). Each solver's state field is independent, so cross-nesting requires no special infrastructure. Self-nesting would corrupt the in-progress computation. See: D-43.7 (43-CONTEXT.md); `hp41-core/src/ops/advantage/fsolve.rs`, `hp41-core/src/ops/advantage/finteg.rs`.

- D-45-09: MATH_1 alias overlap in ADV_MATH_B (12 mnemonics). OM citation: OM 00041-90482 Section 3 (Complex Extensions). Our behavior: 12 ADV MATH mnemonics in XROM 24 overlap with Math Pac I (XROM 7): E^Z, LNZ, LOGZ, Z^N, Z^1/N, Z^W, |Z|, SINZ, COSZ, TANZ, A^Z, CINV. When both modules are loaded (`xrom_modules = 0b0001_1111`), MATH_1 wins (resolver bit-0 fires before bit-4). ADV_MATH_B's resolver (bit-4) is only reached when MATH_1 is unloaded. OM behavior: On hardware, XROM 7 and XROM 24 were separate ROM chips; the XEQ-by-name dispatcher resolved to whichever module was physically present, with the lower-numbered XROM winning ties. Rationale: Hardware-faithful resolution order. The `xrom_shadowing.rs` test uses `0b0001_0000` (bit-4 isolation) to verify ADV_MATH_B functions work independently. See: ADR-v3.3-003; Phase 44 discovery (44-02-SUMMARY.md); `hp41-core/src/ops/math1/xrom.rs`.

**ADR-v3.3-001: Named-Matrix Storage Model (Vec of AdvMatrix)**

Frontmatter: Status "Locked 2026-05-25", Owner "Plan 43-01", Requirement refs "ADV-FW-04, ADV-MTX-01", Downstream consumer "`hp41-core/src/state.rs` (`adv_matrices: Vec<AdvMatrix>`, `adv_matrix_i`, `adv_matrix_j`); `hp41-core/src/ops/advantage/matrix.rs`", ADR write-up prose "Phase 45 / Plan 45-01".

Context: The Advantage Pac (OM 00041-90482, 1985) uses named matrices identified by the ALPHA register, with X-MEM file slots as the underlying storage. Math Pac I (XROM 7) uses a separate register-based matrix model (`matrix_dim` via R14/R15, `matrix_active_reg`). The two matrix systems are fundamentally incompatible -- different addressing, different storage, different lifecycles.

Decision: `adv_matrices: Vec<AdvMatrix>` on CalcState with `#[serde(default)]`. ALPHA register names the active matrix at op-call time. I/J indices (`adv_matrix_i`, `adv_matrix_j`) are global 1-based counters, persistent. Complete isolation from Math Pac I's `matrix_dim`/`matrix_active_reg` (D-43.5).

Consequences: Positive (isolation prevents cross-system corruption, Vec grows unbounded, clean serde). Negative (two parallel matrix systems coexist -- users must understand which module's matrix operations they are using). Neutral (I/J as global matches OM behavior).

Alternatives (per D-30.7 verbatim quote discipline -- quote D-43.5 from 43-CONTEXT.md): Option B: HashMap-based storage (non-deterministic serialization); Option C: Register-based like Math Pac I (D-43.5 incompatibility); Option D: File-based X-MEM model (XMEM-01 post-v3.3); Option E: Per-matrix I/J indices (OM treats I/J as calculator-global).

Footnotes: [^1] OM 00041-90482 Section 2; [^2] 43-CONTEXT.md D-43.1/D-43.4/D-43.5; [^3] state.rs field locations. Footer: "*ADR-v3.3-001 locked: 2026-05-25. Plan 43-01.*"

**ADR-v3.3-002: FROOT Algorithm Choice -- Laguerre's Method with Quadratic Deflation**

Frontmatter: Status "Locked 2026-05-25", Owner "Plan 43-07", Requirement refs "ADV-MATH-06", Downstream consumer "`hp41-core/src/ops/advantage/froot.rs`", ADR write-up prose "Phase 45 / Plan 45-01".

Context: The Advantage Pac FROOT finds all roots of a polynomial of arbitrary degree (1-100). The existing Math Pac I ROOTS uses Bairstow's method limited to degree 2-5. A new algorithm is needed.

Decision: Laguerre's method with initial guess (0.4, 0.9) -- NOT (0, 0) because the origin causes convergence failure for purely imaginary roots (x^2+1=0, G=0 makes denominator degenerate). Quadratic deflation for complex conjugate pairs, linear deflation for real roots, root polishing against original polynomial. All arithmetic in f64 for numerical stability; converted to HpNum at final root output. Degree read from X register, coefficients from R01..R(n+1) per D-43.8.

MUST include the Free42 disclaim verbatim: "Algorithm independently re-derived from primary literature (Numerical Recipes section 9.5 Laguerre's method); Free42 source consulted only as sanity-check oracle, not copied."

Consequences: Positive (arbitrary degree, proven convergence, simple implementation). Negative (f64 intermediate arithmetic means results are not BCD-exact). Neutral (coexists with Math Pac I ROOTS via different mnemonics).

Alternatives: Option A: Bairstow (degree-limited 2-5); Option B: Jenkins-Traub (more robust but ~300 LOC); Option C: Companion matrix eigenvalue (requires dense linear algebra); Option D: Durand-Kerner (simultaneous, higher memory). Footer: "*ADR-v3.3-002 locked: 2026-05-25. Plan 43-07.*"

**ADR-v3.3-003: Dual-XROM-ID Design (XROM 22 + XROM 24)**

Frontmatter: Status "Locked 2026-05-25", Owner "Plan 43-01", Requirement refs "ADV-FW-01, ADV-FW-02", Downstream consumer "`hp41-core/src/ops/math1/xrom.rs` (ADV_MATH_A, ADV_MATH_B, adv_a_resolve, adv_b_resolve)", ADR write-up prose "Phase 45 / Plan 45-01".

Context: The HP Advantage Pac (HP 00041-90482, 1985) ships on two physical ROM chips with hardware XROM IDs 22 and 24. This is a hardware constraint, not a design choice.

Decision: Two XromModule constants: ADV_MATH_A (id=22, bit-3, ADV CONV + ADV MTRX, 63 ops) and ADV_MATH_B (id=24, bit-4, ADV MATH + ADV TVM, 51 ops). Resolver chain: bit-3 fires before bit-4. `xrom_modules = 0b0001_1111` (five bits for five modules). 12 intentional MATH_1 mnemonic overlaps in ADV_MATH_B (E^Z, LNZ, LOGZ, Z^N, Z^1/N, Z^W, |Z|, SINZ, COSZ, TANZ, A^Z, CINV) -- MATH_1 wins when both loaded (bit-0 fires first).

Consequences: Positive (hardware-accurate module assignment); Negative (two resolver arms + two resolve functions for one logical module); Neutral (12 overlaps are hardware-faithful, documented in divergences catalog D-45-09).

Alternatives: Option A: Single XROM ID (violates hardware accuracy); Option B: XROM 22 + 23 (hardware uses 22 + 24); Option C: Flattened namespace (12 overlaps require resolver isolation). Footer: "*ADR-v3.3-003 locked: 2026-05-25. Plan 43-01.*"

**ADR-v3.3-004: math1/ Visibility Promotion Policy (complex_atan2 pub(crate))**

Frontmatter: Status "Locked 2026-05-25", Owner "Plan 43-05", Requirement refs "ADV-MATH-09 through ADV-MATH-20", Downstream consumer "`hp41-core/src/ops/advantage/complex_ext.rs`", ADR write-up prose "Phase 45 / Plan 45-01".

Context: The Advantage Pac complex number extensions (SINZ, COSZ, TANZ, etc.) need `complex_atan2` from `math1/complex.rs`. The math1/ directory is frozen per ADR-v3.1-004.

Decision: Promote `complex_atan2` from `pub(super)` to `pub(crate)` in `hp41-core/src/ops/math1/complex.rs`. This is the third sanctioned carve-out after xrom.rs (D-33.3) and modal.rs (D-33.3b). No other math1/ file modified in Phase 43.

Document the complete list of five math1/ sanctioned carve-outs after v3.3: (1) xrom.rs -- XROM registry, bits 0-4; (2) modal.rs -- ModalProgram dispatch, Advantage variant added Phase 43; (3) complex.rs -- single visibility promotion for complex_atan2. All other math1/ files remain frozen.

Consequences: Positive (minimal change, prevents code duplication); Negative (another math1/ carve-out widens the exception list); Neutral (visibility promotion is the least invasive form of change).

Alternatives: Option A: Re-implement in advantage/complex_ext.rs (duplicates frozen logic); Option B: Move to shared utility module (over-engineering); Option C: Keep pub(super) with wrapper (unnecessary indirection). Footer: "*ADR-v3.3-004 locked: 2026-05-25. Plan 43-05.*"
