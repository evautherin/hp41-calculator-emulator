<task type="auto">
  <name>Task 2: Create numerical accuracy oracle suite for FROOT/FINTG/MDET/MINV</name>
  <files>hp41-core/tests/adv_numerical_accuracy.rs</files>
  <action>
    Create hp41-core/tests/adv_numerical_accuracy.rs with scipy-derived oracle cases for the four key Advantage Pac numerical algorithms per ADV-QUAL-04.

    The file must:
    1. Carry `#![allow(clippy::unwrap_used)]` per the test-file convention.
    2. Carry the Free42 disclaim header per the advantage module convention.
    3. Use `use hp41_core::{ops::{dispatch, Op}, state::CalcState, num::HpNum}` + `use rust_decimal::Decimal` + `use std::str::FromStr` + `use approx::assert_relative_eq`.
    4. Use `approx::assert_relative_eq!(actual, expected, max_relative = 1e-7)` for all f64 comparisons (NOT assert_eq! per Pitfall 17).

    **MDET oracle cases (>= 5):**
    Test MDET (Op::AdvMdet) by creating named matrices via dispatch, populating elements, and comparing the determinant to known values.
    - 2x2 identity matrix: det = 1.0
    - 2x2 [[1,2],[3,4]]: det = -2.0
    - 3x3 [[1,2,3],[4,5,6],[7,8,10]]: det = -3.0
    - 3x3 [[6,1,1],[4,-2,5],[2,8,7]]: det = -306.0
    - 4x4 Hilbert-like matrix: det = known value from scipy

    Setup helper: create a `setup_named_matrix(state: &mut CalcState, name: &str, rows: usize, cols: usize, elements: &[f64])` helper function that:
    a. Sets ALPHA to `name`.
    b. Pushes rows and cols onto the stack and dispatches `Op::AdvMatdim`.
    c. Iterates through elements and dispatches `Op::AdvMs` + `Op::AdvJPlus`/`Op::AdvIPlus` to populate the matrix in row-major order (increment j within each row, then increment i and reset j for the next row).
    d. Returns the state ready for MDET dispatch.

    Alternative simpler approach: use the MSIJ op to set each element by explicit (i,j) coordinates without managing index state. For each element, push i to Y and j to X onto stack, then dispatch AdvMsij. Wait, MSIJ reads the value from X and the indices from... check the actual semantics by reading advantage/matrix_ops.rs. The safest approach is to use the index navigation (I+/J+) pattern after starting from index (1,1), iterating in row-major order.

    Actually the simplest helper pattern: after MATDIM, the current index is (1,1). Store element, advance with appropriate index ops. For a row-major fill of an MxN matrix:
    - For each row i from 1 to M:
      - For each col j from 1 to N:
        - Push value to X, dispatch Op::AdvMs (stores at current index)
        - If j < N: dispatch Op::AdvJPlus (advance column)
      - If i < M: dispatch Op::AdvIPlus + reset j by dispatching Op::AdvJMinus (N-1) times, OR use I+ which may auto-wrap. Check the I+/J+ semantics for wrapping behavior.

    Actually, the cleanest pattern for tests: use MRC+ (read element and advance column) and MSC+ (store element and advance column) which auto-advance. Or just set indices explicitly and store:
    - For each element at (i,j), manually set adv_matrix_i = i and adv_matrix_j = j on the state directly (since this is a test, direct state access is allowed), then dispatch Op::AdvMs.
    - This avoids the I+/J+ navigation complexity entirely.

    Best test approach: access CalcState fields directly in tests to set up matrix contents, since these are unit tests not E2E tests. Create the AdvMatrix struct directly, push it to state.adv_matrices, set state.adv_current_matrix, and then dispatch Op::AdvMdet. This is the most deterministic approach.

    For the helper, read the AdvMatrix struct definition from advantage/mod.rs to understand its fields (name: String, rows: u8, cols: u8, data: Vec<HpNum>).

    **MINV oracle cases (>= 3):**
    Test MINV (Op::AdvMinv) by creating a known matrix, inverting, and verifying elements.
    - 2x2 [[1,2],[3,4]]: inverse = [[-2,1],[1.5,-0.5]]
    - 3x3 identity: inverse = identity
    - 2x2 [[4,7],[2,6]]: inverse = [[0.6,-0.7],[-0.2,0.4]]

    **FROOT oracle cases (>= 5):**
    FROOT finds roots of polynomials via Laguerre's method. The degree is in X, coefficients in R01..R(n+1). Test by setting up polynomial coefficients in registers and dispatching Op::AdvFroot.
    - x^2 - 1 = 0: roots +/-1 (degree 2, coefficients [1, 0, -1])
    - x^2 + 1 = 0: complex roots +/-i (verify real part ~0, imag part ~1)
    - x^3 - 6x^2 + 11x - 6 = 0: roots 1, 2, 3 (degree 3)
    - x^2 - 4x + 4 = 0: double root x=2 (degree 2)
    - x^4 - 1 = 0: roots +/-1, +/-i (degree 4)

    FROOT is a multi-step solver that uses run_loop re-entrancy for the polynomial evaluation callback. The test setup requires: degree in X, coefficients in R01..R(degree+1) in descending power order (leading coefficient in R01). After dispatch of Op::AdvFroot, roots are placed in registers. Read the FROOT implementation in advantage/solvers.rs (specifically op_adv_froot) to understand the exact register layout and output format.

    Since FROOT uses a user-program callback via run_loop, the test needs to set up a program in CalcState that evaluates the polynomial. Check existing FROOT inline tests in solvers.rs for the exact setup pattern.

    **FINTG oracle cases (>= 5):**
    FINTG integrates a user callback via Romberg integration. Similar to FROOT, it uses run_loop re-entrancy. Test by setting up a simple integrand program.
    - integral of x from 0 to 1 = 0.5
    - integral of x^2 from 0 to 1 = 1/3
    - integral of sin(x) from 0 to pi = 2.0
    - integral of 1/(1+x^2) from 0 to 1 = pi/4
    - integral of e^x from 0 to 1 = e - 1

    Read existing FINTG and FROOT inline tests in advantage/solvers.rs to understand the exact test setup pattern (program setup, register layout, dispatch sequence). Replicate that pattern for the oracle cases.

    If the solver tests require complex program setup that would be fragile, alternatively test FROOT and FINTG by verifying the mathematical properties of the output rather than exact values (e.g., verify that the roots of x^2-1 are close to +/-1 by checking the register values after dispatch).

    Oracle source: Python numpy.linalg.det / numpy.linalg.inv for matrix cases; numpy.roots / scipy.integrate.quad for solver cases. Record the oracle derivation in comment headers per the project convention.
