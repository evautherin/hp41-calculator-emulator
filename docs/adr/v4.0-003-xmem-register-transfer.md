# ADR-v4.0-003: Full-Register-Set SAVED/GETD

**Status:** Locked 2026-05-28
**Owner:** Plan 52-04
**Requirement refs:** XMEM-10
**Downstream consumer:** `hp41-core/src/ops/xmem/ops.rs` (`op_saved` — calls
`capture_data_card` to serialize full register set; `op_getd` — calls `load_data_card`
to restore full register set, padded to `MIN_REGS_AFTER_LOAD`);
`hp41-core/src/cardreader/mod.rs` (`capture_data_card`, `load_data_card`,
`MIN_REGS_AFTER_LOAD = 100`);
`docs/hp41-xmem-divergences.md` (D-52-02 — bbb.eee block control word divergence)

---

## Context

The HP-41CX Extended Memory `SAVED` operation stores the calculator's data registers
into a named DATA file in X-MEM. `GETD` restores registers from a named DATA file.
On real HP-41CX hardware, these operations use a **block control word** embedded in the
stack X register to specify which registers to transfer:

- The X register contains a value in `bbb.eee` format before calling `SAVED` or `GETD`.
- `bbb` (before the decimal point) specifies the beginning register number.
- `eee` (after the decimal point) specifies the ending register number.
- `SAVED` saves registers R_bbb through R_eee; `GETD` restores that range.

For example, `5.010 XEQ "SAVED"` saves R05 through R10 into a named DATA file.

The emulator implemented the SAVED/GETD register transfer in Phase 51 (D-51.5). Two
approaches were evaluated:

1. **bbb.eee block control word:** Parse the X register as `bbb.eee`, extract the range,
   and save/restore only the specified register range.
2. **Full-register-set transfer:** Ignore any X register value; always save/restore
   the entire register set R00..R(SIZE-1).

The `hp41-core/src/cardreader/mod.rs` module already provides `capture_data_card` and
`load_data_card` helpers (used by the card-reader `WRTD`/`REDD` operations) that
implement the full-register-set model. `MIN_REGS_AFTER_LOAD = 100` ensures that `GETD`
restores a minimum of 100 registers, padding with zeros if the saved file has fewer.

---

## Decision

**Full-register-set SAVED/GETD: `op_saved` calls `capture_data_card`; `op_getd` calls
`load_data_card` with padding to `MIN_REGS_AFTER_LOAD = 100`.**

The complete implementation (Phase 51 `hp41-core/src/ops/xmem/ops.rs`):

1. `op_saved`: Reads `state.alpha_reg` for the file name, calls `capture_data_card(state)`
   to serialize the full register set R00..R(SIZE-1) into a `DataCard` byte stream, stores
   the serialized data as an `XmemFile { kind: XmemKind::Data, data: serialized_bytes }`
   in `state.xmem_files`. If a file with the same name already exists, it is overwritten
   in place (D-51.6). The active file pointer `state.xmem_active_file` is updated to the
   saved file's name.

2. `op_getd`: Reads `state.alpha_reg` for the file name, locates the matching `XmemFile`
   in `state.xmem_files`, deserializes via `load_data_card` which restores the register
   set and pads to `MIN_REGS_AFTER_LOAD = 100`. The active file pointer
   `state.xmem_active_file` is updated to the loaded file's name.

3. The X register value is **not parsed** for a `bbb.eee` block control word. SAVED always
   saves the full register set; GETD always restores the full register set. This is a
   documented divergence (D-52-02 in `docs/hp41-xmem-divergences.md`).

---

## Consequences

### Positive

- **Reuses tested infrastructure.** `capture_data_card` and `load_data_card` are battle-
  tested helpers already used by the card-reader `WRTD`/`REDD` path. Phase 51 reuses
  their exact serialization format, meaning the save/restore correctness guarantees
  inherited from the card-reader tests apply directly to X-MEM SAVED/GETD.
- **Predictable, simple behavior.** Users know exactly what `SAVED` saves and what `GETD`
  restores — the entire register set. No need to set the X register to a `bbb.eee` range
  before each call. This reduces user error and simplifies programmatic use of SAVED/GETD.
- **`MIN_REGS_AFTER_LOAD = 100` provides a safety floor.** If a DATA file was saved with
  fewer than 100 registers (e.g., from a reduced-size program), `GETD` pads the restored
  register set to 100, preventing out-of-range `STO`/`RCL` errors in programs that assume
  at least 100 registers are available.
- **Forward-compatible data format.** The `DataCard` serialization format is stable across
  emulator versions (used since the card-reader implementation). X-MEM DATA files stored
  in Phase 51/52 will be restorable in future versions.

### Negative

- **Diverges from OM hardware behavior.** Real HP-41CX `SAVED`/`GETD` use the `bbb.eee`
  block control word for partial register transfers. Programs written for real HP-41CX
  hardware that use partial transfers (e.g., `5.010 XEQ "SAVED"` to save only R05–R10)
  will behave differently in this emulator — SAVED will save all registers regardless of
  the X value. This is documented as D-52-02 in `docs/hp41-xmem-divergences.md`.
- **Storage overhead for small transfers.** A user who wants to checkpoint only a small
  register range must still save/restore the entire register set. For the 600-register
  X-MEM capacity model (ADR-v4.0-002), a full save costs 101 registers (100 data + 1
  header), which is 16.8% of total X-MEM capacity per SAVED call.

### Neutral

- **`adv_matrices` are NOT affected by SAVED/GETD.** The named-matrix system
  (`adv_matrices: Vec<AdvMatrix>`) is completely separate from `state.regs`. SAVED/GETD
  operate on `state.regs` only — Advantage Pac matrices are unaffected (D-43.5 isolation,
  D-51.0a). This is verified by the XMEM-09 isolation tests in `xmem_backward_compat.rs`.
- **`xmem_active_file` update is a side effect, not a separate op.** SAVED and GETD both
  update `state.xmem_active_file` as a side effect, setting the active file for subsequent
  `EMREG`/`SAVERX` index operations (D-51.4). This mirrors the hardware behavior where the
  most-recently accessed DATA file becomes the active file.

---

## Alternatives Considered

### Option A: bbb.eee block control word (hardware-faithful partial transfer)

This alternative would implement the full OM-specified behavior: parse the X register as
`bbb.eee` before `SAVED`/`GETD`, extract `bbb` (beginning register) and `eee` (ending
register), and serialize/restore only registers R_bbb through R_eee.

The relevant context decision from 51-CONTEXT.md D-51.5 states verbatim:

> **D-51.5:** `SAVED` captures the **full current register set** R00..R(SIZE-1) (reuse
> `capture_data_card` logic); `GETD` replaces `state.regs` **wholesale**, padding back up
> to `MIN_REGS_AFTER_LOAD` (100) (reuse `load_data_card` logic). Both helpers already
> exist and are tested in `hp41-core/src/cardreader/mod.rs`. Chosen over the faithful
> bbb.eee block control-word (deferred — see Deferred Ideas).

**Why rejected (Phase 51):** Implementing `bbb.eee` block control-word parsing requires:
(a) a new decimal-field parser following the ISG/DSE string-split discipline (no
`floor()`/`fmod()` per CLAUDE.md invariant), (b) partial serialization of a sub-range
of `state.regs`, (c) range validation (bbb ≤ eee, both within `[0, SIZE-1]`), and (d) a
new test fixture covering partial-range round-trips. This work was deferred to a future
phase (candidate for v4.1 alongside ASCII/STATUS file types). The full-register-set
approach using tested helpers achieves the primary goal (register checkpoint/restore)
without the deferred complexity.

**Future upgrade path:** The `XmemFile` data format is byte-compatible with the card-reader
`DataCard` format. A future phase can add `bbb.eee` parsing to `op_saved`/`op_getd`
without changing the file format — the partial range would simply be stored as a smaller
register vector, still compatible with `load_data_card`'s zero-pad behavior.

### Option B: Separate field on `XmemFile` to track transfer range

This alternative would add `start_reg: u32` and `end_reg: u32` fields to `XmemFile`
to record which range was saved (defaulting to 0 and SIZE-1 for full-range saves),
in anticipation of future partial-transfer support.

**Why rejected:** The forward-compatibility rationale above applies here: the `DataCard`
byte format already carries implicit range information (the number of serialized registers
determines the range). Adding explicit range fields to `XmemFile` would add serde
complexity (`#[serde(default)]` needed, test fixture updates, migration arm) for a feature
not yet implemented. YAGNI — add the fields when the `bbb.eee` parsing lands, not
speculatively.
