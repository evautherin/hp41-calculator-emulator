# ADR v4.3-007: Reset Escape Hatch — Two-Tier In-App Recovery

**Status:** Accepted
**Date:** 2026-06-10
**Phase:** 67-reset-escape-hatch (Plans 01–05)

## Context

The HP-41 emulator persists `CalcState` to `~/.hp41/autosave.json` and reloads it on
every launch. This is the "continuous memory" model — faithful to the HP-41 hardware.
However, it creates a **resilience gap**: certain input-blocking fields (`modal_program`,
`pending_yield`, `is_running`, `prgm_mode`, etc.) can be saved while active, so a crash
or abnormal exit leaves the next launch in a trapped state. No operation available
through the normal key→`dispatch()`→`execute_op` path can escape such a trap, because
`dispatch()` itself may be stuck.

The iOS build exposed this gap acutely — an in-app restart (via Tauri's
`process::restart`) reloads from the autosave and reproduces the trap with 100%
reliability. Reinstalling the app was the only recovery option prior to Phase 67.

The real HP-41 exposes a hardware **ON key**: tapping it while the calculator is running
produces a "RUNNING" / non-responsive display, and holding it simultaneously with the
back-arrow key `←` triggers "MEMORY LOST" (continuous-memory wipe). The emulator cannot
faithfully replicate this chord across all platforms; it provides an intentional, safer
cross-platform approximation instead.

## Decision

Deliver a **two-tier in-app reset escape hatch** implemented in four plans (67-01 through
67-04), documented in this ADR and the corresponding divergence entries.

### Architecture

Both tiers operate **outside** the `key → Op → dispatch() → execute_op` path. This is a
deliberate, documented exception — the escape hatch must function even when `dispatch()`
itself is stuck (e.g. inside a `ModalProgram` handler that awaits user input). Neither
tier produces an `Op`; neither appears in any of the four required exhaustive-match sites
(CLAUDE.md §4-way exhaustive-match invariant does not apply to non-`Op` code paths).

#### Tier 1: Soft Reset

`CalcState::soft_reset(&mut self)` (Plan 67-01, `hp41-core/src/state.rs`):

- Clears every transient / input-trapping field: stack (`x/y/z/t/last_x`),
  `entry_buf`, `display_override`, `prgm_mode`, `user_mode`, `modal_program`,
  `modal_prompt`, `integ_state`, `solve_state`, `adv_solve_state`, `matrix_dim`,
  `matrix_active_reg`, `is_running`, `pc`, `call_stack`, `print_buffer`,
  `last_key_code`, `getkey_captured_code`, `pending_yield`, `pending_interrupt`,
  `pending_interrupt_alarm_index`, `pending_interrupt_depth`, `cancel_requested`
  (fresh `Arc`).
- **Preserves** all stored user data: `program`, numbered `regs`, `reg_m`/`n`/`o`,
  text registers, `flags`, `key_assignments`/`assignments`, `xmem_files`/
  `xmem_active_file`, `xrom_modules`, `time_offset_secs`, `rand_seed`,
  `adv_matrices`, `adv_tvm_state`, `angle_mode`, `display_mode`.

#### Tier 2: Full Reset / MEMORY LOST

`CalcState::memory_lost(&mut self)` (Plan 67-01):

```rust
*self = CalcState::new();
```

One line, field-completeness guaranteed by construction. Equivalent to receiving the
hardware "MEMORY LOST" message — all programs, registers, files, and user data erased;
factory state restored.

### Persistence Ordering Invariant (T-67-06)

Immediately after calling either reset method, each frontend **overwrites the autosave
while holding the mutex** (GUI: `AppState` `MutexGuard`; CLI: inline call before
returning from the handler). This guarantees that recovery survives an app restart — the
trapped state is gone from disk before the user sees the reset result. The auto-save
background thread (GUI) acquires the same mutex after the command returns and thus
serializes the already-reset state.

### Frontend Surfaces

**CLI (`hp41-cli`)** — Plan 67-02, `app.rs`:

- Trigger: `Ctrl+R` (intercepts at the very top of `handle_key`, above the
  `pending_input` routing block — documented intentional D-07 exception: the escape hatch
  must beat every stuck modal or pending-input state).
- Note: `Ctrl+R` conflicted with the former `Rdprgm` card-reader comfort shortcut;
  `Rdprgm` was reassigned to `Ctrl+E` (mnemonic: rEad program). This is documented in
  Plan 67-02 (67-02-D01).
- Two-tier status-bar state machine: `ResetPrompt::None` →
  `[s] soft / [f] full / [Esc] cancel` → on `f`: `MEMORY LOST? [y/n]`.
- Both tiers also clear CLI-only transient state: `shift_armed`, `pending_input`,
  `show_help`, `help_search_query`, `show_programs`.
- Synchronous `persistence::save_state` in the handler — no post-reset lag.

**GUI / iOS (`hp41-gui`)** — Plans 67-03 and 67-04:

- Tauri commands `reset_soft` and `reset_full` (Plan 67-03, `commands.rs`), each
  protected by a permission TOML (`permissions/reset-soft.toml`,
  `permissions/reset-full.toml`) and registered in `capabilities/default.json`.
- The `ON` key (formerly a dead, unresolved key with `id: ''`) is wired **outside**
  `key_map.resolve()` / `handleKeyClick` / `dispatch_op` via dedicated pointer props
  on `Keyboard.tsx` (Plan 67-04, `App.tsx`):
  - **Tap (< 600 ms)** → `reset_soft` → clears `shiftActive`, `pendingInput`.
  - **Long-press (≥ 600 ms)** → portaled MEMORY LOST confirm sheet
    ("MEMORY LOST — delete all programs, registers and files?") → on Confirm →
    `reset_full`.
  - Long-press **does not** fire a soft reset on the subsequent `pointerup`
    (`longPressFiredRef` no-double-fire guard — Plan 67-04, 67-04-D02).
  - Confirm sheet rendered via `createPortal(..., document.body)` to escape the
    `transform: scale()` ancestor (ADR-v4.1-005 iOS layout invariant — Plan 67-04,
    67-04-D03).
- The GUI commands call the core methods, persist under the mutex, and return
  `CalcStateView` so the frontend refreshes without a separate `get_state` round-trip.

## Intentional Divergences from Hardware ON Semantics

See `docs/hp41cv-divergences.md §D-CV-10` for the stable, cross-referenced entry.
This ADR records the intentionality:

1. **Soft reset clears working state.** On the real HP-41, pressing ON while a
   computation is running displays "RUNNING" — it does not clear the X register or
   stack. The emulator's soft reset intentionally clears the full working state
   (stack, entry buffer, all transient fields) to guarantee escape from any trapped
   configuration. This is a resilience trade-off, not a fidelity bug.

2. **Full reset maps to ON+← MEMORY LOST.** The real HP-41 requires a simultaneous
   ON + ← physical chord to trigger "MEMORY LOST". The emulator approximates this with
   a long-press + explicit confirm dialog — there is no touch-chord on a touchscreen,
   and the dialog serves as the confirmation safety that the chord provided on hardware.

3. **Long-press replaces the ON+← chord.** No physical key-chord is emulated. The
   600 ms long-press threshold was chosen as a cross-platform approximation consistent
   with the iOS touch convention for destructive long-press actions.

**Mitigation (T-67-12 repudiation):** This ADR makes the intentionality explicit so a
future maintainer will not treat these divergences as bugs to be "fixed" back toward
hardware behavior. The resilience requirement — surviving a persisted trap that reloads
on every launch — overrides ON-key fidelity here.

## Consequences

### Positive

- Users with a stuck calculator can recover without reinstalling the app or manually
  deleting `~/.hp41/autosave.json`.
- Both tiers bypass `dispatch()` and `execute_op`, so they function even when the
  key→Op resolver chain is itself stuck.
- Persistence-under-lock invariant prevents a race between the reset and the
  auto-save thread — the trapped autosave is overwritten atomically.
- 28 core integration tests (Plan 67-01), 13 CLI integration tests (Plan 67-02), 2
  GUI round-trip persistence tests (Plan 67-03), and 4 GUI vitest tests (Plan 67-04)
  cover all tiers, all frontends, and the persisted-trap recovery contract.

### Trade-offs

- Soft reset clears the working state (X/Y/Z/T, last_x, entry buffer, display_override)
  which is not hardware-faithful for a simple ON tap. This is the intentional divergence
  documented above.
- CLI `Ctrl+R` is a new keyboard binding that displaces `Rdprgm` (now `Ctrl+E`).
  Programs that relied on `Ctrl+R` → RDPRGM must now use `Ctrl+E` or `XEQ "RDPRGM"`.

### D-25.6 CLI↔GUI Parity

Both frontends implement the same two-tier model (soft + full/MEMORY LOST). The
frontends differ only in their input surfaces (Ctrl+R status-bar prompt vs. ON-key
tap/long-press), which is expected and accepted — D-25.6 governs one-shot SHIFT and
modal UI state, not the physical input mechanism. The core semantics (what
`soft_reset()` and `memory_lost()` do) are identical across frontends.

## Alternatives Considered

**Route through `dispatch()` with a special Op.**
Rejected: the escape hatch exists precisely because dispatch can be stuck; routing
through dispatch defeats the purpose.

**CLI-only or GUI-only implementation.**
Rejected: D-25.6 parity requires both frontends to expose the same capability. A
CLI-only escape hatch would leave iOS users dependent on reinstall.

**OS-level process kill / reinstall.**
Rejected: not discoverable; iOS users cannot easily delete app data without
reinstalling; the in-app escape hatch is zero-friction by comparison.

**Separate "recovery mode" on launch (detect + clear trapped fields on startup).**
Rejected for v4.3: requires defining a stable "trapped" predicate; risk of
false-positive clearing a legitimately suspended computation. Deferred as a possible
v4.4+ follow-up alongside the root-cause trap-bug fix.
