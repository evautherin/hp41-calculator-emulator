# ADR-v4.0-002: Fixed 600-Register X-MEM Capacity

**Status:** Locked 2026-05-28
**Owner:** Plan 52-04
**Requirement refs:** XMEM-10
**Downstream consumer:** `hp41-core/src/ops/xmem/mod.rs` (`XMEM_CAPACITY = 600`
constant; `registers_used()` helper; `has_room()` check);
`hp41-core/src/ops/xmem/ops.rs` (`op_emroom` returning `600 - registers_used`;
`op_savep` / `op_saved` raising NO ROOM when capacity exceeded)

---

## Context

The HP-41CX Extended Memory consists of physical "X-MEM" registers provided by up to
two optional plug-in X-Memory modules (HP 82181A), each adding 238 registers, on top of
the CX base register set of 124. A fully-expanded HP-41CX therefore has:

- 124 built-in registers (base HP-41CX)
- 238 registers (first X-Memory module)
- 238 registers (second X-Memory module)
- **Total: 600 registers**

The `EMROOM` function returns the number of X-MEM registers still available for storage.
`SAVEP` and `SAVED` raise a "NO ROOM"-style error when a file would not fit within the
available X-MEM capacity.

For the emulator, three capacity models were evaluated:

1. **Minimal (124 registers):** Matches the base HP-41CX without any X-Memory module.
2. **Fixed 600 registers:** Matches a fully-expanded HP-41CX (2 × 238 + 124).
3. **Unlimited:** No cap — `EMROOM` would always return a large constant.

The emulator's existing philosophy is to always model the maximally-equipped HP-41CX:
all five XROM plug-in modules co-loaded (`xrom_modules = 0b0001_1111`), 100 storage
registers (above the base HP-41CV 319-register model), etc. The X-MEM capacity decision
must be consistent with this philosophy.

---

## Decision

**Fixed 600-register X-MEM capacity: `XMEM_CAPACITY = 600`.**

The complete implementation (Phase 51 `hp41-core/src/ops/xmem/mod.rs`):

1. `XMEM_CAPACITY: u32 = 600` — the constant representing the fully-expanded HP-41CX
   X-MEM register count (124 built-in + 2 × 238 X-Memory module registers).

2. `registers_used()` on `Vec<XmemFile>` sums the register footprint of all stored files:
   - A PROGRAM file occupies `⌈program_bytes / 7⌉ + 1` registers (HP-41 packs 7 program
     bytes per X-MEM register, plus 1 directory/header register).
   - A DATA file occupies `N + 1` registers (N data registers + 1 header register).

3. `op_emroom` returns `XMEM_CAPACITY - registers_used()` pushed onto the stack as an
   `HpNum`. When X-MEM is empty, `EMROOM` returns `600`. As files accumulate, the
   returned value decreases — the user can see a real, decreasing counter rather than a
   meaningless constant.

4. `op_savep` and `op_saved` call `has_room(required_registers)` before storing a file,
   and return `Err(HpError::NoRoom)` when the file would not fit. This raises a
   hardware-faithful "NO ROOM" display error.

---

## Consequences

### Positive

- **Consistent with the maximally-equipped emulator philosophy.** The emulator already
  models the fully-expanded HP-41CX across every other dimension (all 5 XROM modules
  co-loaded, 100 storage registers, etc.). Using 600 X-MEM registers continues this
  convention. Users familiar with the fully-expanded HP-41CX hardware will see the
  expected `EMROOM` value of 600 on an empty X-MEM.
- **`EMROOM` is meaningful.** A fixed capacity means `EMROOM` decreases as files are
  stored, giving users real feedback about X-MEM utilization. This is the core UX
  promise of the `EMROOM` function.
- **`NO ROOM` is a tested, warranted error.** The 600-register cap ensures `SAVEP`/`SAVED`
  can raise a genuine overflow error in tests, providing a real quality gate for the
  capacity accounting logic. The "NO ROOM" error path cannot be tested with an unlimited
  model.
- **Hardware-accurate for fully-expanded CX.** HP 82181A documentation specifies 238
  registers per module; 2 modules + 124 base = 600 total. The constant is traceable to
  HP hardware specifications.

### Negative

- **May exceed real HP-41CX configurations.** Users with only one X-Memory module
  (362 registers) or no X-Memory modules (124 registers) will see a larger `EMROOM`
  than their hardware would show. This is a documented emulator extension — the emulator
  does not model partially-equipped hardware configurations.
- **Fixed cap could theoretically be hit in emulator usage.** If a user stores many large
  programs/data files, they could run out of emulated X-MEM. The 600-register cap is
  generous for typical use but is not unlimited.

### Neutral

- **Register accounting formula is HP-faithful (D-51.2).** The 7-bytes-per-register
  program packing and 1-header-register convention reflect the HP-41CX X-MEM hardware
  data model. Future refinements to the accounting formula (if OM verification reveals
  a different packing) can be made without changing `XMEM_CAPACITY`.
- **`EMROOM` is a stack-push operation.** The returned value is a plain `HpNum` on the
  X register — compatible with arithmetic and conditional tests. Users can write programs
  that check `EMROOM` and respond accordingly.

---

## Alternatives Considered

### Option A: Minimal capacity (124 registers — no X-Memory modules)

This alternative would model the base HP-41CX capacity without optional X-Memory modules.
`XMEM_CAPACITY = 124`.

**Why rejected:** 124 registers is far too small for practical use. A single 100-register
DATA file (via `SAVED`) would fill 101 registers (100 data + 1 header), immediately
exceeding the 124-register base capacity after just a few operations. Users would
encounter "NO ROOM" errors with trivial workloads, making the X-MEM feature nearly
unusable. More critically, this contradicts the emulator's maximally-equipped philosophy
— the emulator always provides the most capable HP-41CX configuration.

### Option C: Unlimited capacity (no cap)

This alternative would store arbitrarily many files with no capacity limit. `EMROOM`
would return a constant large value (or the maximum `HpNum`).

**Why rejected:** An unlimited model breaks the `EMROOM` contract. On real HP-41CX
hardware, `EMROOM` is a meaningful measurement — it tells users how many registers remain
before the next `SAVEP`/`SAVED` will fail. Returning a constant large value would make
`EMROOM` useless as a planning tool. Additionally, the "NO ROOM" error path for
`SAVEP`/`SAVED` becomes untestable and unreachable — removing a real quality gate.
The 600-register cap provides a concrete, testable overflow boundary while still being
generous enough for realistic workflows.

### Option D: Configurable capacity (user-settable via a flag or setting)

This alternative would expose `XMEM_CAPACITY` as a user-configurable parameter, allowing
users to model different hardware configurations (no modules: 124; one module: 362;
two modules: 600).

**Why rejected:** Configurability adds complexity without commensurate value. The emulator
does not model any other hardware resource limit as user-configurable (the 100-register
count, XROM modules, stack depth are all fixed). Introducing a capacity setting for X-MEM
alone would be an inconsistency. The maximally-equipped stance is the simplest correct
default, and users who need a specific capacity model can use `ASN` to avoid filling X-MEM
or can structure their programs accordingly.
