# ADR v4.3-001 — Single-Instance Guard (no duplicate tray icon)

**Status:** Accepted
**Date:** 2026-06-06
**Context:** Post-v4.2 desktop polish (user report: launching the macOS menu-bar app twice yields two tray icons)

## Context

The macOS menu-bar app (ADR-v4.1-001) builds its tray icon in `setup_tray()` once
per process. macOS's built-in single-instance behavior only covers double-clicking
the *same* `.app` bundle; launching the dev build (`just gui-dev` / `cargo run`),
`open -n`, or a second copy of the bundle spawns a second process — and therefore a
second tray icon. The user asked for this to be prevented, and for the second launch
to surface the running instance instead.

## Decision

Adopt `tauri-plugin-single-instance` (desktop-only crate), registered as the **first**
plugin (per plugin docs, so it runs before anything else can interfere). When a second
launch is attempted:

- the already-running instance receives the plugin callback and **surfaces itself** —
  on macOS in menu-bar mode it shows the popover (under the last-clicked tray rect, or
  a top-right fallback); otherwise it shows + focuses the main window;
- the second process exits immediately (plugin behavior), so no duplicate tray icon is
  ever created.

The dependency is gated to desktop targets
(`cfg(not(any(target_os = "android", target_os = "ios")))`); the callback helper
`focus_existing_instance` is `#[cfg(desktop)]` and its popover branch is
`#[cfg(target_os = "macos")]`.

## Consequences

- New GUI-workspace runtime dependency: `tauri-plugin-single-instance` (does not touch
  the "zero new runtime deps in hp41-core" invariant — `hp41-core` is unaffected).
- Also fixes the developer annoyance of two dev processes fighting over one tray.
- The "surface the running instance" path reuses the shared `tray::surface_popover`
  introduced alongside the global hotkey (ADR-v4.3-002); both depend on
  `PopoverState.last_tray_rect`.
- No `hp41-core`, IPC-contract, or `Op` changes; SC-4 and bundle ID unchanged. iOS build
  unaffected (verified by `cargo check --target aarch64-apple-ios`).

## Alternatives considered

- **Rely on macOS LaunchServices** — rejected: only guards same-bundle double-clicks;
  misses dev runs, `open -n`, and second bundle copies (exactly the reported cases).
- **Hand-rolled lockfile / port bind** — rejected: re-implements what the maintained
  plugin already does cross-platform (socket on macOS/Linux, named mutex on Windows).
