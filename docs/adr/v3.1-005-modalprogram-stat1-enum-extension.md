# ADR-v3.1-005: `ModalProgram::Stat1(Stat1Step)` Enum Extension — Single `ModalProgram` Enum, No Parallel `Stat1ModalProgram`

**Status:** Locked 2026-05-22
**Owner:** Phase 33 plan-phase (D-33.3b)
**Requirement refs:** STAT-FW-03 (4-way exhaustive-match invariant items 1+2), STAT-CLI-05 (modal-prompt routing reuses `print_buffer` + `modal_program`), STAT-GUI-04 (Phase 36 — LCD-alternation modal prompts reuse existing infrastructure), Pitfall 22 (33-RESEARCH.md §"Mnemonic shadowing")
**Downstream consumer:** `hp41-core/src/ops/math1/modal.rs` (the v3.0 `ModalProgram` enum gains the `Stat1(Stat1Step)` variant alongside the 6 existing Matrix / Solve / Poly / Integ / Difeq / Four variants); `hp41-core/src/ops/stat1/modal.rs` (`Stat1Step` enum + 5 variants: `NormdModeChoice`, `ChisqdNuPrompt`, `ChisqdModeChoice`, `PolypDegreePrompt`, `SeedPrompt` — lives OUTSIDE the math1/ freeze boundary per ADR-v3.1-004); `hp41-cli/src/keys.rs` + `hp41-gui/src-tauri/src/key_map.rs` (Phase 34 CLI + Phase 36 GUI modal-prompt routing consume the `Stat1` variant via the existing `print_buffer` + `modal_program` infrastructure)
**ADR write-up prose:** Phase 35 / STAT-DOC-04 (this is the narrative ADR; the lock happened during Phase 33 plan-phase user-confirmed session 2026-05-22)

---

## Context

`hp41-core/src/ops/math1/modal.rs` defines the v3.0 modal state machine for
prompt-driven Math Pac I workflows. The enum lists six variants:

```rust
pub enum ModalProgram {
    Matrix,
    Solve,
    Poly,
    Integ,
    Difeq,
    Four,
}
```

Each variant corresponds to a single Math 1 program that opens a modal prompt
on `XEQ` and exits the modal state on R/S submit or ESC cancel. The
4-way exhaustive-match invariant (CLAUDE.md) applies: every match on
`ModalProgram` in `current_prompt()`, `requires_alpha_label()`, and
`submit_step()` must enumerate all variants — no `_ => ...` catch-all is
permitted.

Stat 1 Pac introduces 5 distinct multi-step modal workflows:

- **ΣNORMD** (3-mode dispatcher): on `XEQ "ΣNORMD"`, the program reads X
  as the mode index (1 = CDF, 2 = PDF, 3 = inverse) and dispatches.
- **ΣCHISQD** (ν entry + 2-mode dispatcher): prompts for `ν =?` (degrees of
  freedom), then for the 2-mode dispatcher (PDF / CDF) using the captured ν.
- **ΣPOLYP** (DEGREE entry + regression): prompts for `DEGREE =?` (polynomial
  degree), then runs the regression.
- **SEED** (ALPHA seed prompt): opens an ALPHA-mode prompt to capture the
  initial LCG seed for ADR-v3.1-001.
- **(Bonus iteration step)** for the chi-square ν-then-mode chained prompt.

Two architectural choices were evaluated during Phase 33 plan-phase:

- **Option A:** extend the existing `math1/modal.rs` `ModalProgram` enum with
  ONE new variant `Stat1(Stat1Step)`, where `Stat1Step` is a new enum
  declared in `stat1/modal.rs` carrying the 5 step variants. The dispatch
  wiring in `math1/modal.rs` is ~8 lines.
- **Option B:** spawn a parallel `Stat1ModalProgram` enum in `stat1/modal.rs`
  with its own dispatcher + its own `CalcState` field. Every frontend (CLI +
  GUI) would dispatch on EITHER variant at every prompt site.

This ADR locks Option A. The architectural choice is paired with ADR-v3.1-004
(the `math1/` freeze second carve-out): together they enable the 8-line modal
extension while preserving the `math1/` tree's freeze invariant for every
other file.

---

## Decision

**Option A is locked: `ModalProgram` gains a single new variant
`Stat1(Stat1Step)` alongside the 6 v3.0 Math 1 variants.** `Stat1Step` is a
separate enum in `hp41-core/src/ops/stat1/modal.rs` with 5 variants:

```rust
// hp41-core/src/ops/stat1/modal.rs (excerpt)
pub enum Stat1Step {
    NormdModeChoice,           // ΣNORMD opens here; X = mode index
    ChisqdNuPrompt,            // ΣCHISQD opens here; X = ν
    ChisqdModeChoice,          // after ChisqdNuPrompt captures ν, dispatch on mode
    PolypDegreePrompt(usize),  // ΣPOLYP opens here; payload = captured degree
    SeedPrompt,                // SEED opens here; ALPHA-mode capture
}
```

The dispatch wiring in `math1/modal.rs` (added per ADR-v3.1-004's carve-out)
totals approximately 8 lines:

```rust
// hp41-core/src/ops/math1/modal.rs (excerpt — the carve-out delta)
pub enum ModalProgram {
    Matrix, Solve, Poly, Integ, Difeq, Four,
    // D-33.3b: Stat 1 Pac modal prompts delegate to stat1::modal.
    Stat1(crate::ops::stat1::modal::Stat1Step),
}

impl ModalProgram {
    fn current_prompt(&self) -> &str {
        match self {
            // ... v3.0 arms ...
            ModalProgram::Stat1(step) => crate::ops::stat1::modal::current_prompt(step),
        }
    }
    fn requires_alpha_label(&self) -> bool {
        match self {
            // ... v3.0 arms ...
            ModalProgram::Stat1(step) => crate::ops::stat1::modal::requires_alpha_label(step),
        }
    }
}
```

The Stat1Step variant semantics live entirely in `stat1/modal.rs`: the
per-step `submit_step()` impls, the prompt-string formatters, and the
ALPHA-vs-numeric routing all reside there. No Stat 1 Pac semantics leak into
`math1/modal.rs` — the math1-side delta is pure dispatch wiring that delegates
to `stat1::modal::*` functions.

The 4-way exhaustive-match invariant is preserved: every existing match
expression on `ModalProgram` gains exactly one new `Stat1(_) => ...` arm
that delegates. The compile-time exhaustive match in both
`hp41-cli/src/ui.rs::pending_prompt()` and the GUI equivalent forces the new
variant to land in 4 sites before any caller compiles. This is the standard
3+4 surface from CLAUDE.md's "4-way exhaustive-match invariant" section
applied to a modal-program variant.

The ADR pairs with ADR-v3.1-004 (`math1/` freeze second carve-out): -005 is
the enum-design view (single ModalProgram, nested step enum); -004 is the
freeze-invariant view (which files in `math1/` may legitimately change to
land the variant). Both lock the same Phase 33 D-33.3b decision from two
different perspectives.

## Consequences

### Positive

- **4-way exhaustive-match invariant items 1+2 (CLAUDE.md) preserved.** The
  new Stat1 variant lands in `dispatch()` + `execute_op()` exactly once each
  (Phase 33); Phase 34 + Phase 36 wire it through CLI `prgm_display` + GUI
  `prgm_display` (4-way invariant items 3+4) by analogy to the v3.0 cadence.
  Single source-of-truth for the `modal_program` field on `CalcState` (v3.0
  D-30.5 `ModalProgram` extension precedent).
- **Minimal blast radius per new prompt site.** Every match on
  `ModalProgram` adds one new line: `ModalProgram::Stat1(step) =>
  crate::ops::stat1::modal::<fn>(step)`. The delegation pattern keeps the
  v3.0 modal-machinery files (`math1/modal.rs`) free of stat1-specific
  match arms.
- **Future v3.2+ pacs inherit the same pattern.** A Time Pac would add
  `Time(TimeStep)` to `ModalProgram` and declare `TimeStep` in
  `time/modal.rs`. An Advantage Pac would add `Advantage(AdvantageStep)`.
  The precedent scales by analogy without re-litigating the enum design.

### Negative

- **`math1/modal.rs` gains ~8 lines (the new dispatch arm + the import for
  Stat1Step).** ADR-v3.1-004 covers this carve-out (math1/ freeze second
  carve-out). The carve-out is the documented exception; the lines are pure
  dispatch with no Free42 / OM-derived content.
- **Cross-file delegation tightens the coupling between `math1/modal.rs` and
  `stat1/modal.rs`.** A future renaming of `Stat1Step` variants forces an
  edit in both files. Mitigated by the trait-bound-free design — there's no
  `impl Trait for Stat1Step` surface in `math1/`, only a delegation call —
  so changes to `Stat1Step` semantics are local to `stat1/modal.rs`.

### Neutral

- **Future v3.2+ pacs (Time, Advantage) inherit the same pattern.** Add a
  new `ModalProgram::Time(TimeStep)` variant + a new `TimeStep` enum in
  `time/modal.rs`; the precedent scales without re-deciding the enum-design
  question per pac.
- **Phase 34 + Phase 36 inherit the wiring without surprise.** The CLI's
  `pending_prompt()` exhaustive match (CLAUDE.md TUI key files) and the GUI's
  Phase 36 LCD-alternation modal prompts both add a single new arm to
  delegate to `stat1::modal`. STAT-CLI-05 + STAT-GUI-04 explicitly call out
  the reuse of existing infrastructure rather than introducing a new
  prompt-state pipeline.
- **`print_buffer` + `modal_program` `CalcState` fields are unchanged.** No
  new fields on `CalcState` are needed for the Stat 1 modal flow — the
  existing fields are reused because `modal_program: Option<ModalProgram>`
  already wraps the new variant transparently.

## Alternatives Considered

### Option B: Spawn a parallel `Stat1ModalProgram` enum in `stat1/modal.rs`

The rejected alternative is described verbatim in 33-CONTEXT.md D-33.3b
(locked 2026-05-22):

> **D-33.3b** (amended 2026-05-22, user-confirmed during `/gsd-plan-phase 33`):
> Break the `math1/` freeze a SECOND time for `modal.rs` only. Extend
> `hp41-core/src/ops/math1/modal.rs` in place with:
>   - `ModalProgram::Stat1(stat1::modal::Stat1Step)` enum variant (one line,
>     alongside `Matrix`, `Solve`, `Poly`, `Integ`, `Difeq`, `Four`)
>   - Sibling dispatch arms for `submit_step()`, `current_prompt()`, and
>     `requires_alpha_label()` — each delegating to the `stat1::modal` impls
>     (3-arm parity with the existing 6 variants)
>   - `Stat1Step` itself lives in the new `hp41-core/src/ops/stat1/modal.rs`
>     so the math1/modal.rs delta stays to ~8 lines of pure dispatch wiring
>     (no Stat 1 Pac semantics leak into the frozen module)
>   - Update CLAUDE.md "Frozen Invariants → Core engine" to list `modal.rs`
>     alongside `xrom.rs` as the two carved-out files; the rest of math1/
>     remains strictly frozen
>   - Rationale: chosen over a parallel `Stat1ModalProgram` enum (would have
>     required ~80 lines of plumbing across state.rs + commands.rs + app.rs
>     to thread two modal-program enums) and over inline single-prompt Ops
>     (would have diverged from OM 00041-90094 user flow for SEED, ΣPOLYP
>     DEGREE=?, ΣCHISQD ν=? and risked failing SPEC.md acceptance
>     criteria). The 8-line freeze amendment beats permanent infrastructure
>     duplication.

**Additional context on why Option B was rejected:**

- **Cost: ~80 lines of cross-frontend duplication.** The CLI + GUI + test
  surfaces each carry TWO modal-program enums and dispatch on EITHER variant
  at every prompt site. The 4-way exhaustive-match invariant compounds
  across two enums: each new variant in either enum must land in 4 dispatch
  sites; the cognitive load doubles per pac.
- **Loss of single-source-of-truth.** v3.0 D-30.5 (`ModalProgram` extension)
  locked `ModalProgram` as the canonical modal state. Spawning
  `Stat1ModalProgram` violates the lock and sets a precedent for v3.2+ pacs
  (Time → `TimeModalProgram`, Advantage → `AdvantageModalProgram`); the
  proliferation defeats the v3.0 ADR-001 (Op-strategy A) single-Op-enum
  invariant by analogy.
- **Future pacs would each spawn their own ModalProgram enum.** A Time Pac
  adds `TimeModalProgram`; an Advantage Pac adds `AdvantageModalProgram`;
  the dispatch sites multiply per pac. The single-`ModalProgram`-with-nested-
  step-enums pattern (Option A) keeps the cost per new pac at one new
  variant + one delegation arm.

### Option C: Add Stat1 variants directly to `ModalProgram` (no nested `Stat1Step`)

A third option was considered: add 5 separate variants to `ModalProgram`
(one per Stat1Step value), e.g. `ModalProgram::Stat1NormdModeChoice`,
`ModalProgram::Stat1ChisqdNuPrompt`, `ModalProgram::Stat1ChisqdModeChoice`,
`ModalProgram::Stat1PolypDegreePrompt(usize)`, `ModalProgram::Stat1SeedPrompt`.

**Why rejected:** 5 new variants in `math1/modal.rs` (instead of 1 nested
variant); each requires its own dispatch arm in `current_prompt()`,
`requires_alpha_label()`, and `submit_step()`. The math1/ freeze carve-out
scope blows up from ~8 lines to ~30 lines, defeating ADR-v3.1-004's
narrow-carve-out goal. The nested `Stat1Step` enum (Option A) keeps the
`math1/modal.rs` freeze footprint minimal by pushing the 5-variant complexity
into `stat1/modal.rs` where it belongs.
