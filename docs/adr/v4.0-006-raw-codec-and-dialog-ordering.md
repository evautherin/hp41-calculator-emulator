# ADR-v4.0-006: .raw Multi-Program Codec and Tauri Anti-Deadlock Dialog Ordering

**Status:** Locked 2026-05-27
**Owner:** Plans 50-01, 50-02

---

## Context

Phase 50 adds `.raw` file I/O to both the GUI and CLI. The HP-41 `.raw` format is the de facto
community-standard binary encoding for HP-41 programs — programs are encoded as one byte per
instruction, with a 3-byte END marker (`0xC0 0x00 0x0D`) delimiting each program. Community
archives commonly bundle multiple programs in a single `.raw` file with adjacent END markers.

Two distinct architectural decisions arose:

### Decision A: .raw multi-program codec

The existing `hp41-core/src/cardreader/raw.rs` already contained `decode_program` and
`encode_program` for single programs. Phase 50 requires importing multi-program archives.
The codec decision has two sub-questions:

1. **How should multi-program archives be split?** A `.raw` file containing N programs has N
   END markers. The decoder must identify segment boundaries reliably without reimplementing the
   per-byte op decoder.

2. **How should a program be identified for a picker UI?** When a multi-program archive is
   displayed in a picker overlay, each entry needs a human-readable label. HP-41 programs may
   have a `LBL "NAME"` as their first instruction, or they may be anonymous.

3. **What prevents a crafted `.raw` archive from causing memory exhaustion?** A malformed file
   could contain thousands of consecutive END markers, causing `decode_all_programs` to push
   thousands of `DecodedProgram` entries before the DoS guard fires.

### Decision B: Tauri file dialog and AppState Mutex ordering

The Tauri `State<'_, AppState>` extractor holds a `Mutex<CalcState>`. The file dialog API
(`app.dialog().file().blocking_pick_file()`) is a blocking call that waits for the user to
interact with a native OS file picker — potentially for seconds or minutes.

If the implementation acquires the `AppState` Mutex lock BEFORE opening the file dialog, the
Mutex is held for the entire duration of the user's interaction with the file picker. On macOS
and other platforms, a Tauri command that holds a Mutex across an OS dialog call can deadlock:
the main thread is blocked on the dialog call; another Tauri command that needs the Mutex (e.g.,
a `tick_time` call from the `setInterval` live-clock timer) cannot acquire it and hangs. If the
Tauri dispatch queue uses a single-threaded execution model for `async` commands, this creates a
complete deadlock with no recovery path.

This is RESEARCH Pitfall 1 in the Phase 50 planning artifacts: "AppState Mutex + blocking dialog:
hold the lock across the dialog await → deadlock. Dialog must complete before any lock is acquired."

## Decision

### Decision A: `decode_all_programs` splits at END markers, delegates per-segment to `decode_program`; 256-program cap; `picker_label` derives a human-readable entry label

**`decode_all_programs(bytes: &[u8]) -> Result<Vec<DecodedProgram>, HpError>`** in
`hp41-core/src/cardreader/raw.rs`:

1. Scans the byte slice for END markers (`0xC0 0x00 0x0D`) using `windows(3).position()` to
   find the first END marker from the current scan position. Each END marker (inclusive) forms
   one segment boundary.

2. Delegates each segment to the existing `decode_program(&segment[..end+3])` — the same
   per-byte op decoder used for single-program import. No duplicate parser logic; all validation
   (invalid byte → `HpError::CardData`, synthetic byte filtering) is inherited from `decode_program`.

3. Wraps each decoded result in `DecodedProgram { ops: Vec<Op>, byte_len: usize }`.
   `byte_len` is the raw byte count of the segment (END marker inclusive), used by `picker_label`
   for the size annotation.

4. **256-program cap** (`ARCHIVE_CAP = 256`): before pushing each `DecodedProgram`, if
   `programs.len() >= ARCHIVE_CAP` the function returns `Err(HpError::CardData)` with a
   descriptive message. The cap blocks memory exhaustion from crafted inputs (T-50-01 DoS guard).
   256 is a practical upper bound for HP-41 community archives.

5. Returns an empty `Vec` for an empty input (no programs found), `Err(HpError::CardData)` for
   malformed data (delegate propagates per-byte errors), or `Ok(Vec<DecodedProgram>)` for success.

**`picker_label(index: usize, ops: &[Op], byte_len: usize) -> String`**:

1. Iterates `ops` looking for the first `Op::Lbl` instruction. If found, formats
   `"NAME (N bytes)"` where `NAME` is the label string and `N` is `byte_len`.

2. If no `Op::Lbl` is found, formats `"Program N (N bytes)"` using 1-based numbering
   (`index + 1`) per HP-41 UI conventions. This fallback label is used for anonymous programs.

`DecodedProgram` and `picker_label` are re-exported from `hp41-core/src/cardreader/mod.rs` so
Tauri commands in `hp41-gui` can consume them without importing the `raw` submodule directly.

### Decision B: Open native dialog BEFORE acquiring the AppState Mutex lock; use three-phase I/O

All five dialog commands in `hp41-gui/src-tauri/src/commands.rs` follow the **three-phase pattern**:

- **Phase 1 (no lock):** Open the native OS file dialog or file save dialog via
  `app.dialog().file().blocking_pick_file()` or `.blocking_save_file()`. If the user cancels,
  acquire the lock briefly for a `get_state` snapshot and return immediately.

- **Phase 2 (no lock):** Perform file I/O and decoding/encoding. Read the file bytes, call
  `decode_all_programs` / `decode_program` / `decode_data` / `encode_program` / `capture_data_card`.
  Return early with an error if the file is unreadable or the decode fails.

- **Phase 3 (lock for mutation only):** Acquire the `AppState` Mutex via
  `state.lock().unwrap_or_else(|e| e.into_inner())`. Mutate `CalcState` (insert programs, load
  data card). Release the lock immediately after mutation. The entire Mutex hold time is
  O(microseconds) — no I/O occurs while the lock is held.

For **export commands** (`export_raw_dialog`, `export_data_dialog`): take a brief lock in Phase 1
to snapshot the data (encode program bytes or capture data card bytes) BEFORE opening the save
dialog, then open the dialog and write the file with the lock already released.

For **`import_selected_programs`** (re-decode by index for the multi-program picker): the file path
comes from a prior `import_raw_dialog` call that returned `ImportRawResponse::Multi`. The path
passes through JavaScript before returning to Rust, so T-50-04 path validation is applied:
`is_absolute() + is_file()` must both hold before `std::fs::read` is called.

The **`ImportRawResponse`** serde-tagged enum (`#[serde(tag = "type")]`) provides four structurally
distinct response shapes:
- `Single { view, message }` — one program imported immediately; frontend updates state.
- `Multi { programs: Vec<MultiProgramInfo>, file_path }` — 2+ programs; frontend shows picker.
- `Cancelled { view }` — user dismissed dialog; state unchanged.
- `Empty { view, message }` — file had no programs.

`Multi` includes `file_path: String` so `import_selected_programs` can re-read and re-decode the
archive by index, avoiding any need to cache `Vec<Op>` in `AppState` or IPC.

**CLI** (D-50 / Plan 50-04): `--import-raw`, `--export-raw`, `--import-data`, `--export-data`, and
`--batch` flags in `hp41-cli/src/main.rs`. All import/export flags use `Option<String>` (not
`Option<PathBuf>`) to support `"-"` as the stdin/stdout piping sentinel (RESEARCH Pitfall 7).
Processing runs BEFORE TUI initialization, enabling scripting pipelines such as
`curl https://... | hp41 --import-raw - --batch`. `eprintln!` is used for all status messages to
keep `stdout` clean for `--export-raw -` piping.

## Consequences

### Positive

- **No deadlock on any supported platform.** The three-phase pattern guarantees the AppState Mutex
  is never held across a blocking dialog call. The `setInterval`-driven `tick_time` calls can
  always acquire the lock during dialog interactions; the live clock and stopwatch continue to work
  while the user is browsing the file picker.
- **Single-source-of-truth codec.** `decode_all_programs` delegates to the existing `decode_program`
  for each segment. The per-byte op decoder is not duplicated; any future bug fix or behavioral
  change to `decode_program` automatically applies to multi-program archives.
- **DoS guard is tight.** The 256-program cap fires before any potentially large allocation is
  complete; `programs.len() >= ARCHIVE_CAP` is checked at each push, not after the full scan.
  Crafted inputs with thousands of END markers are rejected after 256 valid segments.
- **`picker_label` degrades gracefully.** Anonymous programs (no `LBL` op) get a deterministic
  "Program N (N bytes)" fallback that is unambiguous in the picker UI and includes the byte count
  for user reference.
- **stdin/stdout piping enables scripting.** `hp41 --import-raw program.raw --batch` imports a
  program and exits without launching the TUI — suitable for CI pipelines, test harnesses, and
  shell scripting. The `"-"` sentinel follows Unix convention for stdin/stdout.

### Negative

- **`import_selected_programs` re-reads and re-decodes the file.** The multi-program picker flow
  re-reads the `.raw` file from disk on `import_selected_programs` rather than caching the decoded
  programs in `AppState` or IPC. This is a second disk read for the same file. The tradeoff is
  explicit: caching `Vec<Op>` in `AppState` would add a field to `CalcState` (or a separate
  managed type), and caching in IPC would require serializing potentially large op arrays across
  the JavaScript boundary. The re-read cost is imperceptible for files up to the 256-program cap.
- **`tauri-plugin-dialog` is a new runtime dependency** in `hp41-gui/src-tauri/Cargo.toml`. The
  zero-new-runtime-deps policy applies to `hp41-core` (which has no dialog dependency); the GUI
  workspace is a separate Cargo workspace and the policy only constrains `hp41-core`. The plugin
  is from the official `@tauri-apps` organization and its npm counterpart (`@tauri-apps/plugin-dialog
  ^2.7`) is a peer package to the existing `@tauri-apps/api`.
- **`Multi` response includes `file_path` as a `String` that passes through JavaScript.** T-50-04
  path traversal risk exists because `file_path` originates from the Tauri OS dialog (trusted),
  but re-enters Rust via the JavaScript boundary in the `import_selected_programs` call. The
  `is_absolute() + is_file()` validation mitigates this, but does not prevent the path from being
  replaced in JavaScript by a malicious extension or XSS payload. The threat is accepted as a
  low-severity risk given that Tauri WebViews do not load untrusted web content by default.

### Neutral

- **Three-phase pattern is non-obvious.** Developers adding new dialog commands in the future must
  follow the three-phase discipline. The pattern is documented in `commands.rs` doc comments
  ("Anti-deadlock pattern (RESEARCH Pitfall 1): dialog and file I/O happen BEFORE any AppState
  lock is acquired.") and in Plan 50-02 key-decisions. A future code review should check that any
  new dialog command follows the same ordering.
- **`ARCHIVE_CAP = 256` is a policy constant, not a format limit.** The `.raw` format has no
  built-in archive size limit. The 256-program cap is an emulator-side DoS guard chosen as a
  practical bound for community archives. Real HP-41 program archives never approach this limit;
  the cap exists to block crafted inputs, not to restrict normal usage.

## Alternatives Considered

### Option B: Acquire AppState Mutex before opening the file dialog (wrong approach)

This alternative would use the conventional "lock once for the entire command" pattern:

```rust
pub fn import_raw_dialog(state: State<'_, AppState>) -> Result<...> {
    let mut calc = state.lock().unwrap_or_else(|e| e.into_inner());
    let path = app.dialog().file().blocking_pick_file(); // Lock held here — deadlock risk
    // ...
}
```

**Why rejected:** Holding the AppState Mutex across the blocking dialog call is the root cause of
the deadlock. The `setInterval` in `App.tsx` fires `tick_time` every 200ms to update the live
clock; `tick_time` also calls `state.lock()`. If `import_raw_dialog` holds the lock while the dialog
is open, `tick_time` blocks. On Tauri's async Tokio runtime, multiple commands can be dispatched
concurrently from different `invoke()` calls; a blocked `tick_time` eventually causes the Tauri
command queue to back up. On macOS, the dialog must be opened on the main thread, which intersects
with the Tauri event loop — the deadlock is platform-specific but reproducible. This is
RESEARCH Pitfall 1 and T-50-05.

### Option C: Cache decoded programs in a separate managed state (avoid re-decoding)

This alternative would add a `PendingImport(Vec<Vec<Op>>)` field to a new managed type
`ImportState: Mutex<Option<PendingImportData>>`, holding the decoded programs between
`import_raw_dialog` (Multi response) and `import_selected_programs` (program selection).

**Why rejected:** This would require registering a new Tauri managed type, adding cleanup logic
(what if the user dismisses the picker without importing?), and ensuring the `PendingImportData`
is cleared on app quit and on the next `import_raw_dialog` call. The re-decode approach has a
simpler state invariant: `import_selected_programs` reads a path and index list and produces a
result; there is no intermediate state to manage. For files up to the 256-program cap, the re-read
is microseconds of I/O, not a user-perceptible latency.

### Option D: Implement `decode_all_programs` as a standalone parser (not delegating to `decode_program`)

This alternative would reimplement the per-byte op decoder inline in `decode_all_programs`,
independently of `decode_program`.

**Why rejected:** Duplication of the per-byte decoder creates two code paths that can diverge.
A future bug fix to how a specific byte value is decoded (e.g., a synthetic byte, an XROM byte,
or an end-of-program marker) would need to be applied in two places. The `windows(3).position()`
split-at-END-marker approach cleanly separates the archive-splitting concern from the per-byte
decoding concern: `decode_all_programs` is responsible for finding segment boundaries; `decode_program`
is responsible for validating and decoding each segment. The composition is correct and complete —
`decode_program` already handles the END marker as the last op, so passing
`segment[..end_offset + 3]` (END-marker-inclusive) to `decode_program` is the natural API call.

### Option E: Use a synchronous file picker helper that does not require an AppHandle (avoids the Tauri plugin)

This alternative would use a third-party file dialog crate (e.g., `rfd`, `native-dialog`) that
presents a synchronous file picker without requiring Tauri plugin infrastructure.

**Why rejected:** `tauri-plugin-dialog` is the official Tauri-maintained dialog plugin for Tauri v2.
Using a third-party crate would introduce a dependency that is not maintained by the Tauri team and
may not be tested against the Tauri WebView lifecycle on all three target platforms (macOS, Windows,
Ubuntu). The `rfd` crate in particular has known issues with Tauri's main-thread requirements on
macOS. Using the official plugin avoids these risks. The npm counterpart
(`@tauri-apps/plugin-dialog`) is already in the official `@tauri-apps` organization namespace.
