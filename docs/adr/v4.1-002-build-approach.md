# ADR v4.1-002 — iOS Build Approach (Tauri v2 Mobile vs SwiftUI + UniFFI)

**Status:** Accepted
**Date:** 2026-05-31
**Context:** v4.1 iOS Foundation milestone — Phase 53 scaffold spike

## Context

v4.1 brings the HP-41 emulator to iPhone (TestFlight target; App Store deferred).
Two build approaches were researched (see References):

- **Approach A — Tauri v2 Mobile:** extend the existing `hp41-gui` Tauri project to
  target iOS, reusing the React frontend and all ten Tauri commands verbatim
  (~500–800 LOC of touch CSS + lifecycle + persistence).
- **Approach B — Native SwiftUI + Rust FFI:** a new SwiftUI UI binding `hp41-core`
  through a UniFFI 0.31.1 adapter crate (~2,500–3,500 LOC).

Research recommended Approach A **contingent on one spike**: `hp41-gui` is a nested
standalone workspace (its `src-tauri/Cargo.toml` carries its own `[workspace]` header
and is **not** a member of the root workspace — a Frozen Invariant). Tauri's iOS
bundler has an open bug (tauri-apps/tauri **#5865**) where the bundler hardcodes the
compiled-library path instead of reading `cargo metadata`, which can break the Xcode
**assembly** step for nested workspaces. The decision was therefore keyed strictly on
the spike's **failure stage** (D-53.4 / D-53.5):

- **Clean build** → Approach A confirmed.
- **Rust compiles, then the Xcode assembly fails on the nested-workspace path (#5865)**,
  and still fails after a ~½-day time-box of bounded workarounds → fall back to Approach B.

## Decision

**Approach A — Tauri v2 Mobile.** The Phase 53 spike confirmed it.

**Observed spike outcome** (`just ios-build` → `cargo tauri ios build`, device triple
`aarch64-apple-ios`, inside `hp41-gui/`, Tauri CLI 2.11.1, Xcode 26.5):

| Stage | Result |
|-------|--------|
| Frontend build (`npm run build`) | passed |
| Rust compile → `aarch64-apple-ios` | passed (`hp41-core` + `rust_decimal` + GUI lib) |
| **Xcode project assembly** (the #5865 risk) | **passed** — target dependency graph resolved (`hp41-gui_iOS`), `GatherProvisioningInputs` → `CreateBuildDescription` completed |
| Code signing | stopped: *"Signing for 'hp41-gui_iOS' requires a development team"* |

The build reached the **signing** stage with **no `#5865` nested-workspace path error**.
The bundler located the compiled static library, assembled the Xcode project, and
produced a valid build description; the only stop was the *expected* missing development
team — a signing/provisioning gate handled by Plan 53-02 (register the App ID) and
Plan 53-04 (select the team in Xcode). **No time-boxed workarounds were needed and no
workspace-flattening was attempted** (D-53.6).

A second build for the simulator triple `aarch64-apple-ios-sim` (no signing required)
completed cleanly to a bundled `HP-41 Calculator.app`. Installed and launched on the
iPhone 17 Pro Simulator (iOS 26.5), the app rendered the React HP-41 UI in WKWebView and
the RPN smoke sequence **`2 ENTER 3 +` → `5`, then `SIN`** updated the X register and
dropped the stack (D-53.8 / SC-2) — proving the full loop
touch → `key_map.resolve()` → `invoke("dispatch_op")` → WKWebView bridge → Rust
`hp41-core` → `CalcStateView` → React re-render works unchanged on iOS.

**Conclusion:** the nested-standalone-workspace bundler bug (#5865) does **not** manifest
in Tauri 2.11; Approach A is viable at ~3–5× lower cost than Approach B, with zero
`hp41-core` changes. Approach B is not pursued for v4.1.

## Consequences

### Positive
- The entire React UI, all ten Tauri commands, and the IPC contract carry over to iOS
  unchanged. iOS becomes "just another Tauri target" of `hp41-gui`.
- Single Rust structural change: `crate-type = ["staticlib", "cdylib", "rlib"]` on the
  GUI `[lib]` (Plan 53-01); `rlib` retained so the desktop `[[bin]]` and tests still link.
- The `gen/apple/` scaffold is generated and committed (see gitignore policy below),
  so Phases 54–57 and CI build from a reproducible scaffold.

### Negative / accepted
- Tauri iOS DX has known rough edges (opaque Xcode integration, plugin gaps); accepted
  for a TestFlight-foundation milestone.
- `tauri ios dev` (used by `just ios-sim`) presents an interactive device picker and is
  not usable headless without an explicit device argument; the simulator smoke was run
  instead via `tauri ios build --target aarch64-sim` + `xcrun simctl install/launch`,
  which is fully scriptable. The `ios-sim` recipe accepts a `device=` argument for the
  manual hot-reload loop.
- `tauri-plugin-autostart` is desktop-only; it had to be gated `#[cfg(desktop)]` in
  `lib.rs` so the iOS target compiles (Plan 53-01). Desktop behavior is unchanged.

### Neutral
- Signing (development team, App ID, provisioning) is deliberately out of scope for the
  build decision and is owned by Plans 53-02 / 53-04 and Phase 57 (distribution).

## Frozen Invariant accounting

**Both** approaches preserve the Frozen Invariant, and the chosen Approach A was verified
to do so after the spike:

- Root `Cargo.toml` `members` remains exactly `["hp41-core", "hp41-cli"]` (unchanged by
  `tauri ios init` and by the spike build).
- `tauri` / `tauri-build` remain confined to `hp41-gui/src-tauri/Cargo.toml`; `hp41-core`
  has no iOS or Tauri dependencies (zero-new-deps-in-core invariant intact).
- `hp41-core` is unchanged — no new `Op`, no logic change; the 4-way exhaustive-match and
  serde-default invariants are trivially preserved.
- D-53.6 workspace-flattening was **not** required and was never committed.

## `gen/apple/` gitignore policy (decided in Plan 53-01)

**Option (a) — track the scaffold.** `hp41-gui/src-tauri/gen/apple/` is committed
(`project.yml` is the XcodeGen source of truth; the generated Xcode project, Sources,
`Info.plist`, entitlements, and assets are committed per Tauri maintainer guidance), while
`gen/schemas/` and `gen/apple/Pods/` stay ignored and the Tauri-written nested
`gen/apple/.gitignore` handles the transient `xcuserdata/`, `build/`, and `Externals/`.
Rationale: Phases 54–57 will edit this scaffold (`tauri.ios.conf.json`,
`capabilities/ios.json`, `PrivacyInfo.xcprivacy`), and CI (Phase 57) builds from a
reproducible committed scaffold with no `tauri ios init` step required first. A `just
ios-build` re-emits trivial cosmetic churn (bundle-id quote style in `project.pbxproj`, a
trailing newline in `Info.plist`); this is reverted/ignored, not committed.

## Alternatives considered

- **Approach B — SwiftUI + UniFFI 0.31.1** — rejected for v4.1: ~3–5× the LOC (a new
  `hp41-ios-bridge` nested workspace + a full SwiftUI keyboard) for no additional v4.1
  functionality. It remains the correct escalation *had* the spike failed at the #5865
  Xcode-assembly stage, and stays feasible later (e.g. for native iOS features) because
  `hp41-core` is UI-agnostic. The spike removed the trigger for it.
- **swift-bridge** (for Approach B's FFI) — rejected upstream of this ADR: requires
  annotating `hp41-core` source, violating the Frozen Invariant (see STACK.md §3).

## Downstream

This ADR unblocks detailed planning of Phases 54–57. Because Approach A was confirmed,
Phase 55 stays the **CSS/React touch-adaptation** path (not a SwiftUI keyboard rewrite,
which would have been required under Approach B).
