# ADR-v4.0-001: X-MEM as HP-41CX OS Built-ins — No XROM Bit

**Status:** Locked 2026-05-28
**Owner:** Plan 52-04
**Requirement refs:** XMEM-10
**Downstream consumer:** `hp41-core/src/ops/program.rs` (`builtin_card_op` — name→Op
resolver; 8 X-MEM arms added in Phase 52 Plan 52-01);
`hp41-cli/src/help_data.rs` (`XMEM_HELP_ENTRIES` OnceLock, sixth pool);
`hp41-gui/src/help_data.ts` (Vite JSON import, sixth pool);
`docs/hp41-xmem-functions.json` (canonical JSON source, no `xrom` field per D-52.4)

---

## Context

The HP-41CX Extended Functions (commonly called "X-MEM" or "X-Functions") are
shipped as part of the HP-41CX operating system — they are built into the CX ROM,
not distributed on a separate plug-in ROM module. On real HP-41CX hardware, `XEQ "EMDIR"`,
`XEQ "SAVEP"`, etc. are invoked by name and resolve through the OS; no XROM catalog
entry exists for them, and they carry no XROM module number in CATALOG 2.

The emulator's X-MEM operations (`EmDir`, `EmRoom`, `SaveP`, `GetP`, `SaveD`, `GetD`,
`EmReg`, `SaveRx`) were implemented in Phase 51 (`hp41-core/src/ops/xmem/`). When Phase 52
wired them for CLI/GUI access, a routing decision was required: should the 8 new ops
resolve via `xrom_resolve` (with a new XROM bit) or via `builtin_card_op` (the existing
built-in name→Op resolver)?

The resolver chain in `hp41-core/src/ops/program.rs` already handles two categories:

1. **`builtin_card_op`** — OS built-in XEQ names: `"PI"`, `"PRSTK"`, `"X<>Y?"`,
   all card-reader mnemonic names, and the 8 conditional-test mnemonics added in Phase 25.
   These are HP-41CX built-in functions that are always available and carry no XROM affiliation.

2. **`xrom_resolve`** — XROM plug-in module functions (Math Pac I XROM 7, Stat 1 Pac XROM 2,
   Time Module XROM 26, Advantage Pac XROM 22 + 24). These are separately loadable ROM modules
   tracked by the `xrom_modules: u32` bitmask on `CalcState`; each module occupies one bit in
   the bitmask (bits 0–4 are taken).

The X-MEM functions are HP-41CX OS built-ins, not ROM module functions. They are always
available on any HP-41CX regardless of which ROM cards are inserted.

---

## Decision

**X-MEM operations resolve via `builtin_card_op`, not `xrom_resolve`. No XROM bit is
allocated for X-MEM.**

The complete implementation:

1. `builtin_card_op()` in `hp41-core/src/ops/program.rs` gains 8 new match arms (Phase 52
   Plan 52-01): `"EMDIR"`, `"EMROOM"`, `"SAVEP"`, `"GETP"`, `"SAVED"`, `"GETD"`,
   `"EMREG"`, `"SAVERX"` — each mapping to the corresponding `Op` variant. This is the
   same pattern used for `"PRSTK"`, `"PI"`, and the 8 conditional-test mnemonics.

2. **No new XROM bit** is allocated. The `xrom_modules: u32` bitmask stays at 5 bits
   (`0b0001_1111`); `default_xrom_modules()` returns `0b0001_1111` unchanged. X-MEM ops
   are unconditionally available — they do not participate in module-load/unload logic.

3. **No `xrom` field in `docs/hp41-xmem-functions.json`**. Each of the 8 JSON entries
   has `xrom` absent (deserializes as `None` via `#[serde(default)]` on `HelpEntry.xrom`).
   This is critical: the pool-partition test in `function_matrix_parity.rs` counts entries
   with `xrom: None` as `builtin_count` — adding an `xrom` key would break
   `test_pool_partition_is_exhaustive`.

4. **XEQ-by-name access only** (D-52.4). No comfort keys are wired for X-MEM ops —
   faithful to the real HP-41CX where Extended Functions are invoked by name or assigned
   to user-defined keys via `ASN`. Users can use the existing USER-mode `ASN` mechanism
   to assign X-MEM functions to physical keys.

5. The `key_ref_entries()` right-panel filter in `hp41-cli/src/keys.rs` (`entry.xrom.is_none()`)
   passes X-MEM entries through — they appear in the CLI right panel and the `?` overlay's
   "Extended Memory" section. This is the correct behavior: X-MEM functions are
   keyboard-accessible built-ins (via `XEQ`), not module functions hidden behind a module toggle.

---

## Consequences

### Positive

- **Hardware-accurate resolution path.** On real HP-41CX hardware, Extended Functions are
  OS built-ins — they do not appear in CATALOG 2 (which lists plug-in XROM modules), and
  they have no XROM module number. The `builtin_card_op` path faithfully reflects this.
- **No XROM bit consumption.** The `xrom_modules` bitmask is a `u32` field, but allocating
  a bit for X-MEM would imply the functions can be "unloaded" — which contradicts the
  HP-41CX hardware design (X-MEM is always built-in). Keeping X-MEM out of the bitmask
  prevents confusion and keeps the bitmask semantically accurate.
- **Backward compat unaffected.** `default_xrom_modules()` stays at `0b0001_1111`;
  `migrate_after_load()` needs no new migration arm for v3.3→v4.0 save files. X-MEM fields
  (`xmem_files`, `xmem_active_file`) default cleanly via `#[serde(default)]` from Phase 51.
- **Clean right-panel and `?` overlay behavior.** The `xrom.is_none()` filter in
  `key_ref_entries()` was designed for a world where built-in ops have no XROM affiliation.
  X-MEM ops fit this model naturally — they appear in the discovery surfaces without any
  filter exemption.

### Negative

- **CATALOG 2 does not list X-MEM.** Real HP-41CX CATALOG 2 does not include X-MEM as a
  module entry (because it is an OS built-in), and this emulator's CATALOG 2 follows suit.
  Users who expect to see "X-MEM" in CATALOG 2 may be surprised. This is hardware-faithful
  behavior; it is documented in `docs/hp41-xmem-divergences.md`.

### Neutral

- **8 ops in `builtin_card_op` vs. a module resolver function.** Unlike XROM modules
  (which have a dedicated `xrom_resolve` arm and a per-module resolver function), X-MEM ops
  are spread across 8 individual arms in `builtin_card_op`. The function remains readable
  and the pattern is consistent with the existing card-reader and conditional-test arms.
- **`test_pool_partition_is_exhaustive` requires `xrom: None` discipline.** The parity
  test counts entries by module ID, with `xrom: None` implying "builtin". X-MEM entries
  must not carry an `xrom` field; this is guarded by the Phase 52 reverse parity test
  (`test_every_xmem_json_entry_has_builtin_resolver_match` in `function_matrix_parity.rs`).

## Alternatives Considered

### Option B: Allocate a new XROM bit for X-MEM (XROM bit-5)

This alternative would add an XROM bit (bit-5, `0b0010_0000`) for X-MEM, following the same
pattern as Math Pac I (bit-0), Stat 1 Pac (bit-1), Time Module (bit-2), ADV_MATH_A (bit-3),
and ADV_MATH_B (bit-4).

**Why rejected:** X-MEM is not a plug-in ROM. Allocating an XROM bit would imply X-MEM can
be "unloaded" by clearing the bit — which is not hardware-faithful. On a real HP-41CX, the
Extended Functions are always present; there is no ROM card to remove. Additionally, bits 0–4
correspond to plug-in ROM hardware IDs (7, 2, 26, 22, 24) that HP assigned to physical ROM
cards. There is no HP-assigned XROM ID for the X-MEM built-ins — assigning an arbitrary
bit-5 would have no hardware basis. The `xrom_modules` bitmask semantics would become
confusing if it were to include both "plug-in ROM modules" and "OS built-ins".

### Option C: Extend `xeq_by_name_local_resolve` to handle X-MEM independently

This alternative would handle X-MEM name resolution in a separate fast-path function in
`hp41-cli/src/keys.rs` — a sibling to `xeq_by_name_local_resolve` — rather than routing
through `builtin_card_op`.

**Why rejected:** `builtin_card_op` is already the canonical home for HP-41CX OS built-in
names. It is called by `xeq_by_name_local_resolve` (CLI), `key_map::resolve` (GUI), and
`Op::Xeq` program execution. Adding a parallel fast-path would require updating all three
call sites independently and would fragment the name→Op mapping logic. The single-source-of-
truth invariant (`builtin_card_op` as the canonical built-in name resolver) is stronger
than any performance argument for a parallel path.

### Option D: Add X-MEM ops to `hp41cv-functions.json` (no dedicated pool)

This alternative would add the 8 X-MEM entries to the existing `docs/hp41cv-functions.json`
file (which covers the ~130 HP-41CV ROM built-in functions), treating X-MEM as an extension
of the HP-41CV base pool.

**Why rejected:** X-MEM is specific to the HP-41CX — it is not part of the HP-41CV ROM.
Folding X-MEM into `hp41cv-functions.json` would conflate HP-41CV built-ins with HP-41CX
extended functions. The dedicated pool (`docs/hp41-xmem-functions.json`) provides a clean
`?` overlay section label ("Extended Memory"), a standalone function matrix doc, and an
independent parity test — matching the per-module pattern established for all five XROM
modules. The pool-partition parity test would require changes to accommodate a mixed-category
pool if X-MEM were folded in.
