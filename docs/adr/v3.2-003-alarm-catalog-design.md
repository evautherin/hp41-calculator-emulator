## Context

HP-41CX Time Module (HP 82182A, 1982) includes a hardware alarm system with up to 253
simultaneous alarms. Alarms fire at a user-specified date and time, optionally repeat at a
fixed interval, and can carry either a message (displayed on the LCD) or a control program
label (executed automatically when the alarm fires). The emulator must implement this system
in a way that:

1. Serializes and deserializes correctly with the rest of `CalcState` (save-file invariant).
2. Integrates with the existing drain pattern (print_buffer, event_buffer) used throughout
   `hp41-core`.
3. Handles the distinction between message alarms and control alarms, including the
   HP-41CX's `>>label` interrupting vs. `>label` non-interrupting convention.
4. Fires alarms at the correct time even when the user is not actively pressing keys
   (TIME-ALM-08: "check on each keypress/dispatch").
5. Remains thread-free, async-free, and zero new runtime dependencies.

### The HP-41CX alarm system

The HP-41CX hardware maintains a catalog of up to 253 alarms indexed 1–253. Each alarm
stores:
- A trigger time (date + time of day)
- A repeat interval (0 = one-shot; positive = repeat period in hours/minutes/seconds)
- An alarm type: message alarm (displays text) or control alarm (executes a program label)
- For control alarms: interrupting (`>>label`) or non-interrupting (`>label`)

Alarms are checked by the hardware RTC interrupt. When an alarm fires:
- Message alarms: display the stored text on the LCD with an audible beep.
- Non-interrupting control alarms: XEQ the label when the user presses a key (deferred).
- Interrupting control alarms: interrupt the current program and immediately XEQ the label.

On real hardware, alarms can fire while the calculator is "off" (clock-only mode), waking
it up. The emulator has no "off" state; the emulator is always logically "on", so this
distinction does not apply.

### The design problem

The alarm catalog must be part of `CalcState` to benefit from the existing save/load
infrastructure. The two questions are: **what data structure** should represent the catalog,
and **how** should alarm notifications reach the frontend without requiring push callbacks
or threads?

#### Catalog data structure

The primary candidates are:
- A flat `Vec<AlarmEntry>` on `CalcState`, with free functions operating on it.
- A dedicated `AlarmState` struct nested in `CalcState`.
- An external alarm store with a reference or channel in `CalcState`.

The HP-41CX hardware limit of 253 alarms makes the catalog small by any modern standard.
Even a fully populated catalog with 253 entries containing 64-byte entries would occupy
~16 KB — well within the budget for a `CalcState` field. Linear scans for `check_alarms`
are O(n) but n ≤ 253, making the worst-case cost negligible.

#### Notification mechanism

The core cannot call `println!` or send network packets (zero-I/O principle). The frontend
needs to know when alarms fire. Existing precedent:
- `print_buffer: Vec<String>` — `#[serde(skip)]`, drained by CLI after each dispatch.
- `event_buffer: Vec<String>` — `#[serde(skip)]`, introduced for general in-band notifications.

Both buffers are drained by the frontend after calling `dispatch()`. The same cadence can
serve alarm notifications: `check_alarms()` detects past-due alarms and pushes notification
strings into `event_buffer` and/or `print_buffer`.

#### Interrupting control alarm deferral

The HP-41CX interrupting control alarm (`>>label`) fires while a program is executing and
re-enters the call stack. The emulator's `run_program()` is not re-entrant: it holds a
mutable reference to `CalcState` for the duration of execution. Injecting an alarm-triggered
XEQ inside `run_program()` would require either re-entrant program execution or a
continuation/coroutine model, neither of which is in scope for v3.2.

Decision D-38.4 defers interrupting control alarm execution. The data model stores
interrupting alarms (the `AlarmType::Control { interrupting: true }` variant exists and
is serialized), so the forward-compatible shape is preserved for a future implementation.
Execution is deferred and documented as a divergence in `docs/hp41-time-divergences.md`.

## Decision

**`alarms: Vec<AlarmEntry>` on `CalcState` with `#[serde(default)]`, and alarm
notifications via `event_buffer` drain** (Decisions D-38.8 / D-38.9 / D-38.10 / D-38.11).

The implementation:

### Data model

```rust
// hp41-core/src/ops/time/alarm.rs

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct AlarmEntry {
    pub trigger_unix: i64,    // Unix epoch seconds when alarm fires
    pub repeat_secs: i64,     // 0 = one-shot; >0 = repeat period
    pub alarm_type: AlarmType,
    pub past_due: bool,       // true if fired but not yet acknowledged
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum AlarmType {
    Message(String),
    Control { label: String, interrupting: bool },
}
```

The `past_due` flag enables frontends to re-display unacknowledged alarms on reconnect
(e.g., an alarm that fired while the app was closed).

### CalcState field

```rust
// hp41-core/src/state.rs
#[serde(default)]
pub alarms: Vec<AlarmEntry>,
```

`#[serde(default)]` means pre-v3.2 save files load with an empty alarm catalog — correct
behavior (no alarms were set in sessions before the Time Pac was implemented).

### Alarm operations

Free functions in `alarm.rs` operate on `&mut Vec<AlarmEntry>` through `CalcState`:

- `op_xyzalm` — set alarm from stack X (time) + Y (date) + Z (repeat) + ALPHA (type/label).
  Keeps `alarms` sorted chronologically by `trigger_unix`. Enforces 253-alarm cap.
- `op_rclalm` — recall alarm N from catalog to stack and ALPHA register.
- `op_almcat` — open alarm catalog display modal (ALMCAT step enum).
- `op_clalma`, `op_clalmx` — clear alarm by catalog index or by exact X/Y match.
- `op_clralms` — clear all alarms.
- `op_almnow` — set alarm for the current date/time + interval (ALMNOW shorthand).

### Notification drain

`check_alarms(state: &mut CalcState)` is a free function called by the frontend after
every dispatch and on each 16ms poll-loop iteration (D-39.7):

1. Scan `state.alarms` for entries where `trigger_unix <= current_unix_secs(state.time_offset_secs)`.
2. For each past-due alarm:
   - `Message(text)`: push `format!("alarm:message:{}", text)` into `state.event_buffer`
     and `text` into `state.print_buffer` (mirroring the HP-41CX LCD display behavior).
   - `Control { label, interrupting: false }`: push `format!("alarm:xeq:{}", label)` into
     `state.event_buffer` for the frontend to dispatch on acknowledgment.
   - `Control { interrupting: true }`: push `format!("alarm:interrupting:{}", label)` into
     `state.event_buffer`; documented as deferred — frontend logs but does not execute.
3. If `repeat_secs > 0`: advance `trigger_unix` by `repeat_secs` (reschedule).
4. If `repeat_secs == 0`: mark `past_due = true` (or remove from catalog — per OM, one-shot
   alarms remain in catalog as past-due until explicitly cleared by `CLALMA`/`CLALMX`).

### Repeat interval storage

Repeat intervals are stored as `i64` seconds (Decision D-38.11). `XYZALM` converts the
stack-Z HpNum (in HHHH.MMSScc format) to seconds once at alarm creation. This avoids
accumulating rounding error over repeated reschedule operations — each reschedule adds a
fixed integer, never a floating-point approximation.

## Consequences

### Positive

- **Simple serialization.** `Vec<AlarmEntry>` with `#[serde(default)]` serializes exactly
  like the existing `regs: Vec<HpNum>` and `programs: Vec<Program>` fields. Serde's
  `derive` handles the enum and nested structs automatically. No custom serializer needed.
- **Matches existing patterns.** The `Vec<T>` field on `CalcState` + free functions in a
  module is the established pattern for all mutable HP-41 state: registers, programs,
  flags. The alarm catalog fits cleanly without inventing new idioms.
- **Forward-compatible data model.** `AlarmType::Control { interrupting: true }` exists as
  a named variant; it is stored and serialized even though execution is deferred. When
  interrupting alarm execution is eventually implemented (v3.3+), the data model requires
  no migration — only the execution branch in `check_alarms` needs to be filled in.
- **event_buffer drain pattern is already established.** Frontends already drain
  `print_buffer` after every dispatch (Phase 10 / v1.1). Extending the drain cadence to
  `event_buffer` for alarms requires no new protocol — it is a mechanical extension of
  an existing idiom.
- **Backward compatibility preserved.** `#[serde(default)]` on `alarms` means v3.0 and
  v3.1 save files load with an empty alarm catalog. No migration step in `migrate_after_load`.
  The Time Pac save-file invariant is the same as every prior milestone.

### Negative

- **Vec linear scan for `check_alarms`.** Checking all alarms for past-due status is O(n)
  where n ≤ 253. This is negligible in practice (253 comparisons of i64 values), but it
  is not the O(1) priority-queue approach a production alarm system might use. For the
  HP-41CX emulator's scope, this is an acceptable trade-off.
- **Alarm catalog is O(n) for index operations.** `RCLALM N` and `CLALMX N` iterate the
  sorted vector to find position N. Again, n ≤ 253 makes this acceptable.

### Neutral

- **253-alarm practical limit matches OM.** The HP 82182A hardware indexed alarms 1–253
  (8-bit catalog index with 0 reserved). The emulator enforces the same limit via the
  T-38-13 guard in `op_xyzalm`. Users who attempt to add a 254th alarm receive
  `HpError::InvalidInput`.
- **Interrupting control alarm deferral.** Stored in the data model but not executed.
  Documented as a known divergence in `docs/hp41-time-divergences.md`. The `interrupting`
  field in `AlarmType::Control` is load-bearing for future implementation — it must not
  be removed or flattened during any refactor without first implementing the execution path.

## Alternatives Considered

### Option B: Separate alarm state struct (not on CalcState)

This alternative would define an `AlarmState` struct and nest it in `CalcState`:

```rust
pub struct AlarmState {
    pub entries: Vec<AlarmEntry>,
    pub pending_notification: Option<String>,
}

pub struct CalcState {
    // ...
    pub alarm_state: AlarmState,
}
```

The relevant context decision (38-CONTEXT.md D-38.10) states verbatim:

> **D-38.10:** Direct `alarms: Vec<AlarmEntry>` on CalcState with `#[serde(default)]`.
> Free functions in `alarm.rs` operate on `&mut Vec<AlarmEntry>`. Matches existing
> patterns: `regs` is `Vec<HpNum>`, `programs` is `Vec<Program>`.

**Why rejected:** Nesting adds a layer of indirection (`state.alarm_state.entries` vs.
`state.alarms`) without adding any conceptual clarity. The `regs` and `programs` precedents
are direct `Vec<T>` fields on `CalcState`; inventing an `AlarmState` wrapper only for
alarms creates an inconsistency. A nested struct also complicates the serde path:
`alarm_state: AlarmState` would need `#[serde(default)]` on both the struct and its
inner fields, or a `Default` impl for `AlarmState`. The flat `Vec<AlarmEntry>` approach
achieves the same result with less code.

### Option C: Channel-based notification (mpsc channel)

This alternative would add an `std::sync::mpsc::Sender<AlarmEvent>` to `CalcState`,
injected by the frontend during initialization. When `check_alarms` detects a past-due
alarm, it sends an `AlarmEvent` to the channel instead of pushing to `event_buffer`.

The relevant context decision (38-CONTEXT.md D-38.9) states verbatim:

> **D-38.9:** `check_alarms()` called by frontend after every dispatch via the drain
> pattern (same as `print_buffer` and `event_buffer`). Alarm notifications pushed into
> `event_buffer` for frontend rendering. Matches TIME-ALM-08 requirement: "on each
> keypress/dispatch".

**Why rejected:** Channels require injection (a `Sender` must be passed to `CalcState`
at construction time), which breaks the zero-argument `CalcState::new()` API and
complicates every test that constructs a `CalcState`. `Sender<T>` is not `Serialize` or
`Deserialize`, so the field must carry `#[serde(skip)]`, and the frontend must re-inject
the sender after every `load_state()` call. This introduces a subtle correctness hazard:
a `CalcState` loaded from disk starts with `sender = None` until the frontend re-injects
it; any alarm that fires during this window would be silently dropped. The `event_buffer`
drain pattern avoids this entirely — the buffer is a plain `Vec<String>` that survives
deserialize with `#[serde(skip)]`'s default (empty vec), and the frontend drains it
synchronously after each dispatch, so there is no injection window.

### Option D: Trait-based alarm handler (AlarmObserver trait)

This alternative would define an `AlarmObserver` trait:

```rust
pub trait AlarmObserver: Send + Sync {
    fn on_alarm_message(&self, text: &str);
    fn on_alarm_control(&self, label: &str, interrupting: bool);
}
```

`CalcState` would hold an `Arc<dyn AlarmObserver>`. The frontend would implement the trait
and inject an instance at startup.

The relevant context decisions (38-CONTEXT.md D-38.8 and D-38.10) together provide the
rationale for the chosen shape:

> **D-38.8:** Typed `AlarmType` enum: `Message(String)` carries the ALPHA message,
> `Control { label: String, interrupting: bool }` carries the program label.
> Forward-compatible for when interrupting alarms get implemented — the data model
> supports storing them even though execution is deferred.

> **D-38.10:** Direct `alarms: Vec<AlarmEntry>` on CalcState with `#[serde(default)]`.
> Free functions in `alarm.rs` operate on `&mut Vec<AlarmEntry>`. Matches existing
> patterns: `regs` is `Vec<HpNum>`, `programs` is `Vec<Program>`.

**Why rejected:** Trait-based observer injection has the same fundamental problem as
channel injection (Option C): `Arc<dyn AlarmObserver>` is not `Serialize`/`Deserialize`,
requires re-injection after `load_state()`, and breaks the zero-argument constructor
invariant. Additionally, a trait object in `CalcState` would propagate `Send + Sync`
requirements to `CalcState` itself, which is currently free of such bounds — the GUI
uses `Mutex<CalcState>` for thread safety, but `CalcState` itself is `!Send` by
convention (no interior mutability). Introducing `Arc<dyn AlarmObserver + Send + Sync>`
would change this property globally. The `event_buffer` drain is simpler, more consistent,
and does not impose new trait bounds on `CalcState`.
