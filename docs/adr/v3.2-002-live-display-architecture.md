# ADR-v3.2-002: Live Display Architecture -- Pull-on-Redraw Pattern for Clock/Stopwatch

**Status:** Locked 2026-05-24
**Owner:** Plan 38-03 + Plan 39-02
**Requirement refs:** TIME-DSP-01, TIME-DSP-05, TIME-SW-08, Pitfall 32 (live display)
**Downstream consumer:** `hp41-cli/src/app.rs` (16ms poll loop); `hp41-cli/src/ui.rs`
(`get_display_string()` priority chain); future `hp41-gui/src/App.tsx` (conditional setInterval)
**ADR write-up prose:** Phase 40 / TIME-DOC-03

---

## Context

From v1.0 through v3.1, the HP-41 emulator has operated on a purely event-driven model:
the display updates only when a key is pressed or a program step executes. Every `Op`
dispatches synchronously; `handle_key()` in `hp41-cli/src/app.rs` blocks waiting for user
input; `hp41-core` is single-threaded with no background tasks. This model is correct,
simple, and efficient for RPN calculator semantics where nothing changes between keystrokes.

The HP-41CX Time Module (HP 82182A) breaks this assumption. Two Time Pac functions require
**continuous display updates independent of user input**:

1. **`CLKT` / `CLKTD` / `CLOCK`** — clock display mode (`TIME-DSP-01`): the LCD shows the
   current time (or alternating time/date) until the user presses any key. The displayed
   value must refresh at ≥ 1 Hz so seconds tick visibly. On real HP-41CX hardware, the
   clock is driven by the RTC interrupt (1-second period).

2. **`SW` (interactive stopwatch)** — stopwatch keyboard mode (`TIME-SW-08`): elapsed time
   in `HH:MM:SS.hh` format updates at ≥ 10 Hz so centiseconds are legible. On real
   HP-41CX hardware, the stopwatch is driven by the RTC interrupt (1/100-second period).

The emulator must satisfy these update-rate requirements without introducing threads,
async/await, or new timer infrastructure into `hp41-core` or `hp41-cli`.

### The existing poll loop

`hp41-cli/src/app.rs::run()` already contains a 16ms poll loop:

```rust
loop {
    terminal.draw(|f| ui(f, &self))?;
    if event::poll(Duration::from_millis(16))? {
        if let Event::Key(key) = event::read()? {
            self.handle_key(key);
        }
    }
}
```

This loop redraws the TUI at approximately 62 frames per second regardless of keyboard
input. The `terminal.draw()` call happens **before** `event::poll`, so the display
refreshes on every iteration, not just on keypress. This was introduced in Phase 10
(ratatui smooth rendering) for animation purposes and has been present since v1.1.

The poll loop already satisfies both the 1 Hz clock requirement and the 10 Hz stopwatch
requirement with large margin: 62 fps >> 10 Hz >> 1 Hz.

### The display priority chain

`hp41-cli/src/ui.rs::get_display_string()` computes the string shown in the LCD area.
In v3.1, the priority chain is:

1. Entry buffer (digits being typed) — highest priority
2. ALPHA mode display
3. PRGM mode (program listing)
4. Stack X value — lowest priority

The clock and stopwatch modes must interrupt ALL of these. On real HP-41CX hardware,
activating `CLKT` immediately replaces the normal display with a running clock — even if
the user was mid-keystroke. Similarly, the interactive stopwatch (`SW`) takes over the
display from the moment it starts until the user exits.

### Requirements

- `TIME-DSP-05`: Clock display updates at ≥ 1 Hz.
- `TIME-SW-08`: Stopwatch display updates at ≥ 10 Hz.
- `TIME-DSP-01`: Clock display exits on ANY keypress (key is not consumed — it is still
  processed normally after clock mode exits).
- No new threads, no `async`/`await`, no new timer infrastructure (D-carried.1: zero new
  runtime deps; D-38 carried.7: hp41-core remains thread-free and async-free).

---

## Decision

**Pull-on-redraw pattern** (Decisions D-38 carried.7 + D-39.1 + D-39.2).

The frontend redraw cycle computes time-dependent display state on-demand, every 16ms
(~62 Hz), without any background thread or push notification from hp41-core.

### Implementation

**In `hp41-core`** (Plan 38-03):
- `clock.rs::get_clock_display_str(state: &CalcState) -> Option<String>` — pure compute
  function. Reads `state.clock_active`, calls `adjusted_epoch_secs(state.time_offset_secs)`,
  formats the result. Returns `None` if clock display is inactive.
- `stopwatch.rs::get_stopwatch_display_str(state: &CalcState) -> Option<String>` — pure
  compute function. Reads `state.stopwatch_keyboard_mode`, computes elapsed time from
  `state.stopwatch_start` + `state.stopwatch_accumulated`, formats as `HH:MM:SS.hh`.
  Returns `None` if stopwatch keyboard mode is inactive.
- Both functions are called by the frontend on every redraw. They carry no state and
  perform no I/O beyond the `SystemTime::now()` already sanctioned by ADR-v3.2-001.

**In `hp41-cli`** (Plan 39-02, D-39.1 / D-39.2):
- `ui.rs::get_display_string()` — insert two checks at the TOP of the priority chain,
  above the entry buffer:
  1. If `get_clock_display_str(state).is_some()` → return the clock string (highest priority).
  2. Else if `get_stopwatch_display_str(state).is_some()` → return the stopwatch string.
  3. Fall through to existing entry_buf / ALPHA / PRGM / X chain.
- `app.rs::handle_key()` — insert a clock-exit check at entry: if `state.clock_active`
  is true, set `state.clock_active = false` before processing the key (D-39.3). The key
  is still processed normally.
- The existing 16ms poll loop requires no modification. `terminal.draw()` already fires
  62 times per second, pulling fresh display strings via `get_display_string()`.

**In `hp41-gui`** (Phase 41, D-11 exception):
- The GUI frontend does not poll `get_state()` (D-11 no-polling discipline). For clock and
  stopwatch, a conditional `setInterval` fires during active clock/stopwatch modes only.
  When `state.clock_active` or `state.stopwatch_keyboard_mode` transitions to true (detected
  via the `CalcStateView` response from the activating dispatch), the frontend starts a
  16ms interval and stops it when the mode deactivates. This is the documented D-11 exception.

---

## Consequences

### Positive

- **Zero architectural debt.** The CLI implementation requires no new infrastructure — only
  two new functions in `hp41-core` (pure compute, no side effects) and two new checks at
  the top of `get_display_string()`. The existing 16ms poll loop already provides the
  required update rate.
- **Core remains thread-free.** `hp41-core` has no background threads, no channels, no
  async runtime. The `get_clock_display_str` and `get_stopwatch_display_str` functions are
  pure reads of `CalcState` plus a `SystemTime::now()` call. They are safe to call from
  any thread and require no synchronization.
- **No new crate dependencies.** The pull-on-redraw pattern requires only `std::time::SystemTime`
  (already sanctioned by ADR-v3.2-001) and the existing ratatui 0.30 + crossterm 0.29 stack.
  Zero runtime dep count does not increase.
- **Exceeds update-rate requirements.** 62 Hz >> 10 Hz (stopwatch) >> 1 Hz (clock). Both
  `TIME-DSP-05` and `TIME-SW-08` are satisfied with large margin.

### Negative

- **GUI requires a conditional `setInterval` (D-11 exception).** The no-polling discipline
  (`CLAUDE.md §"No polling (D-11)"`) prohibits frontend polling of `get_state()`. For the
  GUI to show a live clock or stopwatch, it needs a timer that fires periodically. This is
  implemented as a conditional `setInterval` that activates only when clock/stopwatch modes
  are active, and deactivates when they exit. This is the smallest possible D-11 exception.
- **Display update frequency is tied to frontend redraw rate.** The 62 Hz CLI refresh rate
  is adequate for all current requirements, but a future frontend with a slower redraw cycle
  (e.g., a 1 Hz terminal refresh) would need its own timing solution. This is not a current
  concern.

### Neutral

- **Clock display exits on keypress, not "after" keypress.** The D-39.3 implementation
  clears `clock_active` at the top of `handle_key()`, so the key is processed immediately.
  This matches real HP-41CX behavior where pressing any key returns to normal display and
  the key functions normally. There is no "consume the key to exit clock mode" step.
- **Stopwatch keyboard mode is a transient CalcState flag.** `stopwatch_keyboard_mode: bool`
  carries `#[serde(default, skip)]` — it does not persist across save/load cycles. A user
  who saves with the stopwatch keyboard mode active will resume with the stopwatch stopped
  and keyboard mode inactive. The accumulated elapsed time is persisted separately via
  `stopwatch_accumulated: f64` (D-38.6).

## Alternatives Considered

### Option B: Async timer in core

This alternative would introduce an async runtime (e.g., `tokio`) or a spawned `std::thread`
into `hp41-core` that fires timer events for clock/stopwatch updates.

The relevant context decision (38-CONTEXT.md D-carried.7) states verbatim:

> **D-carried.7:** "Pull on redraw" architecture for live display — hp41-core remains
> thread-free and async-free. Frontend redraw cycle computes time-dependent display state
> on-demand.

The Phase 39 context (39-CONTEXT.md D-39.2) confirms:

> **D-39.2:** The existing 16ms poll loop (`event::poll(Duration::from_millis(16))`)
> already redraws the TUI ~62 times/second without requiring a keypress. Clock display
> updates at ≥1 Hz (TIME-DSP-05) and stopwatch at ≥10 Hz (TIME-SW-08) are both trivially
> met — the poll loop calls `terminal.draw()` before polling, so display refreshes even
> when no input arrives. No new timer or async infrastructure needed.

**Why rejected:** Introducing an async runtime or threads into `hp41-core` would violate
the core-as-pure-computation design principle. `hp41-core` has been thread-free since v1.0;
adding `async` would require `Send + Sync` bounds to propagate through `CalcState`, blocking
closures, and the `dispatch()` call graph. The `tokio` or `async-std` dependency would add
hundreds of kilobytes of compiled code and introduce executor configuration surface. Most
critically, it is unnecessary: the 16ms poll loop already exists and already fires at 62 Hz.

### Option C: Push-from-core event system

This alternative would give `hp41-core` a notification mechanism — for example, a
`Sender<DisplayEvent>` injected into `CalcState` — that fires when the clock ticks or the
stopwatch centisecond changes.

The Phase 39 context (39-CONTEXT.md D-39.1) states:

> **D-39.1:** Live clock and stopwatch display take HIGHEST priority in
> `get_display_string()` — above entry_buf, above PRGM mode, above ALPHA mode. When
> `state.clock_active` is true, format the current time (applying `time_offset_secs` +
> `clock_12h` + `clock_display_mode`) and return it. When `state.stopwatch_keyboard_mode`
> is true, format the elapsed stopwatch time as `HH:MM:SS.hh` and return it. This matches
> real HP-41CX behavior where CLKT and SW override all other display modes.

**Why rejected:** Push-from-core requires injecting a channel or callback into `CalcState`,
making it non-trivially constructible and hard to serialize. `CalcState` would need a
`#[serde(skip)]` sender field, and every test that constructs `CalcState::new()` would
need to pair it with a receiver. The "push" model also inverts control in a way that
complicates the GUI integration: the GUI event loop would need to `select!` across both
user input and core-generated display events, which adds complexity to both the Tauri
command handlers and the React component lifecycle. The pull model is simpler in all
dimensions.

### Option D: Dedicated polling thread in frontend

This alternative would spawn a background thread in each frontend (`hp41-cli`, `hp41-gui`)
that sleeps 100ms between iterations and forces a display refresh.

**Why rejected:** A dedicated polling thread duplicates work the existing 16ms ratatui poll
loop already does for free. In the CLI, the ratatui draw-before-poll pattern already
satisfies all update-rate requirements. In the GUI, a dedicated thread would fight with the
React event loop rather than cooperating with it. Thread coordination introduces locking
requirements on `AppState` (the `Mutex<CalcState>` in `lib.rs`) that would hurt keystroke
latency. The conditional `setInterval` (D-11 exception for GUI) is a significantly smaller
and more targeted solution than a background thread.
