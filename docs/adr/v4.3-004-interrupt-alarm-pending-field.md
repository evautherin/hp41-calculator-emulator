# ADR-v4.3-004: Interrupting Control Alarm Pending-Interrupt Mechanism

**Status:** Locked 2026-06-06
**Owner:** Phase 63 Plan 63-02
**Requirement refs:** ALARM-02, ALARM-03
**Downstream consumers:**
- `hp41-core/src/state.rs` (`pending_interrupt`, `pending_interrupt_alarm_index`, `pending_interrupt_depth`, `pending_yield` fields)
- `hp41-core/src/ops/program.rs` (`run_loop` interrupt boundary + Phase-C alarm scan + ack-after-RTN; `run_program` + `resume_program` clear-on-entry)
- `hp41-core/src/ops/time/alarm.rs` (`dispatch_alarm_event` — running-path routing to `pending_interrupt`)
- `docs/hp41-time-divergences.md` §D-40-04 (divergence entry; flipped to implemented in Phase 63)
- ADR v4.3-003 (alarm prefix semantics — confirmed CORRECT before this ADR was authored)

---

## Context

Prior to Phase 63, interrupting control alarms (`>>label`) were stored faithfully in the alarm
catalog (`AlarmType::Control { label, interrupting: true }`) but the `interrupting: true` flag
was not acted upon at runtime. When a past-due interrupting alarm fired while a program was
running, `dispatch_alarm_event` pushed `"alarm:interrupting:deferred"` to `event_buffer` — a
dead-end stub acknowledged as deferred in §D-40-04 of `docs/hp41-time-divergences.md`.

On real HP-41CX hardware, an interrupting control alarm halts the running program at the next
instruction boundary, executes the alarm's stored label program inside the interrupted
program's register environment, and resumes the interrupted program when the alarm program
completes — subject to the 4-level call stack limit.

Three design constraints shaped the Phase 63 implementation:

1. **Synchronous, single-threaded `run_loop`:** `hp41-core` has no async, no threads, and no
   sleep (`CLAUDE.md` no-async invariant). The interrupt must be injected at a synchronous
   instruction-boundary check within the existing clone-and-loop interpreter.

2. **GUI Mutex held during `run_loop`:** The Tauri GUI holds the `AppState` Mutex for the
   entire `run_loop` execution. External `tick_time` calls that normally run `check_alarms`
   cannot fire mid-program. Without an in-loop alarm scan, a compute-heavy program would only
   see an alarm after it ends, violating the "next instruction boundary" requirement (D-05).

3. **4-way exhaustive-match invariant must not be triggered:** No new `Op` variant should be
   added. The interrupt injection must reuse existing call-stack machinery (`push state.pc` +
   `Op::Rtn` pop), not introduce a new resume opcode.

ADR v4.3-003 confirmed that the `>>` / `>` prefix code in `parse_alarm_type` is already
correct (`interrupting: true` for `>>`, `interrupting: false` for `>`), so no flag fix or
`ControlKind` enum rename was needed before implementing the runtime mechanism.

---

## Decision

**Implement interrupting control alarms via a `pending_interrupt: Option<String>` transient
field on `CalcState`, set by `dispatch_alarm_event` when a program is running, consumed by
a synchronous boundary check at the top of `run_loop` each iteration.**

The complete mechanism is described below.

### 1. Transient Control Fields (all `#[serde(default, skip)]`)

Four new fields added to `CalcState` in Plan 63-01:

| Field | Type | Role |
|-------|------|------|
| `pending_interrupt` | `Option<String>` | Label to XEQ on the next run-loop boundary; consumed (`.take()`) by `run_loop` |
| `pending_interrupt_alarm_index` | `Option<usize>` | Alarm index for ack-after-RTN (D-06a); paired with `pending_interrupt` |
| `pending_interrupt_depth` | `Option<usize>` | `call_stack.len()` at injection; gate for ack-after-RTN (D-06) |
| `pending_yield` | `Option<YieldState>` | Typed yield channel for PSE/VIEW/AVIEW (D-04; separate concern, same field group) |

All four carry `#[serde(default, skip)]` — they are transient and reset to `None` by
`CalcState::new()`. They do not appear in JSON save files; older save files load without
migration.

No new `Op` variant is added. The 4-way exhaustive-match invariant (`dispatch`, `execute_op`,
CLI `op_display_name`, GUI `op_display_name`) is not triggered.

### 2. Phase-C Alarm Scan (inside `run_loop`)

```rust
// After `steps += 1`:
if steps == 1 || steps.is_multiple_of(1000) {
    time::alarm::check_alarms(state);
}
```

Fires on the very first step (converts any pre-existing past-due alarm to `pending_interrupt`
while `is_running=true`) and every 1000 steps for long-running programs. At emulated execution
speed, 1000 steps is sub-millisecond — effectively "next boundary" from a human perspective.
This is the Phase-C check from `ARCHITECTURE.md`, required because the GUI Mutex prevents
external `tick_time`-driven `check_alarms` from running mid-program.

### 3. Interrupt Injection Boundary (inside `run_loop`, after Phase-C scan)

```rust
if let Some(label) = state.pending_interrupt.take() {
    if state.call_stack.len() >= 4 {
        // D-07: silent 4-level cap suppress — hardware-faithful behavior
        state.pending_interrupt_alarm_index = None;
        state.pending_interrupt_depth = None;
    } else {
        match find_in_program(program, &label) {
            Ok(target) => {
                state.pending_interrupt_depth = Some(state.call_stack.len());
                state.call_stack.push(state.pc);
                state.pc = target + 1;
            }
            Err(_) => {
                // D-08: missing label is a user authoring error — surface it
                state.event_buffer.push(format!("alarm:missing:{label}"));
                state.pending_interrupt_alarm_index = None;
                state.pending_interrupt_depth = None;
            }
        }
    }
}
```

The synthetic XEQ frame reuses the existing call-stack machinery verbatim. When the alarm
handler executes `RTN` (or falls off the end of the program), the existing `Op::Rtn` arm pops
`state.pc` back to the interrupted resume address — no new resume opcode needed.

### 4. Ack-after-RTN (inside `Op::Rtn` arm, after `state.pc = return_pc`)

```rust
if state.pending_interrupt_alarm_index.is_some()
    && Some(state.call_stack.len()) == state.pending_interrupt_depth
{
    if let Some(idx) = state.pending_interrupt_alarm_index.take() {
        let _ = time::alarm::acknowledge_alarm(state, idx);
    }
    state.pending_interrupt_depth = None;
}
```

The `pending_interrupt_depth` gate fires the ack only when `Op::Rtn` pops the call stack back
to the depth it had at injection — correctly skipping the ack for `RTN`s inside a nested XEQ
within the handler. The cap-drop and missing-label paths clear `pending_interrupt_alarm_index`
earlier, so the `is_some()` guard naturally skips both.

Acknowledgment + rescheduling happen inside `acknowledge_alarm` — the repeating-alarm
reschedule occurs after the handler program completes and before the interrupted program
resumes its next instruction (D-06, most hardware-faithful ordering).

### 5. Clear-on-Entry (`run_program` and `resume_program`)

Both entry points clear all four transient fields before entering `run_loop`:

```rust
state.pending_interrupt = None;
state.pending_interrupt_alarm_index = None;
state.pending_interrupt_depth = None;
state.pending_yield = None;
```

This implements D-09 (drop interrupt set just before STOP) and D-12 (clear-on-entry).

### 6. `dispatch_alarm_event` Running-Path Routing

`check_alarms` calls `dispatch_alarm_event(state, label, index, defer_to_run_loop=true)`.
When `defer_to_run_loop=true` and the program is running with no pending interrupt and no
solver/modal active:

```
Running + no pending + no solver/modal + defer=true → pending_interrupt = Some(label)
                                                        pending_interrupt_alarm_index = Some(index)
```

All other paths (idle, already-pending, solver/modal active, `defer=false` from `op_almnow`)
route to `alarm:xeq:{label}` in `event_buffer` — same as non-interrupting alarms.

## Edge Handling

| Case | Disposition | Decision ref |
|------|-------------|-------------|
| Call stack at 4-level cap | Silent suppress; alarm stays `past_due` | D-07 |
| Missing handler label | Surface `alarm:missing:{label}` event; no ack | D-08 |
| Interrupt set just before `Op::Stop` | Dropped at `resume_program` clear-on-entry | D-09 |
| Solver (`integ_state`/`solve_state`/`difeq_state` Some) or modal active | Demote to `alarm:xeq:{label}` | D-10 |
| Idle (`is_running == false`) | Route to `alarm:xeq:{label}` via existing idle path | D-13 |
| Second interrupting alarm fires while one is pending | Demoted to `alarm:xeq:{label}` | D-13 |
| `is_running` restoration | `run_program` always restores on all paths including errors | D-07 |

## Consequences

### Positive

- **Hardware-faithful mid-run interruption.** Interrupting control alarms (`>>label`) now
  execute their handler program at the next instruction boundary (within 1000 steps in the
  worst case) and resume the interrupted program from exactly where it was halted — matching
  the HP-41CX hardware behavior described in HP 00041-90035 §XYZALM.
- **No new Op variant / no 4-way match change.** The synthetic XEQ frame reuses `call_stack`
  push and the existing `Op::Rtn` pop. The 4-way exhaustive-match invariant is undisturbed.
- **No new runtime dependencies.** Consistent with the zero-new-runtime-deps discipline
  (ADR-v3.1-002).
- **Backward-compatible save files.** All four new fields carry `#[serde(default, skip)]`;
  v1.0–v4.2 save files load without migration. `CalcState::migrate_after_load()` is unchanged.
- **Repeating alarms reschedule correctly.** `acknowledge_alarm` is called after the handler
  RTN, so repeating alarms are re-armed before the interrupted program resumes (ALARM-03).
- **GUI stays responsive.** The Mutex is released between `run_loop` calls (each yield/interrupt
  cycle returns control to the Tauri command layer), so the GUI remains interactive.

### Negative / Known Simplifications

- **Interrupt-before-STOP dropped (D-09).** An alarm that fires in the last few instructions
  before `Op::Stop` will have `pending_interrupt` cleared at the next `resume_program` call.
  The real HP-41CX behavior at this edge is undocumented; this simplification is considered
  acceptable.
- **Deeper interrupt nesting out of scope.** A handler program that itself triggers a second
  interrupting alarm is demoted (the second alarm sees `pending_interrupt.is_some()` — already
  pending — and routes to `alarm:xeq:{label}` instead). Only one level of mid-run interrupt
  injection is supported in Phase 63.
- **Mid-solver interrupt demoted.** An interrupting alarm that fires while a FSOLVE/FINTG
  solver or modal is active is demoted to `alarm:xeq:{label}` (D-10), to avoid corrupting
  the solver re-entrancy state. On real HP-41CX hardware, the solver is a program-level
  construct and the same 4-level-cap behavior would apply; the demotion is conservative and
  correct.
- **Phase-C granularity is ~1000 instructions, not every instruction.** The `steps==1 ||
  steps.is_multiple_of(1000)` cadence is a practical trade-off between responsiveness and
  overhead. At emulated execution speed (~millions of steps per second), the worst-case
  detection latency is sub-millisecond and imperceptible to humans.

## Alternatives Considered

### Option B: Per-instruction alarm check (every step)

Check `check_alarms` on every iteration of `run_loop`.

**Why rejected:** `check_alarms` scans all alarms and computes `SystemTime::now()` on each
call. Calling it on every instruction would add up to 253× the alarm-scan cost per emulated
step — a measurable CPU overhead for no perceptible improvement, since 1000 steps is already
sub-millisecond at emulated speed.

### Option C: Parallel execution thread with shared `Arc<Mutex<CalcState>>`

Run a background timer thread that injects interrupts into a shared `CalcState` via a
`Mutex` or `RwLock`, making the interrupt truly concurrent with `run_loop`.

**Why rejected:** Requires `Arc<Mutex<CalcState>>` or `Arc<RwLock<CalcState>>` throughout
the entire codebase — a major architectural change violating the no-async / no-threads
invariant in `CLAUDE.md`. The real HP-41CX's 4-level call stack makes interrupt handler
programs small enough that the synchronous boundary check (within 1000 steps) is a good
approximation of hardware behavior without the concurrency complexity.

### Option D: Frontend acknowledges after `run_program` returns

Let the frontend (CLI + GUI) acknowledge the alarm and reschedule after `run_program` ends,
rather than doing so inside `Op::Rtn` in the core.

**Why rejected:** Late re-arm is ambiguous under multi-yield scenarios (the frontend sees the
result after the whole run, not after the handler specifically). Splitting alarm acknowledgment
across core + both frontends fragments logic that belongs in the single-responsibility
`acknowledge_alarm` function. The ack-after-RTN approach is more hardware-faithful (the
alarm is re-armed before the interrupted program resumes) and self-contained in `hp41-core`.

### Option E: Auto-ack in `check_alarms` when setting `pending_interrupt`

Acknowledge (and reschedule) the alarm at the moment `check_alarms` sets `pending_interrupt`,
before the handler runs.

**Why rejected:** Acknowledging before the handler runs wrongly re-arms alarms whose handlers
subsequently get dropped (4-level-cap suppress) or have a missing label. The handler might
never execute, yet the alarm would already be rescheduled — a correctness hazard. The
ack-after-RTN design naturally skips the ack in both failure cases (cap-drop and missing-label
paths clear `pending_interrupt_alarm_index` before `Op::Rtn` could fire the ack gate).
