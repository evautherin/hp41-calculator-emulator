# ADR v4.3-003 — Control-Alarm Prefix Semantics (>> vs > Resolution)

**Status:** Accepted
**Date:** 2026-06-06
**Context:** Phase 62 research task: resolve the alleged `>` / `>>` prefix inversion before implementing interrupting-alarm execution in Phase 63.

## Context

The HP-41CX Time Module supports three alarm types, two of which are "control alarms" that run
a program when they fire. These are distinguished in the ALPHA register by a prefix character:
`>>label` (double arrow) and `>label` (single arrow). The HP-41CX uses up-pointing arrow
characters on its character set; ASCII listings render them as `>>`/`>` or `^^`/`^`.

The v4.3 audit surfaced a possible inversion between the behavioral prose in
`.planning/research/CONTROL-ALARMS.md` and the existing code in
`hp41-core/src/ops/time/alarm.rs`. The CONTROL-ALARMS.md document described `>label` (single
arrow) as the "control alarm" that interrupts a running program, and `>>label` (double arrow) as
the "conditional alarm" that defers. This is the INVERSE of the existing code's `parse_alarm_type`
logic (which maps `>>` → `interrupting: true`). The divergence document D-40-04 cites a third
source, the HP 82182A Time Module OM (HP 00041-90035 §XYZALM).

Two citation discrepancies complicated the picture (D-02): D-40-04 cites the 82182A Time Module
OM, while CONTROL-ALARMS.md cites the HP-41CX OM Vol 2. It was unclear whether the two manuals
used contradictory notation or whether a transcription error had produced an inverted reading.

This question had to be settled before Phase 63 could safely implement the `>>` interrupt
execution engine. If the flag were inverted, Phase 63 would implement the wrong behavior and
corrupt stored alarms.

## Decision

The prefix-to-behavior mapping is established by two independent HP primary sources obtained and
read directly during Phase 62 research:

**Source 1 — HP 82182A Time Module Quick Reference Card**
Part number 82182-90002, Hewlett-Packard Company, November 1981.
The XYZALM "ALPHA Parameter Options" section states verbatim:

```
>> label  or  >> function  =  Interrupting Control Alarm
 > label  or  >  function  =  Noninterrupting Control Alarm
```

**Source 2 — HP-41CX Quick Reference Guide**
Part number 00041-90475, Hewlett-Packard Company, August 1983. Page 32, "Alarm Format":

> **Control Alarm:** runs the specified program or programmable catalog-2 function when the alarm
> comes due.
>
> **Conditional Alarm:** does not interrupt a running program, unlike the other alarms.
> If the HP-41CX is off or displaying the clock, a conditional alarm becomes a control alarm.

Page 33 diagram: `↑↑ global label` → Control Alarm; `↑ global label` → Conditional Alarm.
(↑↑ = >> = double arrow; ↑ = > = single arrow in HP-41 character set.)

**Resolved mapping (stated in observable-behavior terms):**

| Prefix | HP-41CX QRG name | 82182A QRC name | Observable behavior |
|--------|-----------------|-----------------|---------------------|
| `>>label` (double arrow) | Control Alarm | Interrupting Control Alarm | **Interrupts a running program**; executes the label immediately |
| `>label` (single arrow) | Conditional Alarm | Noninterrupting Control Alarm | Does **NOT** interrupt; fires only when the calculator is idle or off |
| (no prefix) | Message Alarm | — | Displays text and beeps |

An implementer reading only this ADR can determine unambiguously: **the alarm that interrupts a
running program is `>>label`** (double arrow). **The alarm that does NOT interrupt — firing only
when idle or off — is `>label`** (single arrow).

**Audit verdict — current code is CONFIRMED CORRECT:**

The existing `parse_alarm_type` function in `hp41-core/src/ops/time/alarm.rs` (lines 78–92):

```rust
fn parse_alarm_type(alpha: &str) -> AlarmType {
    if let Some(label) = alpha.strip_prefix(">>") {
        AlarmType::Control {
            label: label.to_string(),
            interrupting: true,        // >> = Interrupting Control Alarm ✓ CORRECT
        }
    } else if let Some(label) = alpha.strip_prefix('>') {
        AlarmType::Control {
            label: label.to_string(),
            interrupting: false,       // > = Conditional/Noninterrupting Alarm ✓ CORRECT
        }
    } else {
        AlarmType::Message(alpha.to_string())
    }
}
```

`>>` is checked before `>` (shadow-safety; longer match wins), producing `interrupting: true`.
This matches both primary sources. The code is NOT inverted. The `AlarmType::Control { label,
interrupting: bool }` field name is semantically unambiguous given this resolution: `true` means
the alarm interrupts a running program.

The `dispatch_alarm_event` routing (lines 499–510) also has the correct orientation:

```rust
AlarmType::Control { label, interrupting } => {
    if *interrupting {
        // >> path — the D-40-04 dead-end Phase 63 will replace with actual execution
        state.event_buffer.push("alarm:interrupting:deferred".to_string());
    } else {
        // > path — non-interrupting; queues label for deferred XEQ
        state.event_buffer.push(format!("alarm:xeq:{label}"));
    }
}
```

The `alarm_matches_alpha` reconstruction (`format!(">>{label}")` for `interrupting: true`,
`format!(">{label}")` for `interrupting: false`) is also correct.

**D-02 citation discrepancy resolved:** Both the 82182A QRC (82182-90002) and the HP-41CX QRG
(00041-90475) use the same prefix convention (`>>` = interrupting, `>` = non-interrupting). They
differ only in prose names ("Interrupting/Noninterrupting Control Alarm" vs "Control/Conditional
Alarm") — not in prefix semantics. The existing D-40-04 citation (HP 00041-90035 §XYZALM) is
correct and need not change.

**Root cause of the CONTROL-ALARMS.md inversion (for the record):** The HP-41CX OM Vol 2 prose
names the interrupting alarm "control alarm" and the non-interrupting alarm "conditional alarm",
but does not clearly associate these prose names with the `>` vs `>>` prefix symbols in the same
passage. The CONTROL-ALARMS.md researcher read the behavioral description of "control alarm"
(fires, interrupts program) and inferred that the single-arrow `>` was the control alarm, leaving
`>>` for "conditional." The prefix-to-name mapping is only unambiguous when the QRC/QRG diagram
is read alongside the behavioral prose. This was a documentation-reading artifact, not a code bug.

**D-05 conditional correction plan — NOT triggered:** The correction plan in D-05 applies only if
the flag is confirmed inverted. The flag is confirmed correct. No prefix flip or rename is needed.
The following constraints are carried for the record in case a future maintainer ever reconsiders
the representation: (1) the final mapping must be OM-correct (`>>` = interrupting); (2) the
representation must be unambiguous so `>` / `>>` cannot silently re-invert in a future reading;
(3) save-file back-compat must be preserved because `AlarmType::Control { interrupting }` is
serialized in `CalcState::alarms` (D-38.8) — any semantic flip without migration would
silently corrupt stored alarms. The choice between a minimal boolean flip and replacing
`interrupting: bool` with a self-documenting `ControlKind` enum is explicitly delegated to the
Phase 63 planner (D-05 "Claude's Discretion") — this ADR does not pre-commit that strategy.

**Prefix-agnostic mechanism note:** The synchronous, single-threaded interrupt mechanism
described in ARCHITECTURE.md (using `pending_interrupt: Option<String>` checked at each
`run_loop` iteration boundary) is correct regardless of which prefix wins — it is prefix-agnostic.
Only the routing condition in `dispatch_alarm_event` matters, and that condition is already
correct. Phase 63 is unblocked the moment this contract is committed: it can implement the
interrupting-alarm execution engine directly against the existing `interrupting: bool` semantics
without any prefix-mapping remediation.

**Zero runtime code changes this phase:** This ADR is the sole deliverable of Phase 62.
No `.rs` file is modified. `just ci` stays green throughout.

## Consequences

**Phase 63 is unblocked.** The contract is locked. The `>>label` interrupt mechanism can be
implemented directly in `dispatch_alarm_event` without any routing-condition flip.

**Edge case: 4-level call-stack cap.** The HP-41 supports a maximum call-stack depth of 4.
When an interrupting control alarm (`>>label`) fires while a program is running with a full
call stack, the alarm cannot push a return address. In this case the interrupt is suppressed
and the alarm is left `past_due = true`; the running program continues unaffected. This behavior
is hardware-consistent with the documented 4-level cap (OM-silent on the exact alarm disposition
at depth 4; rated MEDIUM confidence per research assumption A3 — hardware verification would
confirm). Phase 63 must implement this guard.

**Edge case: idle-fire behavior.** When no program is running (`state.is_running == false`), an
interrupting control alarm (`>>label`) fires as a direct XEQ of the label — there is no program
to interrupt, so execution is immediate. For conditional alarms (`>label`), HP-41CX QRG page 32
states: "if the HP-41CX is off or displaying the clock, a conditional alarm becomes a control
alarm." The detailed state-machine for `>` idle-fire (off / clock-display / on-but-idle
sub-cases) is a Phase 63 implementation detail; the existing `alarm:xeq:{label}` event routing
handles the "execute label when idle" path correctly today.

**Edge case: non-interrupting path unchanged.** The existing `>label` execution path —
`dispatch_alarm_event` emitting `"alarm:xeq:{label}"` into `event_buffer`, drained by CLI
`drain_event_buffer` (which calls `run_program`) and by GUI `tick_time` — is CORRECT and MUST
remain unchanged in Phase 63. Phase 63 modifications touch only the `interrupting: true` arm
of `dispatch_alarm_event`. The `interrupting: false` arm must not be modified.

**D-40-04 deferred.** `docs/hp41-time-divergences.md §D-40-04` is NOT updated in this phase.
Its update (cross-referencing this ADR and reflecting the closed state of the prefix question)
is a Phase 66 success criterion. Clean split: ADR = decision (now); divergence doc = reflected
state (Phase 66).

**Save-file back-compat.** Since the code is confirmed correct and no prefix flip is applied,
no migration is needed. Existing v4.x stored alarms with `interrupting: true` (set via the
`>>` prefix at XYZALM-set time) correctly represent interrupting control alarms before and after
Phase 62. The D-05 correction-plan migration constraint is not triggered.

## Alternatives considered

- **Rename `interrupting: bool` to a `ControlKind` enum (Interrupting | Conditional)** —
  not pre-committed here. Deferred to the Phase 63 planner as an allowed option per D-05
  "Claude's Discretion." The boolean field name is unambiguous given this ADR's resolution,
  but a self-documenting enum would permanently kill the ambiguity. The planner may choose it
  if the refactor cost is acceptable within Phase 63 scope.

- **Treat CONTROL-ALARMS.md as authoritative (accept the inversion)** — rejected. Overridden by
  two independent HP primary-source documents (82182A QRC 82182-90002, 1981; HP-41CX QRG
  00041-90475, 1983) read directly during Phase 62 research. CONTROL-ALARMS.md was a secondary
  in-project research note; the primary sources take precedence.

- **Defer prefix resolution to Phase 63** — rejected. Phase 63 cannot safely implement the
  interrupt execution engine without a locked mapping; an unresolved inversion would risk
  implementing the wrong behavior and corrupting stored alarms. Phase 62 exists precisely to
  close this gate before any runtime code is written.
