# ADR-v3.1-002: Distribution Primitives Policy — `statrs` Rejected; AS 239 / AS 63 / Acklam Hand-Coded ~140 LOC

**Status:** Locked 2026-05-22
**Owner:** Plan 33-02
**Requirement refs:** STAT-DST-06, STAT-DST-07, Pitfall 19 (33-RESEARCH.md §"Free42 GPL contamination guard"), Pitfall 27 (33-RESEARCH.md §"Free42 stats-domain contamination guard")
**Downstream consumer:** `hp41-core/src/ops/stat1/distributions.rs` (3 hand-coded primitives — `norm_cdf_inv_f64` Acklam ≡ AS 241, `gamma_regularized_f64` AS 239, `beta_regularized_f64` AS 63); `scripts/check-free42-contamination.sh` (Phase 33 Plan 33-00 18-token extension; both `math1/` and `stat1/` directories scanned at every CI run)
**ADR write-up prose:** Phase 35 / STAT-DOC-04 (this is the narrative ADR; the lock happened during research SUMMARY.md write 2026-05-21 + Phase 33 discuss-phase D-33.5 2026-05-22)

---

## Context

Three distribution primitives are needed to ship the Stat 1 Pac's distribution
programs:

- `norm_cdf_inv_f64` — Acklam's quantile function for the normal distribution
  (algorithmically equivalent to AS 241 / Wichura 1988). Consumed by ΣNORMD in
  inverse-CDF mode.
- `gamma_regularized_f64` — regularised lower incomplete gamma `P(s, x)`. Consumed
  by ΣCHISQD (chi-square distribution evaluated via `P(ν/2, x/2)`).
- `beta_regularized_f64` — regularised incomplete beta `I_x(a, b)`. Consumed by
  ΣTSTAT (Student-t distribution evaluated via the beta-function relation).

`rust_decimal 1.42`'s `MathematicalOps` trait does not implement any of these
quantile/CDF functions (`.planning/research/STACK.md` confirms the gap). Two
implementation strategies were evaluated during Phase 33 research:

- **Strategy A — `statrs` 0.18.0 runtime dependency.** `statrs` exposes
  `Normal::inverse_cdf`, `ChiSquared::cdf`, and `StudentsT::cdf` against a
  fixed `f64` interface. Reuse is mature; the crate has been published since
  2014 and is widely used in the Rust scientific-computing ecosystem.
- **Strategy B — hand-coded primitives from primary literature.** Three
  functions, ~140 LOC total, implemented in `hp41-core/src/ops/stat1/distributions.rs`
  from Wichura's AS 241 (refined by Acklam 1996/1999), Shea's AS 239 (≡ Cody 1976
  for the chi-squared probability function), and Majumder & Bhattacharjee's AS 63
  (≡ Lentz 1976 continued-fraction expansion of the incomplete beta).

The research SUMMARY.md write (2026-05-21) recommended Strategy B for three
reasons: zero new runtime dependency, last-digit OM-divergence control, and
freedom from Free42's stats-domain code path (Pitfall 27). Phase 33 discuss-phase
D-33.5 locked the recommendation on 2026-05-22.

Every primitive is validated against an inline scipy oracle block of ≥ 6
`(input, scipy_expected, tolerance)` tuples per primitive (D-33.6) BEFORE any
program Op consumes it (STAT-DST-06). The two-level tolerance policy follows
STAT-QUAL-05: `1e-9` for closed-form primitives, `1e-7` for iterative ones.

---

## Decision

**Strategy B is locked: three primitives hand-coded from primary AS sources in
`hp41-core/src/ops/stat1/distributions.rs`.** The file is ~140 LOC. Each
primitive returns `Result<f64, HpError>` so cancellation paths (Pitfall 25) and
convergence-failure paths (SPEC.md Req. 33) flow through the standard error
channel. The `f64` boundary is the bridge from `rust_decimal HpNum`: callers
convert at the entry, the primitive runs entirely in `f64`, and the caller
converts the result back to `HpNum` at the boundary.

Algorithm independently re-derived from primary sources (Wichura AS 241 / Cody AS 239 / Lentz AS 63); Free42 source consulted only as sanity-check oracle, not copied.

The disclaim sentence above is grep-detectable in CI. The same wording appears
in the per-file header of `hp41-core/src/ops/stat1/distributions.rs` (two-line
SPDX-style banner above the `//!` doc-comment) and in this ADR's Footnotes
section below. The CI enforcement script `scripts/check-free42-contamination.sh`
extends the v3.0 12-symbol policy by 6 stat1-era prefix tokens
(`math_normal_`, `math_chi2_`, `math_t_dist_`, `math_F_dist_`, `math_gamma_`,
`math_beta_inc`) — drawn from Free42's `common/core_math2.cc` function-name
conventions — and adds the `hp41-core/src/ops/stat1` directory to the scanned
set, for a combined 18-token policy across both `math1/` and `stat1/` (Phase 33
Plan 33-00 / D-32.7 reassignment).

The Acklam coefficient table (21 constants `ACKLAM_A1..D4` + an iterative
refinement constant) is verbatim from the published Acklam mirror
(stackedboxes.org 2017 article; public-domain mirror of the 1996/1999 paper);
the inline `#![allow(clippy::excessive_precision)]` annotation preserves citation
form (the relative-error bound depends on the exact coefficients). The AS 239
gamma series + asymptotic continued-fraction switch is implemented per Numerical
Recipes 3e §6.2 with the AS 239 series cutoff at `x < s + 1`. The AS 63 beta
continued fraction uses Lentz's modified algorithm per NR §6.4 with the AS 63
convergence-tolerance constant.

## Consequences

### Positive

- **Zero new runtime dependencies.** `rust_decimal 1.42` remains the only
  numerical crate in `hp41-core/Cargo.toml`. Strategy A would have pulled
  `statrs 0.18.0` + transitive `approx 0.5.0` into the runtime dependency
  graph — three new compilation units, no security-audit history, and a new
  surface for Pitfall 11 (transitive-dep audit) to police.
- **Last-digit OM-divergence risk eliminated.** Hand-coded primitives operate
  on `f64` end-to-end with `HpNum` only at the boundary; control of the
  truncation point is local to `hp41-core`. `statrs`'s `f64`-only interface
  forces conversion shims (`HpNum → f64 → HpNum`) that drift in the 10th digit
  because the round-trip is not bit-identical to `rust_decimal`'s 10-significant-
  digit rounding policy (the policy that guarantees the v1.x 503-case
  `numerical_accuracy.rs` baseline).
- **Pitfall 27 mitigation in place.** Hand-coding from Wichura / Cody / Lentz
  primary sources keeps the implementation provably independent of Free42's
  `core_math2.cc` stats path. The 18-token CI guard catches any future
  drive-by edit that imports a Free42 identifier.
- **Oracle-tuple validation surfaces are cleanest possible.** Every primitive
  carries its own inline-constant block (≥ 6 tuples per primitive against
  scipy.stats) in `#[cfg(test)] mod tests` at the bottom of the file. The
  oracle values were frozen at write-time via a one-shot Python snippet
  preserved in the plan comments; they never re-generate (D-33.6).

### Negative

- **~140 LOC of hand-coded numerical code.** One-time cost; reviewed during
  Plan 33-02 with the verbatim-coefficient discipline above. Maintenance
  burden is approximately zero — the Acklam / AS 239 / AS 63 algorithms have
  been stable since the 1970s–1990s and require no version bumps.
- **Two-level tolerance discipline (STAT-QUAL-05) required.** Callers must
  choose `1e-9` (closed-form: Acklam quantile, Lanczos `ln_gamma`) or `1e-7`
  (iterative: AS 239 series, AS 63 continued fraction). The tolerance lives in
  the caller, not the primitive, so the primitive returns a converged `f64`
  with documented bounds rather than re-asserting tolerance at every call site.

### Neutral

- **Future v3.2+ pacs needing distribution primitives extend
  `distributions.rs`.** A future Time Pac (Lanczos gamma for date-difference
  functions) or an Advantage Pac (cumulative-binomial via beta-regularised)
  reuses the same hand-coded pattern + per-primitive oracle-tuple block. The
  precedent scales without re-litigating the `statrs` rejection.
- **Forward reference: the `check-free42-contamination.sh` 18-token extension
  landed in Phase 33 Plan 33-00 ahead of any `stat1/*.rs` algorithm file
  (STAT-QUAL-09 reassigned from Phase 37 → Phase 33 per D-33.8 / D-32.7
  reassignment).** Phase 35 documents the policy retrospectively; the CI
  enforcement was already running before the first ΣNORMD code shipped.

## Alternatives Considered

### Option A: `statrs 0.18.0` runtime dependency

The rejected alternative is documented in `.planning/research/SUMMARY.md`
(write date 2026-05-21) and reaffirmed in 33-CONTEXT.md D-33.5 / D-33.2. The
research note's rejection paragraph reads:

> `statrs` (0.18.0) was evaluated as a candidate dependency for the three
> distribution primitives needed by ΣNORMD, ΣCHISQD, and ΣTSTAT. The crate is
> mature and widely used, but three properties rule it out: (a) it adds a new
> runtime dependency with its own transitive surface (`approx`, `nalgebra`
> features), violating the "zero new runtime deps unless justified" discipline
> (Pitfall 11); (b) its `f64`-only API forces a `HpNum → f64 → HpNum`
> conversion shim at every call site, which can drift in the 10th digit
> against `rust_decimal`'s 10-significant-digit rounding policy that
> underpins the v1.x numerical accuracy baseline; (c) `statrs` vendor-binds
> several Free42-derived approximation paths internally, partially defeating
> the Pitfall 27 contamination guard at the dependency boundary. Hand-coding
> the three primitives from primary AS sources (Wichura AS 241 / Cody AS 239
> / Lentz AS 63) is the cleanest cross-check.

**Why rejected (additional context beyond the verbatim research-note quote):**

- **Pitfall 11 (transitive-dep audit) ceiling.** v3.0 closed at zero new
  runtime deps across the entire milestone. Adding `statrs` would re-open the
  dependency conversation for every future v3.x pac; refusing it once sets the
  precedent for v3.2+ to follow.
- **`f64`-only interface mismatch.** `rust_decimal`'s 10-significant-digit
  policy is what guarantees the 99.3 % (763/768) numerical-accuracy baseline
  from v3.0. A `HpNum → f64 → HpNum` round-trip through `statrs` is not
  bit-identical to a hand-coded `f64` primitive that takes its rounding cue
  from the caller; the difference manifests in the last displayed digit on
  worked examples from the OM.
- **Pitfall 27 surface.** `statrs`'s code path for some primitives is itself
  derived from the same body of literature as Free42's `core_math2.cc`,
  including (in some versions) verbatim approximation tables. The
  contamination guard would need to extend to inspect the dependency tree,
  not just `hp41-core/src/ops/stat1/`. Hand-coding from primary sources keeps
  the audit surface inside the repository.

### Option B: Vendored Free42 source-port

A third option was considered: vendor the Free42 stats primitives
(`free42/common/core_math2.cc::math_normal_inv`, `math_chi2_cdf`, `math_t_dist_cdf`)
under a clean-room translation banner.

**Why rejected:** Free42 is GPL v2+. Vendoring (even with translation) creates
a GPL boundary inside `hp41-core` that conflicts with the project's permissive
licensing posture. Pitfall 19 (Free42 GPL contamination guard) explicitly
forbids this path; the CI enforcement script enforces zero distinctive Free42
identifiers across both `hp41-core/src/ops/math1/` and `hp41-core/src/ops/stat1/`.
Hand-coding from Wichura / Cody / Lentz primary sources (all > 50 years old, in
the public domain in every jurisdiction) is the legally-clean alternative.
33-CONTEXT.md D-33.5 codifies this as the policy.
