# ADR v4.1-005 — iOS Scale + Safe-Area Architecture (outer-frame insets, portaled overlays)

**Status:** Accepted
**Date:** 2026-06-03
**Context:** v4.1 iOS Foundation — quick tasks 260603-klp, 260603-laz, 260603-mxg, 260603-sef

## Context

The GUI scales the whole calculator to the viewport with a CSS `transform: scale()` in
`ScaledApp` (`main.tsx`, established by quick task 260602-kw4). On-device on iPhone this
interacted badly with iOS safe-area insets and `position: fixed` overlays:

- The Phase-55 safe-area padding lived **inside** the scaled content (`.calculator-safe-area`),
  so the rendered top gap was `scale × inset`. At scale < 1 (e.g. PRGM mode adds height) the
  gap shrank below the Dynamic Island and the 7-segment display clipped under it.
- The help-overlay header consumed its own inset (260603-klp), and the iOS keyboard's
  dismissal didn't reliably fire a `resize`, leaving the scaler stuck at a too-small scale
  after closing an overlay.
- `position: fixed` bottom sheets / the ALPHA bar were rendered **inside** the
  `transform`ed node. A transform ancestor becomes the containing block for `position:
  fixed` descendants, so they were glued to the scaled calculator's box, overlapping the
  keypad — not pinned to the viewport.

## Decision

**Handle safe-area once, outside the transform; recompute scale on the right events; and
portal `position: fixed` overlays out of the scaled tree.**

1. **Safe-area at the outer frame, in a stylesheet (mxg).** The un-scaled outer wrapper
   carries `padding: env(safe-area-inset-*)` via a `.scaled-app-frame` **CSS class** (NOT a
   React inline style — `env()` set through the CSSOM is unreliable on WKWebView and resolves
   to 0). `computeScale` fits the calculator into the inset-reduced available area. The
   per-component insets (`.calculator-safe-area`, `.help-overlay-header`) are removed — the
   Dynamic Island / home-indicator gaps now render at full device pixels regardless of scale.
2. **Recompute on overlay/PRGM/keyboard changes (laz, mxg).** `App` dispatches a custom
   `hp41:recompute-scale` event whenever the help/settings overlay or PRGM/print sheet
   toggles; `ScaledApp` re-measures across `requestAnimationFrame` + a 350 ms timeout (to
   outlast the iOS keyboard-dismiss animation, which doesn't reliably fire `resize`), and
   also listens to `window.visualViewport` `resize`/`scroll`.
3. **Portal `position: fixed` overlays to `document.body` (sef).** The iOS print bottom
   sheet (and, while it existed, the ALPHA bar) are rendered via
   `createPortal(..., document.body)` so `position: fixed` resolves against the viewport, not
   the scaled box. The peek-reservation that keeps the keypad above a visible sheet still
   finds it via `document.querySelector('.bottom-sheet')`.
4. **Pinch-zoom locked (laz).** The calculator owns its own CSS-transform fit, so browser
   pinch-zoom only pans/offsets it: viewport meta `maximum-scale=1, user-scalable=no` +
   WebKit `gesture*`/multi-touch `touchmove` `preventDefault`.

## Consequences

- iOS top display clears the Dynamic Island in all modes; overlays close without leaving a
  stale scale; bottom sheets sit above the home indicator without overlapping the keypad.
- Desktop is a no-op: `env(safe-area-inset-*)` = 0, the outer padding is 0, `computeScale`'s
  available area equals the full viewport, and there are no fixed-in-transform overlays at
  scale ≈ 1.
- **Frontend-only**; no `hp41-core`/IPC change.
- **Testing note:** vitest runs `globals: false` (no testing-library auto-cleanup); portaled
  nodes therefore need an explicit `afterEach(cleanup)` to avoid leaking across tests.
- **Gotcha catalog:** the recurring traps (inline `env()`, fixed-in-transform, keyboard-no-
  resize, disk-full builds) are recorded in the `reference_ios_gui_layout_gotchas` memory.
