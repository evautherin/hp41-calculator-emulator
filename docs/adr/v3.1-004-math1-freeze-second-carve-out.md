# ADR-v3.1-004: `math1/` Freeze Second Carve-Out — `xrom.rs` + `modal.rs` (≤ 8-Line Dispatch Wiring)

**Status:** Locked 2026-05-22
**Owner:** Phase 33 plan-phase (D-33.3b)
**Requirement refs:** STAT-FW-01, STAT-FW-03, STAT-DOC-05 (CLAUDE.md amendment gated by this ADR), Pitfall 22 (33-RESEARCH.md §"Mnemonic shadowing — XROM bit-1 arm fires after bit-0")
**Downstream consumer:** `hp41-core/src/ops/math1/xrom.rs` (`STAT_1: XromModule` const + bit-1 dispatch arm at the `xrom_resolve` call site); `hp41-core/src/ops/math1/modal.rs` (`ModalProgram::Stat1(Stat1Step)` enum variant + 3-arm dispatch wiring totalling ~8 lines); `hp41-core/src/ops/stat1/modal.rs` (`Stat1Step` enum + per-step semantics — entirely outside the frozen `math1/` module boundary); `CLAUDE.md` "Frozen Invariants → Core engine" section (amendment listing the carve-outs, gated by this ADR's Status: Locked line — Plan 35-04 task)
**ADR write-up prose:** Phase 35 / STAT-DOC-04 (this is the narrative ADR; the lock happened during Phase 33 plan-phase user-confirmed session 2026-05-22 / D-33.3b)

---

## Context

`hp41-core/src/ops/math1/` is FROZEN since Plan 25-01 (v3.0 invariant per
`CLAUDE.md §"Core engine"`). The frozen-invariant rule reads:

> `hp41-core/src/ops/math1/` is frozen since Plan 25-01. Math Pac I
> algorithms re-derived from HP OM 00041-90034 (1979); Free42 consulted as
> sanity-check oracle only, not copied. Every file in this directory carries
> the verbatim disclaim header.

The freeze exists for two intertwined reasons: (a) the Math Pac I algorithms
shipped to v3.0 with a 99.3 % (763/768) `numerical_accuracy.rs` baseline that
no future edit is permitted to regress, and (b) every file in `math1/` carries
the Free42 disclaim header that the Plan 32-03 CI guard
(`scripts/check-free42-contamination.sh`) verifies on every CI run. Edits to
files under `math1/` are therefore high-cost and high-risk by policy.

v3.1 adds a SECOND XROM module (Stat 1 Pac, hardware-XROM ID 2 per
`calc.fjk.ch/db/hp41mod.php` "Statistics Pac 1B") that needs two integration
points with the existing XROM framework:

- **XROM registry extension (`math1/xrom.rs`).** A `pub const STAT_1: XromModule`
  declaration listing the 26 Stat 1 Pac entry-point mnemonics, alongside the
  existing `MATH_1` const. The `xrom_resolve(name, modules)` function gains a
  bit-1 arm: if `modules & 0b0000_0010 != 0`, try `stat1_resolve(name)` after
  `math1_resolve(name)` has returned `None`. This was always intended for
  v3.1+: the v3.0 `xrom.rs` carried an inline comment-stub
  `// if modules & 0b0000_0010 != 0 { stat1_resolve(name) }` placeholder at
  the bit-0 arm's tail.
- **Modal dispatch extension (`math1/modal.rs`).** v3.0's
  `pub enum ModalProgram { Matrix, Solve, Poly, Integ, Difeq, Four }` is the
  single source of truth for prompt-driven workflows. Stat 1 Pac introduces 5
  multi-step modal flows (ΣNORMD 3-mode dispatcher, ΣCHISQD ν-prompt + 2-mode
  dispatcher, ΣPOLYP DEGREE prompt + regression, SEED ALPHA prompt, plus one
  bonus iteration). Adding these as ModalProgram variants requires either
  (a) one new variant `Stat1(Stat1Step)` where `Stat1Step` is a separate enum
  in `stat1/modal.rs`, or (b) five separate variants on the v3.0 enum, or
  (c) a parallel `Stat1ModalProgram` enum.

D-33.3 (Phase 33 plan-phase) locked the first carve-out for `xrom.rs` only —
the bit-1 stub was always intended for v3.1+ and is structurally narrow.
D-33.3b (Phase 33 plan-phase, user-confirmed 2026-05-22 during
`/gsd-plan-phase 33`) amended to add `modal.rs` as the second carve-out, with
the explicit constraint that the math1/modal.rs delta stays ~8 lines of pure
dispatch wiring and `Stat1Step` semantics live entirely in the NEW
`stat1/modal.rs` file (outside the frozen module).

---

## Decision

**The second carve-out is locked:** `hp41-core/src/ops/math1/xrom.rs` AND
`hp41-core/src/ops/math1/modal.rs` are sanctioned exceptions to the
`math1/` freeze. The freeze continues to apply, unchanged, to all OTHER files
in `math1/` (`complex.rs`, `difeq.rs`, `four.rs`, `hyperbolics.rs`,
`integ.rs`, `matrix.rs`, `mod.rs`, `poly.rs`, `solve.rs`, `trans.rs`,
`tri.rs`). The carve-out is gated by THIS ADR: the CLAUDE.md "Frozen
Invariants → Core engine" amendment (Plan 35-04 task) explicitly cites
ADR-v3.1-004 as the policy authority. The total edit footprint in `math1/` is
under 30 lines combined across `xrom.rs` + `modal.rs`.

The carve-out perimeter is narrow and intentional:

- **`xrom.rs`:** add `pub const STAT_1: XromModule { id: 2, name: "STAT 1B", ops: &[...26 entries] }`;
  add `fn stat1_resolve(name: &str) -> Option<Op>` (delegating to
  `crate::ops::stat1::dispatch_by_name`); add the bit-1 arm in `xrom_resolve`.
  The bit-1 arm fires AFTER the bit-0 arm so a Math 1 name keeps its v3.0
  resolution priority (Pitfall 22 — mnemonic shadowing).
- **`modal.rs`:** add `Stat1(crate::ops::stat1::modal::Stat1Step)` to the
  `ModalProgram` enum (one line, alongside the 6 v3.0 variants); add the
  matching arm in `current_prompt()`, `requires_alpha_label()`, and the
  submit dispatcher (each delegating to `crate::ops::stat1::modal::*`). The
  three arms total ~8 lines.

No Stat 1 Pac algorithm code lands in `math1/`. The `Stat1Step` enum (with
5 variants: `NormdModeChoice`, `ChisqdNuPrompt`, `ChisqdModeChoice`,
`PolypDegreePrompt`, `SeedPrompt`) lives in `hp41-core/src/ops/stat1/modal.rs`.
The Stat 1 entry-point dispatch (`stat1_resolve`) calls into
`hp41-core/src/ops/stat1/dispatch_by_name`. The freeze invariant survives
because no Free42-disclaim-headered file in `math1/` ever runs Stat 1 algorithm
code — those files only carry dispatch wiring.

CLAUDE.md's "Frozen Invariants → Core engine" sentence is amended (Plan 35-04
task, gated by THIS ADR's Status: Locked line) to read approximately:

> `hp41-core/src/ops/math1/` is frozen since Plan 25-01. Math Pac I
> algorithms re-derived from HP OM 00041-90034 (1979); Free42 consulted as
> sanity-check oracle only, **not** copied. Every file in this directory
> carries the verbatim disclaim header.
> **Exceptions:** `xrom.rs` (D-33.3 / ADR-v3.1-004 — XROM registry for v3.1+
> extension; bit-1 stub was always intended for v3.1+) and `modal.rs`
> (D-33.3b / ADR-v3.1-004 — ~8-line dispatch wiring for `ModalProgram::Stat1`
> variant; `Stat1Step` semantics live in the new `stat1/modal.rs` so no
> Stat 1 Pac code leaks into the frozen module).

The exact wording is Plan 35-04's discretion (the substance is fixed).

## Consequences

### Positive

- **Stat 1 Pac extends the XROM framework without parallel registry / modal
  infrastructure.** Approximately 80 lines saved compared to the rejected
  parallel-enum alternative (see Alternatives Considered). The cost-saving is
  load-bearing for future v3.2+ pacs: every new XROM module pays the
  ~30-line-in-`math1/` cost and ~150 lines of new pac-specific files (in its
  own `<pac>/` directory) rather than ~80 lines of parallel-enum plumbing per
  pac.
- **4-way exhaustive-match invariant items 1+2 (CLAUDE.md) still apply.**
  Every Stat 1 `Op` variant lands in `dispatch()` (item 1) + `execute_op()`
  (item 2) before any caller compiles. The carve-out doesn't bypass that
  discipline — it only widens the scope of files in `math1/` that may
  legitimately change to keep up with the invariant.
- **Free42 contamination guard surface unchanged.** Both `xrom.rs` and
  `modal.rs` continue to carry the verbatim Free42 disclaim header. The CI
  script `scripts/check-free42-contamination.sh` does not need any update
  for the carve-out itself (it already scans both files); the 18-token
  extension in Plan 33-00 is independent of this ADR (it covers stat1/-era
  identifier prefixes for the algorithm files in `hp41-core/src/ops/stat1/`).

### Negative

- **Maintenance burden: every future v3.x pac needs a similar carve-out**
  (xrom.rs registration + modal.rs dispatch arm). The carve-out scope
  (`xrom.rs` + `modal.rs` only) is the locked perimeter; expanding it
  requires a future ADR amendment. Mitigated by the narrow scope itself:
  the perimeter is small enough that "add a sibling arm" is a 5-line
  edit per future pac and the discipline carries forward by analogy.
- **CLAUDE.md "Frozen Invariants" prose grows.** The amendment lists the
  carve-outs explicitly; the section is no longer a one-sentence rule.
  Mitigated by the ADR cross-reference — readers wanting the rationale
  follow the ADR link rather than expanding the CLAUDE.md prose.

### Neutral

- **CLAUDE.md's "math1/ is frozen since Plan 25-01" sentence is amended to
  add the exception clause** naming `xrom.rs` (D-33.3 / ADR-v3.1-004 — XROM
  registry for v3.1+ extension) and `modal.rs` (D-33.3b / ADR-v3.1-004 —
  ~8-line dispatch wiring for ModalProgram::Stat1 variant; Stat1Step
  semantics live in the new stat1/modal.rs so no Stat 1 Pac code leaks into
  the frozen module). Plan 35-04 lands the amendment; it is gated by THIS
  ADR's Status: Locked line.
- **Pitfall 22 (mnemonic shadowing) discipline carries through.** The bit-1
  arm fires AFTER the bit-0 arm in `xrom_resolve`, so a hypothetical name
  collision between a Math 1 mnemonic and a Stat 1 mnemonic resolves to the
  Math 1 entry (v3.0 takes precedence). The collision surface is
  empirically empty (CATALOG 2 lists no shared mnemonics between MATH 1A and
  STAT 1B), but the priority discipline is explicit in the dispatch arm
  order.

## Alternatives Considered

### Option B: Parallel `Stat1ModalProgram` enum (rejected)

The rejected alternative is described verbatim in 33-CONTEXT.md D-33.3b
(locked 2026-05-22):

> **D-33.3b** (amended 2026-05-22, user-confirmed during `/gsd-plan-phase 33`):
> Break the `math1/` freeze a SECOND time for `modal.rs` only. Extend
> `hp41-core/src/ops/math1/modal.rs` in place with:
>   - `ModalProgram::Stat1(stat1::modal::Stat1Step)` enum variant (one line,
>     alongside `Matrix`, `Solve`, `Poly`, `Integ`, `Difeq`, `Four`)
>   - Sibling dispatch arms for `submit_step()`, `current_prompt()`, and
>     `requires_alpha_label()` — each delegating to the `stat1::modal` impls
>     (3-arm parity with the existing 6 variants)
>   - `Stat1Step` itself lives in the new `hp41-core/src/ops/stat1/modal.rs`
>     so the math1/modal.rs delta stays to ~8 lines of pure dispatch wiring
>     (no Stat 1 Pac semantics leak into the frozen module)
>   - Update CLAUDE.md "Frozen Invariants → Core engine" to list `modal.rs`
>     alongside `xrom.rs` as the two carved-out files; the rest of math1/
>     remains strictly frozen
>   - Rationale: chosen over a parallel `Stat1ModalProgram` enum (would have
>     required ~80 lines of plumbing across state.rs + commands.rs + app.rs
>     to thread two modal-program enums) and over inline single-prompt Ops
>     (would have diverged from OM 00041-90094 user flow for SEED, ΣPOLYP
>     DEGREE=?, ΣCHISQD ν=? and risked failing SPEC.md acceptance
>     criteria). The 8-line freeze amendment beats permanent infrastructure
>     duplication.

**Additional context on why Option B was rejected:**

- **Cost: ~80 lines of cross-frontend duplication.** A parallel
  `Stat1ModalProgram` enum would require CLI + GUI + test surfaces to each
  carry TWO modal-program enums and dispatch on EITHER variant at every
  prompt site. The 4-way exhaustive-match invariant (CLAUDE.md) would
  compound across two enums: each new variant in either enum must land in 4
  dispatch sites, so the cognitive load doubles per pac.
- **Loss of single-source-of-truth.** v3.0 D-30.5 (ModalProgram extension)
  locked `ModalProgram` as the canonical modal state. Spawning a parallel
  enum violates that lock and creates a precedent for v3.2+ pacs (Time →
  `TimeModalProgram`, Advantage → `AdvantageModalProgram`) where each pac
  spawns its own enum and the dispatch sites proliferate.
- **SPEC.md acceptance-criteria risk.** Inline single-prompt Ops (a third
  rejected alternative — see Option C below) would have diverged from the OM
  00041-90094 user flow for SEED / ΣPOLYP DEGREE=? / ΣCHISQD ν=?. The 8-line
  freeze amendment preserves OM fidelity at the cost of one carved-out file.

### Option C: Move the entire `math1/xrom.rs` + `math1/modal.rs` files into a new shared `xrom/` directory

A third option was considered: refactor v3.0 by extracting the XROM
infrastructure (registry + modal dispatch) into a new `hp41-core/src/ops/xrom/`
directory and rewiring v3.0's Math 1 Pac files to consume it from outside the
`math1/` boundary. The freeze invariant would then apply to `math1/`
unconditionally (no carve-outs at all).

**Why rejected:** invasive refactor of v3.0 code — every callsite that
imports `crate::ops::math1::xrom::*` or `crate::ops::math1::modal::*` would
need to update its import path; the Plan 32-04 `numerical_accuracy.rs`
baseline depends on the `math1/` tree being bit-identical to v3.0 ship, and
the refactor changes module paths that the v3.0 test files reference. The
narrow-carve-out approach (this ADR) preserves the v3.0 source tree exactly
and confines the v3.1 surface to two narrow edits in known files.
