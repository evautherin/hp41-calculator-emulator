# ADR-v3.3-004: math1/ Visibility Promotion Policy -- complex_atan2 pub(crate)

**Status:** Locked 2026-05-25
**Owner:** Plan 43-05
**Requirement refs:** ADV-MATH-09 through ADV-MATH-20 (complex number extensions in
ADV_MATH_B)
**Downstream consumer:** `hp41-core/src/ops/advantage/complex_ext.rs` (Advantage Pac
complex number extensions that call `complex_atan2`);
`hp41-core/src/ops/math1/complex.rs` (visibility promotion from `pub(super)` to
`pub(crate)` for the `complex_atan2` function)
**ADR write-up prose:** Phase 45 / Plan 45-01

---

## Context

`hp41-core/src/ops/math1/` is FROZEN since Plan 25-01 (v3.0 invariant per
`CLAUDE.md §"Core engine"`). Two prior sanctioned carve-outs are documented in
ADR-v3.1-004:

1. `xrom.rs` (D-33.3) — XROM registry for v3.1+ module extension; bits 0–4 in
   `xrom_resolve`.
2. `modal.rs` (D-33.3b) — `ModalProgram` dispatch; Stat1/Time/Advantage variants added
   in Phases 33/38/43 respectively.

The v3.3 Advantage Pac complex number extensions (SINZ, COSZ, TANZ, A^Z, and related
operations in ADV_MATH_B) require the `complex_atan2` function from
`hp41-core/src/ops/math1/complex.rs`. This function computes the two-argument complex
arctangent and is a building block for TANZ, A^Z, and CINV implementations.

The problem: `complex_atan2` is currently declared `pub(super)` in `math1/complex.rs`,
making it visible only within the `math1` module. The `advantage/complex_ext.rs` file
is in a sibling module (`ops::advantage`) and cannot access `pub(super)` items from
`ops::math1`.

The freeze invariant exists for two reasons: (a) preserving the Math Pac I numerical
accuracy baseline (99.3% at 763/768 cases), and (b) maintaining the Free42 disclaim
header integrity on every file in `math1/`. Any edit to a frozen file risks both.

The question is: how can `advantage/complex_ext.rs` access `complex_atan2` without
violating the freeze invariant?

---

## Decision

**Promote `complex_atan2` from `pub(super)` to `pub(crate)` in
`hp41-core/src/ops/math1/complex.rs`.**

This is the third sanctioned carve-out to the `math1/` freeze, following ADR-v3.1-004's
pattern:

- **The change is minimal:** a single keyword replacement on one function declaration
  (`pub(super)` → `pub(crate)`). The function body, algorithm, and all other code in
  `math1/complex.rs` are untouched.
- **The numerical accuracy baseline is unaffected:** changing visibility does not alter
  the function's behavior in any way.
- **The Free42 disclaim header is unaffected:** the header remains on the file; no
  algorithmic content is added, removed, or modified.

The complete list of sanctioned `math1/` carve-outs after v3.3 (three total):

1. `xrom.rs` — XROM registry. Bits 0 (MATH_1) + 1 (STAT_1) + 2 (TIME_MODULE) were
   added in Phases 28/33/38 respectively; bits 3 (ADV_MATH_A) + 4 (ADV_MATH_B) were
   added in Phase 43. ADR-v3.1-004, D-33.3.
2. `modal.rs` — `ModalProgram` dispatch. Variants: Matrix/Solve/Poly/Integ/Difeq/Four
   (v3.0), Stat1 (Phase 33), Time (Phase 38), Advantage (Phase 43). ADR-v3.1-004, D-33.3b.
3. `complex.rs` — single visibility promotion: `complex_atan2` from `pub(super)` to
   `pub(crate)`. Phase 43. This ADR.

All other files in `math1/` remain strictly frozen:
`difeq.rs`, `four.rs`, `hyperbolics.rs`, `integ.rs`, `matrix.rs`, `mod.rs`, `poly.rs`,
`solve.rs`, `trans.rs`, `tri.rs`.

---

## Consequences

### Positive

- **Minimal change.** One keyword replacement on one function declaration. The change is
  auditable in a single-line diff and has zero behavioral impact on any existing test case.
- **Prevents code duplication.** Duplicating `complex_atan2` in `advantage/complex_ext.rs`
  would mean maintaining two copies of a numerically-sensitive function with the Free42
  disclaim header. The freeze exists partly to prevent exactly this kind of drift. Promoting
  visibility avoids duplication while maintaining the freeze for algorithm content.
- **No new imports or dependencies.** `advantage/complex_ext.rs` uses a `use` path to
  call `crate::ops::math1::complex::complex_atan2`. No new crate dependencies are
  introduced.
- **Consistent with ADR-v3.1-004 precedent.** The carve-out mechanism (narrow surgical
  edit to one frozen file, documented in an ADR) follows exactly the pattern established
  for `xrom.rs` and `modal.rs`.

### Negative

- **The carve-out exception list grows.** After v3.3, `math1/` has three sanctioned
  exceptions instead of two. Each additional exception increases the risk that future
  developers treat the freeze as broadly negotiable. This ADR is the documented limit:
  visibility promotion is the least invasive form of change and sets a higher bar than
  logic edits.
- **`complex.rs` is now modified (visibility-only).** The file's git history will show a
  v3.3 commit that touches it, which could cause confusion for a future developer checking
  the file's change history. The commit message and this ADR provide the rationale.

### Neutral

- **Visibility promotion is the least invasive form of change.** Rust's `pub(crate)`
  makes the function accessible within the crate without exposing it to external consumers
  of `hp41-core`. The function remains private to the crate's public API.
- **The `complex_atan2` function is a pure mathematical utility.** It has no side effects,
  no state mutations, and no interaction with `CalcState`. Widening its visibility from
  `pub(super)` to `pub(crate)` cannot introduce correctness issues in the calling code.

---

## Alternatives Considered

### Option A: Re-implement `complex_atan2` in `advantage/complex_ext.rs`

This alternative would copy the `complex_atan2` algorithm into a new function in
`advantage/complex_ext.rs`, breaking the dependency on `math1/complex.rs` entirely.

The relevant context from 43-CONTEXT.md states verbatim:

> **Code Context: Reusable Assets**
> `math1/complex.rs::complex_atan2`: promote to `pub(crate)` for reuse in
> `advantage/complex.rs`

**Why rejected:** Duplicating `complex_atan2` would create two copies of a numerically-
sensitive function with the Free42 disclaim header. The freeze invariant exists to protect
the Math Pac I numerical accuracy baseline — a duplicated implementation risks drift
between the two copies over time (e.g., a bug fix in one copy not applied to the other).
More fundamentally, duplication is exactly the kind of code quality problem the freeze
was designed to prevent. The visibility promotion approach preserves a single source of
truth for the algorithm.

### Option B: Move `complex_atan2` to a shared utility module

This alternative would create a new `hp41-core/src/ops/complex_utils.rs` module
(outside both `math1/` and `advantage/`) and move `complex_atan2` there, removing it
from `math1/complex.rs`.

**Why rejected:** Moving `complex_atan2` out of `math1/complex.rs` would change the
file's structure in a way that goes beyond a visibility promotion — it would require
updating all existing callers within `math1/` to use the new module path. This is a
more invasive change than the freeze allows and would touch more lines in `math1/complex.rs`
than the single visibility change. The shared utility module adds architectural complexity
(a new module with one function) that is not justified for a single function call.

### Option C: Keep `pub(super)` and call via a wrapper in `math1/mod.rs`

This alternative would add a thin `pub(crate)` wrapper function in `math1/mod.rs` that
delegates to `complex.rs::complex_atan2`, preserving `pub(super)` on the original function
while providing a `pub(crate)` access point.

**Why rejected:** A wrapper introduces unnecessary indirection without providing any
isolation benefit. The wrapper function would be a one-line stub (`fn complex_atan2_pub(a, b) -> c { complex::complex_atan2(a, b) }`). This is strictly worse than a direct
visibility promotion — it modifies an additional frozen file (`mod.rs`) and adds a
non-obvious level of indirection in call sites. The direct `pub(crate)` promotion on
`complex.rs` is the cleaner, more honest change.
