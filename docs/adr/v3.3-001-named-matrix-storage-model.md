# ADR-v3.3-001: Named-Matrix Storage Model -- Vec<AdvMatrix> on CalcState

**Status:** Locked 2026-05-25
**Owner:** Plan 43-01
**Requirement refs:** ADV-FW-04, ADV-MTX-01
**Downstream consumer:** `hp41-core/src/state.rs` (`adv_matrices: Vec<AdvMatrix>`,
`adv_matrix_i: u8`, `adv_matrix_j: u8`, `adv_current_matrix: Option<String>`);
`hp41-core/src/ops/advantage/matrix.rs` (all named-matrix operations);
`hp41-core/src/ops/advantage/mod.rs` (`ADV_MATRIX_MAX_ROWS`, `ADV_MATRIX_MAX_COLS`)
**ADR write-up prose:** Phase 45 / Plan 45-01

---

## Context

The HP Advantage Pac (OM 00041-90482, 1985) uses named matrices identified by the
ALPHA register at the time of each matrix operation. On HP-41C hardware, matrices were
stored in X-MEM (Extended Memory) file slots — each named matrix occupied one or more
X-MEM registers identified by a name string. The naming convention was enforced by the
XEQ-by-name dispatch: `XEQ "MSTORE"` used the current ALPHA register value to locate
or create a named matrix in X-MEM.

The existing Math Pac I (XROM 7) uses a completely different matrix model: the matrix
order is stored in R14 (via `state.matrix_dim`); matrix elements live in R15+ (via
`state.matrix_active_reg`). This register-based model is accessed by absolute register
number, not by name. The two matrix systems are fundamentally incompatible — different
addressing, different storage, different lifecycles.

The emulator must choose a data model for named matrices that:
1. Faithfully represents the ALPHA-register-named, X-MEM-backed model from OM 00041-90482
2. Is completely isolated from the Math Pac I register-based model (D-43.5 mandate)
3. Integrates cleanly with the existing `CalcState` serde/persistence infrastructure
4. Supports the I/J global index registers used by element-access operations
5. Enforces a reasonable per-dimension size cap without artificial matrix count limits

---

## Decision

**`adv_matrices: Vec<AdvMatrix>` on `CalcState` with `#[serde(default)]`.**

The complete implementation:

1. `adv_matrices: Vec<AdvMatrix>` — unbounded list of named matrices, each identified by
   a `name: String` field. Persistent (`#[serde(default)]`). Zero cross-references to
   `state.matrix_dim` or `state.matrix_active_reg` in `advantage/` code (D-43.5).

2. ALPHA register names the active matrix at op-call time — the dispatched op reads the
   current ALPHA string, searches `adv_matrices` for a matching name, and creates a new
   entry if none exists. This faithfully reflects the X-MEM slot-naming convention from
   OM 00041-90482 Section 2.

3. `adv_matrix_i: u8` and `adv_matrix_j: u8` — global 1-based row/column index counters,
   persistent (`#[serde(default)]`). These are calculator-global pointers (not per-matrix)
   per OM 00041-90482 Section 2 conventions. I+ and J+ increment them; MR/MS use them.

4. `adv_current_matrix: Option<String>` — transient (`#[serde(default, skip)]`). Caches
   the last-used matrix name within a session. Clears to `None` on save/load (matches
   hardware semantics — the ALPHA register was volatile across power cycles).

5. `ADV_MATRIX_MAX_ROWS: u8 = 255` and `ADV_MATRIX_MAX_COLS: u8 = 255` — the `u8` type
   enforces a 255-element maximum per dimension. MATDIM with dimensions exceeding 255
   returns `HpError::InvalidData`.

6. Complete isolation invariant: verified by grep in Phase 43 Plan 10 — zero executable
   code references to `matrix_dim` or `matrix_active_reg` in `hp41-core/src/ops/advantage/`.

## Consequences

### Positive

- **Isolation prevents cross-system corruption.** The two matrix systems (`adv_matrices`
  vs. `matrix_dim`/`matrix_active_reg`) have zero shared data paths. A user who runs
  both Advantage Pac matrix operations and Math Pac I `MATRIX` in the same session cannot
  inadvertently corrupt either system's state.
- **Vec grows unbounded.** Any number of named matrices can coexist, matching the
  emulator's philosophy of removing hardware-resource constraints that do not reflect
  meaningful algorithmic limits (X-MEM slot counts are not a useful emulator constraint).
  Documented as emulator extension D-45-01.
- **Clean serde.** `Vec<AdvMatrix>` with `#[serde(default)]` serializes as a JSON array;
  old save files (pre-v3.3) load cleanly because the default is an empty Vec. No migration
  step required.
- **Global I/J matches OM behavior.** OM 00041-90482 treats I/J as calculator-global
  index registers, not per-matrix. The global `adv_matrix_i`/`adv_matrix_j` fields reflect
  this accurately.

### Negative

- **Two parallel matrix systems coexist.** Users must understand which module's matrix
  operations they are using — `MATRIX` (Math Pac I via XEQ, uses R14/R15+) vs. `MSTORE`/
  `MNAME?`/`MATRX`/etc. (Advantage Pac, uses ALPHA register for naming). The two systems
  cannot be combined: an Advantage Pac matrix and a Math Pac I matrix are completely
  separate entities.
- **255 per-dimension cap diverges from X-MEM slot limits.** The hardware limit was
  organic (based on installed X-MEM registers); the emulator imposes a fixed 255×255 cap
  via the `u8` type. Documented as emulator extension D-45-02.

### Neutral

- **I/J as global registers matches OM 00041-90482.** The OM treats the I and J indices
  as calculator-wide pointers, not properties of individual matrices. This is the
  natural implementation for a module that the HP-41C's hardware regarded as having
  global index state.
- **`adv_current_matrix` transient matches hardware volatility.** The ALPHA register was
  not persistently saved across power cycles on real HP-41C hardware; the cache of the
  last-used matrix name should therefore be transient for the same reason.

## Alternatives Considered

### Option B: HashMap-based storage (`HashMap<String, AdvMatrix>`)

This alternative would store named matrices in a `HashMap<String, AdvMatrix>` keyed by
name string, providing O(1) lookup instead of O(n) linear search.

The relevant context decision from 43-CONTEXT.md D-43.1 states verbatim:

> **D-43.1:** **Unlimited matrix count.** `adv_matrices: Vec<AdvMatrix>` grows without
> artificial cap. No maximum number of named matrices. Document as emulator extension
> in divergences (hardware had X-MEM file slot limits).

**Why rejected:** `HashMap` has non-deterministic serialization order in Rust — iterating
a `HashMap` does not produce keys in insertion order or alphabetical order. This means two
save-files created from the same sequence of operations can serialize to different JSON
byte sequences, breaking the deterministic round-trip invariant expected by persistence
tests. `serde_json` serializes `HashMap` using the underlying hash order; `Vec<AdvMatrix>`
serializes in push-order (insertion order), which is deterministic. The O(n) linear
search is acceptable for the typical number of named matrices in an HP-41C Advantage Pac
program (typically 2–20 matrices).

### Option C: Register-based storage (reusing Math Pac I's R14/R15+ model)

This alternative would store Advantage Pac named matrices in numbered storage registers
(R14 for the dimension, elements in R15+), sharing the existing `matrix_dim` and
`matrix_active_reg` fields on `CalcState`.

The relevant context decision from 43-CONTEXT.md D-43.5 states verbatim:

> **D-43.5:** **Named-matrix storage MUST NOT touch `state.matrix_dim` or
> `state.matrix_active_reg`.** These belong to Math Pac I's R14/R15+ register-based
> matrix model. Complete isolation between the two matrix systems.

**Why rejected:** The two matrix systems are incompatible at the storage level. Sharing
`matrix_dim`/`matrix_active_reg` would mean that running an Advantage Pac matrix op
and a Math Pac I matrix op in the same session could silently corrupt each other's
state. D-43.5 mandates complete isolation as a correctness requirement. Register-based
storage for named matrices would also require mapping string names to register offsets,
replicating the entire X-MEM slot-management infrastructure, which is deferred to
post-v3.3 (XMEM-01).

### Option D: File-based X-MEM model (EMDIR/EMROOM/EMREG)

This alternative would implement the full HP-41C Extended Memory file system model —
`EMDIR` for directory listing, `EMROOM` for available slot count, individual X-MEM
registers for matrix element storage — faithfully emulating the hardware X-MEM interface
on top of `CalcState`.

**Why rejected:** Full X-MEM emulation is explicitly deferred to post-v3.3 (XMEM-01 in
the deferred items list in 43-CONTEXT.md). The EMDIR/EMROOM/EMREG operations are not
part of the v3.3 scope. The `Vec<AdvMatrix>` model provides correct named-matrix behavior
for all v3.3 Advantage Pac operations without requiring X-MEM infrastructure. A future
XMEM-01 phase can add full Extended Memory emulation without breaking the existing
`adv_matrices: Vec<AdvMatrix>` API.

### Option E: Per-matrix I/J indices (field inside `AdvMatrix`)

This alternative would store I and J index values as fields on each `AdvMatrix` struct
(`AdvMatrix { name, rows, cols, data, i: u8, j: u8 }`) rather than as global CalcState
fields.

**Why rejected:** OM 00041-90482 Section 2 treats I and J as calculator-global pointers —
the I and J values are shared across all named matrices in a session. A program that uses
`XEQ "I+"` expects I to increment the global index regardless of which matrix is
currently active. Per-matrix I/J would require the implementation to select which
matrix's I/J to increment on an `I+` call, which is not OM-faithful. The global
`adv_matrix_i`/`adv_matrix_j` fields on `CalcState` directly reflect the OM's model.
