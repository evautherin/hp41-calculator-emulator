# ADR-v3.1-003: ANOVA / Multiple-Regression Register Layout — OM Transcription Policy + Named Consts (P21 Mitigation)

**Status:** Locked 2026-05-22
**Owner:** Plan 33-00 + Plan 33-06
**Requirement refs:** STAT-UNI-02, STAT-UNI-03, STAT-AOV-01, STAT-AOV-02, STAT-AOV-03, STAT-AOV-04, STAT-REG-05, STAT-REG-06, STAT-REG-07, STAT-REG-08, STAT-HYP-05, STAT-HYP-06, Pitfall 21 (33-RESEARCH.md §"OM register layout — silent-wrong-answer trap"), Pitfall 18 (citation provenance)
**Downstream consumer:** `hp41-core/src/ops/stat1/mod.rs` (`//!` doc-comment header with OM Σ-register-layout transcription + `STAT1_AOV_*_REG` / `STAT1_AOVTWO_*_REG` / `STAT1_ANOCOV_*_REG` / `STAT1_MLR_*` / `STAT1_POLYP_*` / `STAT1_CTKKK_*` / `STAT1_MMTUG_*_REG` named consts); `hp41-core/src/ops/stat1/anova.rs`, `hp41-core/src/ops/stat1/regression.rs`, `hp41-core/src/ops/stat1/moments.rs`, `hp41-core/src/ops/stat1/nonparam.rs` (consumers)
**ADR write-up prose:** Phase 35 / STAT-DOC-04 (this is the narrative ADR; the lock happened during Phase 33 Plan 33-00 spec-phase + Plan 33-06 OM-register-dependent-set implementation 2026-05-22)

---

## Context

HP-41C Stat 1 Pac (HP 00041-90030, 1979) Appendix A "Program Data" lays out a
contiguous Σ-register block for every program in the suite. The exact register
indices differ per program: ΣBSTAT uses R00–R11 (12 registers); ΣAOVONE uses
R00–R19 (20 registers); ΣAOVTWO uses R00–R17 (18 registers); ΣANOCOV uses
R00–R25 (26 registers); ΣMLRXY / ΣMLRXYZ / ΣPOLYP / ΣPOLYC use R00–R44 (45
registers); ΣCTKKK uses R00–R14 (15 registers). Per-program SIZE directives
(`SIZE 012`, `SIZE 020`, `SIZE 018`, `SIZE 026`, `SIZE 045`, `SIZE 015`) match
the table.

This is the textbook silent-wrong-answer trap catalogued as Pitfall 21:
implementing ΣMMTUG, ΣAOVONE / ΣAOVTWO / ΣANOCOV, ΣMLRXY / ΣMLRXYZ, ΣPOLYP, or
ΣCTKKK from inference or from memory — without first transcribing the OM
register layout — produces F-ratios, regression coefficients, and Spearman
correlations that look plausible but are wrong. The user-facing failure mode is
"calculator returns a number; no error is raised". A user comparing against
scipy.stats or a textbook worked-example might never spot the drift until a
specific check happens to land on a register-index mismatch.

Phase 33 Plan 33-00 was the spec-phase that read the OM Appendix A "Storage
Registers" section BEFORE any Op was implemented. This ordering is exactly the
discipline Pitfall 21 demands: ground-truth in the source tree before any
algorithm depends on it. Plan 33-06 then implemented ΣAOVONE / ΣAOVTWO / ΣANOCOV
consuming the named consts established in Plan 33-00. The 33-REVIEW.md WR-01
finding (commit `b29aa03`) cleaned up the last few literal indices in
`anova.rs` that had crept in during early Plan 33-06 work, consolidating
everything onto the `mod.rs`-declared consts.

---

## Decision

**The transcription policy is locked:** `hp41-core/src/ops/stat1/mod.rs`
carries a `//!` doc-comment header transcribing the OM register-layout
assignments verbatim (with page references), followed by approximately 30
named-const declarations. Every Stat 1 Pac program file that depends on the
OM-register layout consumes ONLY the named consts — no literal register indices
in any `hp41-core/src/ops/stat1/*.rs` file except `mod.rs` itself (the const
declarations).

The OM transcription header in `mod.rs` opens with the verbatim Appendix A
table:

```text
PROGRAM                                              #REG. TO COPY     DATA REGISTERS
Basic Statistics for Two Variables                        50              00 ~ 11
Moments, Skewness, and Kurtosis                           36              00 ~ 11
Analysis of Variance (One Way)                            29              00 ~ 19
Analysis of Variance (Two Way)                            33              00 ~ 17
Analysis of Covariance (One Way)                          60              00 ~ 25
Curve Fitting                                             34              00 ~ 15
Multiple Linear Regression                               157              00 ~ 44
Polynomial Regression                                    102              00 ~ 44
t Statistics                                              29              00 ~ 14
Chi-Square Evaluation                                     21              00 ~ 07
Contingency Table                                         33              00 ~ 14
Spearman's Rank Correlation Coefficient                   13              00 ~ 02
Normal and Inverse Normal Distribution                    47              00 ~ 18
Chi-Square Distribution                                   21              00 ~ 06
```

(OM page 73–74). The maximum across all entries (`STAT1_MAX_REG = 44` from
ΣMLR / ΣPOLYP) drives the contiguous-block invariant.

Named consts then carve out each program's role-specific register slots. A
representative slice from `stat1/mod.rs`:

```rust
// ΣAOVONE — Analysis of Variance, One Way (OM p. 20, SIZE 020)
//   R00 = k (group count; 1 ≤ k ≤ STAT1_AOV_KMAX = 4)
//   R03 = N (grand sample count)
//   R02 = ΣΣx (grand sum)
//   R01 = ΣΣx² (grand sum of squares)
//   Per-group block at base STAT1_AOV_GROUP_BASE_REG + STAT1_AOV_GROUP_STRIDE * i:
//     +0 = group sum;  +1 = group sum-sq;  +2 = group n;  +3 = (reserved)
pub const STAT1_AOV_K_REG: usize = 0;
pub const STAT1_AOV_N_REG: usize = 3;
pub const STAT1_AOV_GRAND_SUM_REG: usize = 2;
pub const STAT1_AOV_GRAND_SUMSQ_REG: usize = 1;
pub const STAT1_AOV_GROUP_BASE_REG: usize = 4;
pub const STAT1_AOV_GROUP_STRIDE: usize = 4;
pub const STAT1_AOV_GROUP_SUM_OFFSET: usize = 0;
pub const STAT1_AOV_GROUP_SUMSQ_OFFSET: usize = 1;
pub const STAT1_AOV_GROUP_N_OFFSET: usize = 2;
pub const STAT1_AOV_KMAX: usize = 4;
```

Sibling const blocks exist for ΣAOVTWO (`STAT1_AOVTWO_R_REG`,
`STAT1_AOVTWO_C_REG`, `STAT1_AOVTWO_GRAND_SUMSQ_REG`, `STAT1_AOVTWO_GRAND_SUM_REG`,
`STAT1_AOVTWO_ROW_BASE_REG`, `STAT1_AOVTWO_DIM_MAX`), ΣANOCOV
(`STAT1_ANOCOV_GRAND_SUMSQ_X_REG`, `STAT1_ANOCOV_GROUP_BASE_REG`,
`STAT1_ANOCOV_GROUP_STRIDE`), ΣMMTUG (`STAT1_MMTUG_CUBE_REG`,
`STAT1_MMTUG_QUAD_REG`, `STAT1_MMTUG_MAX_REG`), and the per-program SIZE
ceilings (`STAT1_MMTUG_MAX_REG = 11`, `STAT1_AOVONE_MAX_REG = 19`,
`STAT1_AOVTWO_MAX_REG = 17`, `STAT1_ANOCOV_MAX_REG = 25`, `STAT1_MLR_MAX_REG = 44`,
`STAT1_POLYP_MAX_REG = 44`, `STAT1_CTKKK_MAX_REG = 14`).

The bidirectional invariant is: a grep for literal register indices in any
`hp41-core/src/ops/stat1/*.rs` file other than `mod.rs` must return empty
(or only test-fixture data, not production code). Plan 33-06 WR-01 enforced
this for `anova.rs` post-fix; the discipline applies to every file in
`stat1/` going forward.

---

## Consequences

### Positive

- **Pitfall 21 silent-wrong-answer trap mitigated.** No literal register
  indices in production code means an off-by-one slip on a register layout is
  caught at code-review time by a `grep -nE "\\bR[0-9]{2}\\b"` scan of the
  file. The named consts force every register reference to declare its
  semantic role.
- **Single source of truth.** `stat1/mod.rs`'s `//!` header is the canonical
  OM-page transcription; every consumer file imports the named consts. If the
  OM is ever re-read (e.g. a later edition surfaces with corrections), only
  `mod.rs` changes — every consumer recompiles against the new values
  automatically.
- **Future v3.2+ pacs (Time, Advantage) inherit the named-const pattern.**
  Any future XROM module with OM-defined register layouts (e.g. an Advanced
  Statistics Pac with its own SIZE-allocated block) follows the same
  `<MODULE>_<PROGRAM>_<ROLE>_REG` naming convention.
- **`cargo clippy -D warnings` clean.** Named `pub const usize` declarations
  carry no lint surface; magic-number warnings are silenced by definition
  (the const has a name).

### Negative

- **`stat1/mod.rs` is large** (~37.5 KB per 33-VERIFICATION.md artifact line 52)
  because it carries the OM-transcription header + ~30 named consts. The file
  is OM-derived content rather than behavioural logic, so the size is
  inert — `cargo build` does not slow down meaningfully and the file is read
  rarely. The trade-off (large module hub vs scattered magic numbers) is
  explicitly accepted.
- **OM page references must be kept current** if a later OM edition
  re-paginates the Appendix. Mitigated by the verbatim quote discipline — if
  the page numbers in the OM Appendix change, the inline header text changes
  with them in one place.

### Neutral

- **Phase 33 Plan 33-06 commit `b29aa03` (REVIEW.md WR-01)** is the canonical
  evidence: a `git log --grep "WR-01"` returns the fix commit;
  `grep -nE "\\bR[0-9]{2}\\b" hp41-core/src/ops/stat1/anova.rs` returns
  empty post-fix.
- **Plan 33-06 consolidated `STAT1_AOVTWO_DIM_MAX` to `mod.rs`** alongside the
  other ΣAOVTWO consts (originally drifted into `anova.rs` during early
  iteration). The WR-01 fix is the textbook example of catching the trap at
  code-review time rather than at numerical-accuracy-regression time.
- **Future test surface:** Phase 37 STAT-QUAL-06 (or follow-up) may add a
  `lint_stat1_assertions.rs` test that grep-asserts no literal R-indices in
  `stat1/*.rs` non-`mod.rs` files; the discipline this ADR locks survives the
  Plan 33-06 review boundary.

## Alternatives Considered

### Option B: Inline literal register indices in each program file

The rejected alternative is the anti-pattern Pitfall 21 catalogues. From
`.planning/research/PITFALLS.md` P21 (paraphrased — research-doc text is not
quoted verbatim because it's a pitfall description rather than a discrete
CONTEXT.md decision):

> P21 — Inline literal register indices in `stat1/anova.rs` /
> `stat1/regression.rs` / `stat1/nonparam.rs` produce silent wrong answers
> when the OM register layout drifts between programs. ΣAOVONE uses R00 = k
> (group count); ΣAOVTWO uses R00 = r (row count). A copy-paste from ΣAOVONE
> into ΣAOVTWO that retains the literal `0` will silently read the row count
> as the group count and produce a plausible-but-wrong F-ratio.

**Why rejected:** Pitfall 21 explicitly identifies this anti-pattern; the
spec-phase Plan 33-00 was the gate that read the OM layout before any Op
implementation began. By the time Plan 33-06 starts implementation, the named
consts already exist in `mod.rs` and the literal-index path is structurally
unavailable to any reasonable code review.

### Option C: Per-Op register-layout constants (no shared `stat1/mod.rs` declaration)

A third option was considered: declare register-layout consts in each
per-program file (e.g. `AOV_K_REG: usize = 0` inside `stat1/anova.rs`,
`AOVTWO_R_REG: usize = 0` in the same file). Under this option, `stat1/mod.rs`
would carry only the OM transcription header and not the const declarations.

**Why rejected:** ΣAOVTWO and ΣANOCOV share register-base conventions
(both use R04 as a grand-sum slot reused across covariance paths). De-duplicating
into `mod.rs` makes the shared invariant explicit (the const declaration is the
single source); a per-file declaration would either duplicate
`STAT1_AOVTWO_GRAND_SUM_REG = 4` in both `anova.rs` and `nonparam.rs` (drift
surface) or force a cross-file import chain that defeats the locality benefit.
WR-01 specifically consolidated `STAT1_AOVTWO_DIM_MAX` from `anova.rs` back
into `mod.rs` after this trade-off was re-evaluated.

### Option D: Runtime register-layout configuration

A fourth option was considered: store the register-layout as a runtime
configuration table (e.g. a `HashMap<&'static str, usize>` keyed by role
name) that programs query at execution time.

**Why rejected:** OM register layout is hardware-deterministic; the Stat 1
Pac OM published in 1979 will not surface new register-index conventions in
the 47 years since. Runtime configuration adds zero value (the OM is fixed)
and removes the compile-time bounds-checking opportunity that named `const
usize` declarations enable (`stat1_array[STAT1_AOV_GROUP_SUM_OFFSET]` is a
compile-time-checked index when the array length is known). No
33-CONTEXT.md verbatim quote is needed for this paraphrased rejection — it
is the standard "compile-time over runtime when the value is fixed at the
spec" trade-off per Pitfall 18 sourcing discipline.
