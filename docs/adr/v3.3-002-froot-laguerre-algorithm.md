# ADR-v3.3-002: FROOT Algorithm Choice -- Laguerre's Method with Quadratic Deflation

**Status:** Locked 2026-05-25
**Owner:** Plan 43-07
**Requirement refs:** ADV-MATH-06
**Downstream consumer:** `hp41-core/src/ops/advantage/froot.rs` (FROOT polynomial
root-finding implementation)
**ADR write-up prose:** Phase 45 / Plan 45-01

---

## Context

The HP Advantage Pac (OM 00041-90482, 1985) Section 3 defines `FROOT` as a polynomial
root-finder that finds all roots of a polynomial of arbitrary degree. The calling
convention: polynomial degree is read from register X; coefficients a₀, a₁, ..., aₙ
are stored in R01..R(n+1) (per D-43.8 resolution — degree from X register, not a modal
prompt). Roots are returned to the stack sequentially, real-part in X and imaginary-part
in Y for complex roots.

The existing Math Pac I (XROM 7) `ROOTS` operation already implements polynomial root-
finding using Bairstow's method, limited to degree 2–5. The two root-finders must coexist
without conflict — they use different mnemonics (`FROOT` vs. `ROOTS`), different register
conventions, and different degree ranges.

A new algorithm is needed for FROOT that:
1. Handles arbitrary polynomial degree (1–100 per OM 00041-90482 scope)
2. Finds all roots, including complex ones
3. Is implementable in ~100–200 lines of Rust without dense linear algebra infrastructure
4. Coexists with Math Pac I `ROOTS` without shared state
5. Maintains the Free42 GPL-contamination guard (ADR-v3.1-002): algorithm must be
   independently re-derived from primary literature, not copied from Free42

*Algorithm independently re-derived from primary literature (Numerical Recipes section 9.5
Laguerre's method); Free42 source consulted only as sanity-check oracle, not copied.*

---

## Decision

**Laguerre's method with initial guess (0.4, 0.9) and quadratic deflation.**

The implementation:

1. **Initial guess (0.4, 0.9) — NOT (0, 0).** Using (0, 0) as the starting point causes
   convergence failure for polynomials with purely imaginary roots (e.g., x²+1 = 0) because
   the Laguerre correction denominator G becomes zero at the origin, making the iteration
   degenerate. The offset (0.4, 0.9) avoids this singularity and provides reliable
   convergence across the tested degree range. This was discovered during Phase 43 Plan 07
   implementation and is documented in 43-07-SUMMARY.md.

2. **Laguerre's method for root finding.** Each iteration computes the Laguerre correction:
   ```
   a = n  (degree)
   G = P'(x) / P(x)
   H = G² - P''(x) / P(x)
   denominator = max of (G ± sqrt((a-1)(aH - G²)))
   x_{k+1} = x_k - a / denominator
   ```
   Iteration continues until |P(x)| < ε or maximum iteration count is reached.

3. **Quadratic deflation for complex conjugate pairs.** When a complex root z = u + iv is
   found, both z and its conjugate z̄ = u - iv are known. The polynomial is deflated by
   the quadratic factor (x - z)(x - z̄) = x² - 2ux + (u² + v²), keeping all arithmetic
   in the reals until the final root is extracted.

4. **Linear deflation for real roots.** When a real root r is found, the polynomial is
   deflated by (x - r).

5. **Root polishing against the original polynomial.** After all roots are found via the
   deflated polynomial, each root is polished (a few more Laguerre iterations) against the
   original undeflated polynomial. This corrects for error accumulation during deflation.

6. **f64 intermediate arithmetic.** All Laguerre iterations and polynomial evaluations use
   `f64` arithmetic for numerical stability. Results are converted to `HpNum` (via
   `rust_decimal`) only at final root output — one root pair at a time, pushed to the
   stack as (real_part, imaginary_part).

7. **Register conventions.** Polynomial degree n is read from register X. Coefficients
   a₀, a₁, ..., aₙ are read from R01 (a₀ = constant term) through R(n+1) (aₙ = leading
   coefficient). Roots are returned sequentially to the stack in (X=real, Y=imaginary)
   pairs. Real roots have imaginary part 0.

## Consequences

### Positive

- **Arbitrary degree.** Laguerre's method handles polynomials of degree 1–100 (and beyond)
  without restructuring the algorithm. There is no degree-limited path analogous to
  Bairstow's degree 2–5 restriction.
- **Proven convergence for isolated roots.** Laguerre's method has guaranteed linear
  convergence for polynomials of degree ≥ 2 and cubic convergence near simple roots
  (Numerical Recipes §9.5). The (0.4, 0.9) initial guess avoids the known degenerate
  case at the origin.
- **Simple implementation.** The full FROOT implementation is approximately 120 lines of
  Rust — well within the project's target of avoiding dense linear algebra infrastructure.
  No external numerical library is needed.
- **Coexists with Math Pac I ROOTS.** FROOT (ADV_MATH_B, XROM 24) and ROOTS (MATH_1,
  XROM 7) use different Op variants, different mnemonics, and different register conventions.
  No shared state or conflict when both modules are loaded.
- **Zero new runtime dependencies.** All arithmetic is in `f64` (standard library) and
  `rust_decimal` (already a dependency). The ADR-v3.1-002 zero-new-runtime-deps invariant
  is preserved.

### Negative

- **f64 intermediate arithmetic means results are not BCD-exact.** Laguerre iterations
  on a degree-20 polynomial accumulate floating-point rounding errors in f64. The final
  roots, converted to HpNum, may differ from exact BCD arithmetic by small amounts. The
  OM does not specify BCD-exact root finding; for the polynomial degrees typical of HP-41C
  programs (2–10), f64 provides more than sufficient precision.
- **Convergence not guaranteed for pathological polynomials.** Laguerre's method can cycle
  on polynomials with closely-spaced roots or high-multiplicity roots. The implementation
  caps iterations per root; non-convergent cases return `HpError::BadData` after the cap.

### Neutral

- **Coexistence with Math Pac I Bairstow.** The two root-finders serve different use cases:
  ROOTS (Bairstow, degree 2–5, BCD arithmetic, modal prompt) is appropriate for simple
  programs; FROOT (Laguerre, arbitrary degree, f64 arithmetic, X-register input) is
  appropriate for higher-degree polynomial problems. The Advantage Pac's FROOT extends
  rather than replaces Math Pac I's ROOTS.
- **(0.4, 0.9) initial guess is non-obvious.** The choice was empirically validated during
  Phase 43 Plan 07 implementation. The 43-07-SUMMARY.md deviation log records the (0, 0)
  convergence failure and the (0.4, 0.9) resolution.

## Alternatives Considered

### Option A: Bairstow's method (extend Math Pac I's ROOTS algorithm)

This alternative would reuse or extend the Bairstow's method implementation from
`math1/poly.rs` to handle degrees beyond 5, matching the algorithm already used by
Math Pac I `ROOTS`.

The relevant context decision from 43-CONTEXT.md D-43.8 states verbatim:

> **D-43.8:** **FROOT calling convention is Claude's discretion.** Whether polynomial
> degree comes from X register or a modal prompt — determine from OM 00041-90482
> Section 3 conventions.

**Why rejected:** Bairstow's method is degree-limited to 2–5 in the current Math Pac I
implementation because Bairstow works on quadratic factors (degree 2) successively —
extending it to degree 100 would require significant restructuring. More fundamentally,
Bairstow's method is an iterative quadratic factor extraction technique that becomes
numerically unstable for high-degree polynomials. The Advantage Pac `FROOT` was designed
to handle arbitrary degree, which makes Bairstow an unsuitable choice. Using a different
algorithm for FROOT also emphasizes the deliberate separation between the two root-finding
operations.

### Option B: Jenkins-Traub algorithm

This alternative would implement the Jenkins-Traub three-stage algorithm, which provides
more robust convergence guarantees than Laguerre's method for polynomials with closely-
spaced roots, near-multiple roots, or roots near the origin.

**Why rejected:** Jenkins-Traub requires approximately 300 lines of Rust and involves
three distinct iteration stages with complex stage-switching logic. The robustness
advantage over Laguerre's method is meaningful for pathological polynomials, but HP-41C
programs rarely use polynomials where this matters. The implementation complexity cost
(300 lines vs. ~120 lines for Laguerre) exceeds the benefit for the targeted use cases.
Laguerre's method, with the (0.4, 0.9) initial guess fix, converges reliably for all
test cases in the numerical accuracy suite.

### Option C: Companion matrix eigenvalue method

This alternative would construct the companion matrix of the polynomial and compute its
eigenvalues (which are exactly the polynomial's roots) via QR iteration or similar
dense eigenvalue methods.

**Why rejected:** Dense eigenvalue computation requires a full O(n²) or O(n³) dense linear
algebra stack — matrix allocation, factorization, iteration — that is not otherwise needed
in `hp41-core`. Introducing this infrastructure for a single operation would add significant
complexity and potentially hundreds of lines of additional code. The companion matrix
approach is academically elegant but over-engineered for HP-41C emulation purposes where
polynomials rarely exceed degree 20.

### Option D: Durand-Kerner (Weierstrass) simultaneous method

This alternative would use the Durand-Kerner method, which iterates all roots simultaneously
starting from a set of distributed initial guesses on the unit circle.

**Why rejected:** The Durand-Kerner method requires storing all n roots simultaneously in
memory and updating them concurrently, which requires O(n²) work per iteration. For
degree-100 polynomials this means maintaining 100 complex numbers in parallel iteration
state. The sequential Laguerre + deflation approach requires only O(1) additional storage
per root (current root estimate + deflated polynomial coefficients), which is simpler
and more memory-efficient. Additionally, Durand-Kerner is less commonly documented than
Laguerre in standard numerical computing references; Laguerre's method (Numerical Recipes
§9.5) is the standard reference for sequential polynomial root-finding.
