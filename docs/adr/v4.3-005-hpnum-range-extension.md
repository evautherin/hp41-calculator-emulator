# ADR v4.3-005: HpNum Range Extension to ±9.999E±99

**Status:** Accepted  
**Date:** 2026-06-07  
**Phase:** 65-01 (MATH-01 — HpNum range extension)

## Context

The original `HpNum` was a newtype wrapper around `rust_decimal::Decimal` (`HpNum(Decimal)`).
`Decimal` can represent values up to approximately `7.92E28` (28-digit precision). This ceiling
caused `FACT(27..=69)` to return `HpError::Overflow` instead of the correct HP-41 factorial —
despite `FACT(69) ≈ 1.711E98` being within the HP-41 hardware range of `±9.999E±99`.

The HP-41 hardware specification (Owner's Manual p.234) defines:
- `FACT(0..=69)` → valid (0 through 69 inclusive)  
- `FACT(X > 69)` → `OutOfRange`

The old code broke this contract: `FACT(27..=69)` returned `Overflow` because `Decimal::from_f64`
returned `None` for f64 values above `~7.92E28`.

## Decision

Extend `HpNum` from a bare `Decimal` wrapper to a **two-tier struct**:

```rust
pub struct HpNum {
    pub(crate) mantissa: Decimal,  // 10 significant digits
    pub(crate) exponent: i8,       // -99..=99
}
```

### Two-tier semantics

**Common case (`exponent == 0`):** `mantissa` holds the full decimal value (up to 10 sig digits).
This is backward-compatible with the pre-ADR `HpNum(Decimal)` representation — all existing code
using `inner()` continues to return the full value unchanged.

**Large-exponent case (`exponent != 0`):** `mantissa` is normalized to `[1, 10)` for non-zero
values (10 significant digits). The full value is `mantissa × 10^exponent`. Code that needs the
full value must use `to_f64()`.

The two-tier design means:
- The 99%+ common case (values up to `~7.92E28`) is completely backward-compatible
- Large-exponent values are handled transparently by arithmetic operations
- `inner()` preserves its semantics for the common case

### Constructors

| Constructor | Purpose |
|------------|---------|
| `from_decimal(d)` | In-range values; rounds to 10 sig digits; exponent = 0 |
| `from_sci(mantissa, exp)` | Large-exponent values; validates bounds |
| `from_f64(acc)` | f64 bridge (factorial/transcendental); fast path via `Decimal::from_f64` for in-range values |
| `rounded(d)` | Backward-compat alias for `from_decimal(d)` |

### Serialization (backward compat)

New save format: `{"m": "1.088886945", "e": 28}` (object with mantissa string and exponent).

Legacy save files (v1.0–v4.2) stored `HpNum` as a bare Decimal string (e.g. `"3.1415926536"`).
Deserialization uses a private `HpNumWire` untagged enum with `Extended { m, e }` FIRST so the
new format is tried before the legacy fallback. All v1.0–v4.2 save files load without migration.

### op_fact change

```rust
// Before (Decimal wall):
let result = Decimal::from_f64(acc)
    .map(HpNum::rounded)
    .ok_or(HpError::Overflow)?;

// After (full HP-41 range):
let result = HpNum::from_f64(acc).ok_or(HpError::Overflow)?;
```

The `X > 69 → OutOfRange` guard is UNCHANGED (D-06, SC-3).

## Consequences

### Positive

- `FACT(27..=69)` now returns correct 10-sig-digit factorials as HP-41 hardware specifies
- `FACT(69) ≈ 1.711E98` — the full range `FACT(0..=69)` is correctly handled
- Full backward compatibility with v1.0–v4.2 save files via serde legacy path
- Zero new runtime dependencies (no `bigdecimal`, `num-bigint`, or similar crates)
- All existing code using `inner()` continues to work for in-range values (exponent == 0)

### Trade-offs

- ADV binary operations (NOT, AND, OR, XOR) with small inputs produce 11-digit intermediate
  results (`ADV_WORD_MASK = 2^36-1 = 68,719,476,735` has 11 decimal digits) that round to 10
  sig digits. Double-NOT is no longer an identity for small inputs (e.g. `NOT(NOT(42)) = 45`).
  This is **HP-41-faithful**: the hardware would also round 11-digit values to 10 digits on
  the display register. Pre-ADR v4.3-005, the code allowed more precision than the HP-41 has.
- The `Display` implementation calls `normalize()` to strip round_sf trailing zeros (e.g.
  `7.000000000` → `7`). The internal representation preserves trailing zeros for HMS/date
  string parsing (which uses `inner().to_string()` and relies on the fractional structure).

### Frozen Invariant amendment

The CLAUDE.md Frozen Invariant for BCD/f64 is amended to document the two-tier representation
and the new post-compute wall for `op_fact`.

## Alternatives considered

**`bigdecimal` crate:** Arbitrary precision, no ceiling. Rejected: new runtime dependency,
contradicts "Zero new runtime deps since v3.0" invariant.

**Custom BCD (evaluated for v1.0):** Already rejected in the original design decision.

**String-based large number:** Slower, complex arithmetic, no obvious benefit.

**Normalized representation for all values:** Store all values in [1,10) × 10^exp form.
Rejected: breaks all code that uses `inner()` for value comparisons and arithmetic — would
require touching every call site and removing the backward-compatible `inner()` semantics.
The two-tier design preserves all existing behavior while adding the large-exponent capability.
