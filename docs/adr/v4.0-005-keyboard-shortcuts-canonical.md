# ADR-v4.0-005: keyboard-shortcuts.json as Canonical Source for GUI/CLI Keyboard Parity

**Status:** Locked 2026-05-27
**Owner:** Plan 49-01
**Requirement refs:** KBD-01, KBD-02, KBD-03, KBD-04, D-49.10, D-49.11, D-49.12, D-49.13
**Downstream consumer:** `docs/keyboard-shortcuts.json` (61-entry canonical data file);
`hp41-gui/src/help_data.ts` (`KeyboardShortcut` interface, `getKeyboardShortcuts()` Vite JSON-import);
`hp41-gui/src/HelpOverlay.tsx` (collapsible "KEYBOARD SHORTCUTS" section, collapsed by default,
not searchable); `hp41-gui/src/App.tsx` (`resolveKeyId()` Ctrl+key extensions, F5 binding);
`hp41-gui/src-tauri/src/prefs.rs` (`onboarding_done` field); `hp41-gui/src/OnboardingWizard.tsx`
(panel 4 teaser pointing to the full `?` overlay shortcut reference)

---

## Context

Phase 49 adds two GUI features with a shared underlying concern: onboarding (a first-run wizard) and
keyboard parity (Ctrl+W/R/D/F card-reader shortcuts, Ctrl+S / F5 save, surfaced in the `?` overlay).

The keyboard parity requirement (D-49.12) is that the GUI's physical keyboard bindings should mirror
the CLI's `handle_key` bindings. As of Phase 48 the GUI had partial keyboard coverage: digits, Enter,
Backspace, Tab (SHIFT), letter keys (a–z, A–Z), and F7/F8 (SST/BST). The CLI additionally handled
Ctrl+W/R/D/F (card reader operations) and Ctrl+S (save). Phase 49 closes this gap.

Three decisions arose from the parity requirement:

1. **Data representation:** Should the canonical list of GUI keyboard bindings be hardcoded in
   `App.tsx`, expressed only in the component logic, or represented as a machine-readable data file?

2. **Discovery surface:** The `?` overlay already serves as a function reference for all six JSON
   data pools (hp41cv, math1, stat1, time, advantage, xmem). Should keyboard shortcuts be surfaced
   in the same overlay, or in a separate panel?

3. **Parity audit:** D-49.14 requires a systematic CLI ↔ GUI comparison. This is only tractable
   if both sides have a machine-readable binding list, not just imperative code.

The project already has a strong precedent for JSON-canonical data flows: `docs/hp41cv-functions.json`
and its five siblings drive the `?` overlay, the right-panel, parity tests, and documentation
generation via the same `include_str!` / Vite JSON-import pattern. Phase 28 (ADR-v3.0-005)
established this as the project's canonical approach for any data that flows to multiple consumers.

---

## Decision

**`docs/keyboard-shortcuts.json` is the single source of truth for GUI physical keyboard bindings,
consumed via Vite static JSON-import by the `?` overlay's new collapsible "KEYBOARD SHORTCUTS"
section.**

The complete implementation:

1. **`docs/keyboard-shortcuts.json`** — 61 entries, each with `"key"` (the physical key or key
   combination, e.g. `"Enter"`, `"Ctrl+W"`, `"F5"`), `"op"` (the HP-41 operation name, e.g.
   `"ENTER"`, `"WPRGM"`, `"SAVE"`), and `"description"` (one-line prose). Covers: digits 0–9,
   decimal point, EEX, CHS; navigation (Enter, Backspace/CLX, Tab/SHIFT); arithmetic and math;
   trig; transcendental; statistics; time; mode (USER, PRGM); program debug (F7/SST, F8/BST);
   card reader (Ctrl+W/R/D/F); and save (Ctrl+S, F5). Created before the frontend consumes it,
   following the D-25.16 "data file before code" discipline.

2. **`KeyboardShortcut` interface and `getKeyboardShortcuts()` in `help_data.ts`** — the same
   Vite static JSON-import pattern used for the five HP-41 function JSON pools. Build-blocker
   semantics: malformed `keyboard-shortcuts.json` fails the Vite build. The `getKeyboardShortcuts()`
   accessor returns the JSON as `readonly KeyboardShortcut[]`; the HelpOverlay consumes this
   directly without a `OnceLock` equivalent (TypeScript modules are themselves singletons).

3. **HelpOverlay "KEYBOARD SHORTCUTS" section** — rendered as a dedicated collapsible block at
   the top of the `?` overlay, above the six function-pool sections. Collapsed by default (most
   users want the function reference, not the keyboard map, per D-49.10). Not searchable — the
   section has a different content shape (shortcut rows, not `HelpEntry` rows) and is implemented
   with standalone `kbdExpanded: boolean` state rather than by widening the `SectionDef` union
   (see Alternatives Considered). The section resets to collapsed on every overlay open.

4. **`App.tsx` / `resolveKeyId()` extensions** (D-49.12, D-49.13) — Ctrl+key checks are added
   FIRST in `resolveKeyId()` to prevent fall-through to the letter-key `MAP` lookup. New bindings:
   `Ctrl+W` → `"xeq_WPRGM"`, `Ctrl+R` → `"xeq_RDPRGM"`, `Ctrl+D` → `"xeq_WDTA"`,
   `Ctrl+F` → `"xeq_RDTA"`, `Ctrl+S` → `"__save_state__"`, `F5` → `"__save_state__"`.
   `metaKey` (macOS Cmd key) is included alongside `ctrlKey` for Ctrl+S / Ctrl+W etc., matching
   macOS keyboard conventions (RESEARCH A1). The `__save_state__` special ID is intercepted before
   `dispatchKeyId` and never reaches `key_map.rs` (D-07 never-discard + T-49-08).

5. **`onboarding_done` in `GuiPrefs`** (D-49.4) — `prefs.rs` gains `pub onboarding_done: bool`
   with `#[serde(default)]`. Set to `true` by `App.tsx` via fire-and-forget `set_pref` IPC after
   the user dismisses the wizard. Never appears in `autosave.json` (P59). Old `prefs.json` files
   (Phase 48 format, without `onboarding_done`) load cleanly with `false` via `#[serde(default)]`.

6. **`save_state` Tauri command** (D-49.13) — a new command that clones the `CalcState` under the
   mutex lock (CR-01 clone-under-lock pattern), releases the lock, and then calls
   `persistence::save_state`. The module-qualified call avoids name shadowing with the command
   function itself (RESEARCH Pitfall 1). Returns `Result<(), String>`.

## Consequences

### Positive

- **Parity is auditable.** `keyboard-shortcuts.json` lists every GUI physical key binding in one
  place. A CLI ↔ GUI parity audit (D-49.14) can diff the JSON against `hp41-cli/src/keys.rs`
  and `handle_key` arm by arm, rather than tracing `App.tsx` logic paths.
- **Help surface stays in one overlay.** The `?` overlay already serves as the function-reference
  surface for all six JSON pools. Adding the keyboard shortcuts as a seventh section keeps all
  discovery in one place — users do not need to learn a second overlay or access a separate help
  panel to find keyboard bindings.
- **Build-blocker semantics.** The Vite static JSON-import means a malformed `keyboard-shortcuts.json`
  causes the build to fail immediately, with a clear error message — the same hard-build-blocker
  discipline used for all five HP-41 function JSON pools (D-25.17 carry-forward).
- **Extensibility.** Adding a new keyboard binding in a future phase requires: (a) adding an entry
  to `keyboard-shortcuts.json`, (b) adding the `resolveKeyId()` arm in `App.tsx`. The `?` overlay
  automatically shows the new entry without any HelpOverlay changes.
- **Onboarding wizard panel 4 teaser.** The wizard's "Keyboard Shortcuts" panel points users to
  the `?` overlay section, creating a discovery path from the first-run flow to the definitive
  reference without duplicating data.

### Negative

- **`keyboard-shortcuts.json` covers GUI only.** The CLI's physical key bindings live in
  `hp41-cli/src/keys.rs` (key_to_op, shifted_key_to_op) and `app.rs` (handle_key Ctrl+key arms).
  The JSON does not currently drive the CLI — it is a GUI-only data file. A future phase could
  add a CLI parity test that reads the JSON and asserts every entry resolves via the CLI resolver
  chain, closing KBD-04 fully.
- **Standalone `kbdExpanded` state adds minor HelpOverlay complexity.** The KEYBOARD SHORTCUTS
  section does not participate in the `SectionDef[]` array used for the function sections because
  it has a different content shape and is not searchable. This means two separate rendering paths
  exist in `HelpOverlay.tsx` — the standalone `kbdExpanded` block, and the `sectionGroups.map()`
  loop. The tradeoff is explicitly documented as a divergence from the PATTERNS.md suggestion.
- **F5 = SAVE in GUI diverges from CLI F5 = R/S.** On the CLI, F5 triggers `run_program` (the
  R/S key). On the GUI, F5 triggers `save_state` (D-49.13 / KBD-02). This divergence is
  intentional and documented in `keyboard-shortcuts.json`. The GUI's R/S is triggered by clicking
  the on-screen R/S key or pressing `r` (the dedicated letter binding) — no physical function key
  is needed. The CLI's R/S on F5 predates the keyboard-shortcuts.json era and will remain for
  CLI-user muscle memory.

### Neutral

- **61 entries vs. the CLI's full binding count.** The `keyboard-shortcuts.json` covers the
  physical keyboard bindings that have a direct 1:1 key-to-op mapping. It does not enumerate
  modal sequences (e.g., `STO + digit + digit` for STO 00–99) or ALPHA input flows —
  those are procedural, not declarative. The count of 61 represents the complete set of
  non-modal physical bindings.
- **No Rust-side `OnceLock` needed.** Unlike the `hp41-cli` help pools, which use
  `static HELP_ENTRIES: OnceLock<Vec<HelpEntry>>` in `help_data.rs`, the TypeScript module
  system provides singleton semantics for the Vite JSON-import by construction. The JSON is loaded
  once at module initialization time.

## Alternatives Considered

### Option B: Hardcode keyboard bindings in App.tsx and HelpOverlay.tsx

This alternative would list the shortcut descriptions inline in `HelpOverlay.tsx` as JSX, mirroring
the approach taken before Phase 49 for other static content.

**Why rejected:** Hardcoded inline content defeats the CLI ↔ GUI parity audit goal (D-49.14).
The only way to mechanically verify that GUI bindings match CLI bindings is to have a machine-readable
source. Additionally, hardcoding duplicates data between the code (`resolveKeyId()` arm) and the
documentation (the shortcut table) — a change to `resolveKeyId()` would require a separate documentation
update. The JSON-canonical pattern (D-25.16) already establishes that "data that flows to multiple
consumers lives in a JSON file, not in code".

### Option C: Extend `SectionDef` union to include a `'kbd'` keyboard section

The PATTERNS.md for Phase 49 suggested widening the `SectionDef` `id` union type in `HelpOverlay.tsx`
to add a `'kbd'` key, with special handling at every `SectionDef` render site.

**Why rejected:** The KEYBOARD SHORTCUTS section has fundamentally different content shape from
function pool sections — it renders shortcut rows (key + op + description), not `HelpEntry` rows
(category + mnemonic + description + optional example/notes). It is also not searchable (shortcut
queries are not the same as function queries). Widening the `SectionDef` union to accommodate this
would require type guards and special cases at every render site, making the `SectionDef` abstraction
leaky. The standalone `kbdExpanded: boolean` state + a separate render block before the
`sectionGroups.map()` loop is cleaner, as noted in 49-03-SUMMARY.md.

### Option D: Separate "Keyboard Reference" panel, distinct from the `?` function overlay

This alternative would add a dedicated keyboard reference overlay (triggered by, e.g., `Ctrl+/` or
a new button) instead of embedding the shortcuts section in the existing `?` overlay.

**Why rejected:** The `?` overlay already serves as the single-entry-point discovery surface for all
HP-41 function reference content. Splitting keyboard shortcuts into a second overlay would create two
reference panels that users must discover independently. The onboarding wizard's panel 4 already
points users to the `?` overlay; pointing to a second, separate panel would complicate the
first-run experience. D-49.8 explicitly mandates that `?` = function reference + shortcuts; `⚙` =
app settings + onboarding — two surfaces, not three.
