# ADR-v4.0-004: GUI Preferences Isolation — GuiPrefs Separate from CalcState

**Status:** Locked 2026-05-27
**Owner:** Plan 48-01
**Requirement refs:** THEME-05, D-48.8, D-48.9, D-48.11, D-48.12, D-48.13, D-49.4
**Downstream consumer:** `hp41-gui/src-tauri/src/prefs.rs` (`GuiPrefs`, `load_prefs`, `save_prefs`,
`VALID_THEMES`); `hp41-gui/src-tauri/src/commands.rs` (`get_prefs`, `set_pref` Tauri IPC commands);
`hp41-gui/src/themes.css` (four `[data-theme]` blocks with CSS custom properties);
`hp41-gui/src/App.tsx` (theme state management, `document.body.dataset.theme` application);
`hp41-gui/src/Keyboard.tsx` (`GradientColors` interface, `THEME_GRADIENTS` map)

---

## Context

Phase 48 adds a four-theme system (Dark, Light, Classic Beige, High Contrast) and a settings gear
icon to the Tauri GUI. The theme preference must be persisted across app restarts.

Two architectural decisions were required simultaneously:

1. **Where to store theme preference?** The calculator already persists `CalcState` to
   `~/.hp41/autosave.json` (the shared save file read by both CLI and GUI). A naïve approach would
   add a `theme` field to `CalcState`.

2. **How to implement runtime theme switching?** The calculator's SVG keyboard and overlays use
   hardcoded hex colors in `App.css`. A naïve approach would scatter per-component color logic across
   every React component.

Both questions have the same core constraint: theme preference is a GUI concern, not a calculator
concern. The CLI has no display themes; the calculator's mathematical state (registers, program,
stack) is orthogonal to screen appearance. Adding any GUI-facing field to `CalcState` would violate
the `hp41-core` / `hp41-gui` boundary that the SC-4 invariant protects.

An additional constraint from D-48.8 and D-48.12: the theme switch must be instant (no CSS transition
animation), and the default theme on first launch is "dark" — matching the current app appearance with
zero visual regression on first boot.

---

## Decision

**`GuiPrefs` in a dedicated `prefs.rs` module, persisted to `~/.hp41/prefs.json`, completely
isolated from `CalcState` / `autosave.json`. CSS custom properties with four `[data-theme]`
blocks in a dedicated `themes.css` file for zero-JS runtime theme switching.**

The complete implementation:

1. **`GuiPrefs` struct** (`hp41-gui/src-tauri/src/prefs.rs`) — fields `theme: String`
   (with `#[serde(default = "default_theme")]`, defaulting to `"dark"`) and
   `onboarding_done: bool` (added Phase 49, `#[serde(default)]`). Every field uses
   `#[serde(default)]` so old `prefs.json` files load cleanly when new fields are added.
   `load_prefs()` returns `GuiPrefs` directly (not `Result`) — a missing `prefs.json` is the
   expected first-run state, not an error; corrupt JSON also returns `GuiPrefs::default()`.

2. **Separate managed state type** — `pub type PrefsState = Mutex<prefs::GuiPrefs>` in `lib.rs`;
   loaded and registered via `app.manage(Mutex::new(prefs::load_prefs(...)))` in the Tauri
   `.setup()` closure, separately from `AppState` which holds `CalcState`. The two managed types
   are fully independent; acquiring one lock never requires acquiring the other.

3. **`get_prefs` / `set_pref` Tauri IPC commands** — `get_prefs` clones the in-memory `GuiPrefs`;
   `set_pref(key, value)` validates the key/value pair against `VALID_THEMES` before updating
   in-memory state and calling `save_prefs()` immediately (D-48.13 — no deferred write). Unknown
   keys and invalid theme values return `Err(String)` per T-48-01 threat mitigation (input from the
   JavaScript trust boundary must be allowlist-validated before touching the filesystem).

4. **`themes.css` with four `[data-theme]` blocks** — `hp41-gui/src/themes.css` defines
   `[data-theme="dark"]`, `[data-theme="light"]`, `[data-theme="classic-beige"]`, and
   `[data-theme="high-contrast"]` blocks, each containing 39 CSS custom properties
   (`--calc-bg`, `--display-bg`, `--display-text`, `--key-face`, `--key-label`, `--panel-bg`, etc.)
   per D-48.9 semantic-token convention. Each block is fully self-contained — no inter-theme
   inheritance (D-48.7 full-re-skin mandate). Theme switching is achieved by setting
   `document.body.dataset.theme` in JavaScript and letting the browser re-resolve all `var(--token)`
   references, with no layout changes and no animation (D-48.12).

5. **`App.css` color migration** — all hardcoded hex colors for theme-dependent UI surfaces in
   `App.css` are replaced with `var(--token)` references. The P51 SVG animation invariant
   (`.key { transform-box: fill-box; transform-origin: center; }`) is preserved unchanged —
   `themes.css` contains no `transform-box`, `transform-origin`, or `transition` properties.

6. **SVG gradient prop threading** (D-48.10 / P55) — SVG `<defs>` gradient `stopColor` attributes
   cannot use CSS `var()` because the SVG `<defs>` element is not in the CSS cascade when
   inlined in JSX. Gradient stop colors are therefore passed as React props: `GradientColors`
   interface with 14 fields in `Keyboard.tsx`; `THEME_GRADIENTS` map keyed by theme name in
   `App.tsx`; `gradientColors` prop threaded from `App.tsx` to `<Keyboard>`. All other colors
   (flat fills, labels, borders) use CSS custom properties without prop threading.

7. **No flash of unstyled content** (D-48.8) — `data-theme="dark"` is baked into `<body>` in
   `hp41-gui/index.html` so the browser applies the dark theme before JavaScript hydration.
   `themes.css` is imported in `main.tsx` after `index.css` to ensure correct CSS specificity
   order (D-48.11).

8. **THEME-05 isolation invariant** — `grep -c CalcState hp41-gui/src-tauri/src/prefs.rs`
   returns 0. The `prefs.rs` module contains no reference to `CalcState` in executable code or
   doc comments. This is a hard constraint: theme preference must never appear in the autosave
   file shared with the CLI.

---

## Consequences

### Positive

- **Clean boundary between app preferences and calculator state.** The CLI reads `autosave.json`;
  the GUI reads `autosave.json` for calculator state and `prefs.json` for appearance. No coupling
  between the two files. A user who edits `autosave.json` cannot accidentally affect the theme.
- **Zero impact on save-file backward compat.** Because `GuiPrefs` lives in a separate file,
  the `#[serde(default)]` additions to `CalcState` are not needed for preference fields. The
  v1.0–v3.3 save-file invariant is unaffected.
- **CSS custom properties are efficient.** The browser recomputes the cascade on `data-theme`
  attribute change; there is no per-component React re-render triggered by the theme switch beyond
  the `document.body.dataset.theme` assignment and the `gradientColors` prop update to `<Keyboard>`.
- **Each `[data-theme]` block is self-documenting.** A designer who wants to add a fifth theme adds
  one CSS block; no JavaScript changes are required unless gradient stops differ.
- **Allowlist validation prevents injection.** The `set_pref` command validates the theme value
  against `VALID_THEMES` before storing it. An attacker who can invoke Tauri IPC cannot cause
  arbitrary strings to be written into `prefs.json` via this path.

### Negative

- **SVG gradient prop threading adds some verbosity.** The `GradientColors` interface has 14 fields;
  `THEME_GRADIENTS` duplicates gradient stop hex values that are also expressed in `themes.css`.
  This is a consequence of the SVG `<defs>` / CSS cascade limitation, not a design choice —
  there is no way to use `var(--token)` inside `<defs>` gradient `stopColor` attributes (P55).
- **`prefs.json` is a new file for existing users.** On first launch after upgrade, `prefs.json`
  does not exist; `load_prefs()` silently returns `GuiPrefs::default()` (dark theme). This is the
  correct behavior per D-48.8, but it means users who had somehow set a preference previously will
  not see it honored (non-issue in practice since no preference file existed before Phase 48).

### Neutral

- **Two separate managed types in the Tauri app.** `AppState` (holding `CalcState`) and
  `PrefsState` (holding `GuiPrefs`) are registered independently. Commands that need calculator
  state use `State<'_, AppState>`; commands that need preferences use `State<'_, PrefsState>`.
  Commands that need both (none currently) would accept both `State<>` extractors.
- **`load_prefs` silent-fallback semantics differ from `load_state`.** `load_state` returns
  `Result<CalcState>` and the caller handles errors; `load_prefs` returns `GuiPrefs` directly
  and discards all errors. The difference reflects the different failure semantics: a missing or
  corrupt `autosave.json` may mean data loss (worth surfacing); a missing or corrupt `prefs.json`
  means a first-run state (safe to swallow).

## Alternatives Considered

### Option B: Store theme preference in CalcState / autosave.json

This alternative would add a `theme: Option<String>` field with `#[serde(default)]` to `CalcState`,
following the established pattern for new persistent fields.

**Why rejected:** CalcState is shared between CLI and GUI — it is the canonical calculator
persistence layer. The CLI has no themes and no display preferences; `CalcState` is already at
the conceptual boundary of what constitutes "calculator memory" (registers, programs, flags, stack).
Adding a GUI-only preference field would violate the SC-4 invariant spirit (no GUI-specific concerns
in `hp41-core` / `CalcState`) even though `CalcState` itself lives in `hp41-core`. It would also
cause the theme to be serialized into `autosave.json`, which is shared with the CLI — a CLI user
who edits the autosave file would encounter a `"theme"` key with no meaning in the CLI context.
THEME-05 and P59 mandate hard separation.

### Option C: Store theme in localStorage (browser side only)

This alternative would use the browser's `localStorage` API from JavaScript, bypassing Tauri IPC
and the Rust backend entirely.

**Why rejected:** Tauri WebViews do not have reliable `localStorage` persistence across app restarts
on all platforms — the storage may be cleared by OS maintenance, by changing the app bundle ID, or
by Tauri version updates. The existing persistence story for `autosave.json` uses the Rust filesystem
layer precisely to guarantee cross-platform reliability. Using `localStorage` for theme would create
a two-tier persistence system (Rust for calculator state, browser for theme) with inconsistent
reliability guarantees. The Tauri `store` plugin was also considered but rejected as an unnecessary
dependency given that `prefs.rs` with `serde_json` is ~50 LOC.

### Option D: Embed per-component color logic in React state

This alternative would manage the active theme as a React context value and have each component
import a color palette object, updating whenever the theme state changes.

**Why rejected:** Per-component color logic duplicates color definitions — any change to a theme
value requires updating multiple locations. CSS custom properties with a `[data-theme]` attribute
are the standard web mechanism for runtime theme switching; they are computed by the browser without
JavaScript involvement. The `themes.css` approach reduces JavaScript bundle size (no runtime
color tables), is trivially debuggable in browser DevTools (inspect any element, see which CSS
variable resolves to which value in the current theme), and requires no React context provider
plumbing.
