# ADR-v3.2-001: Clock Access Pattern -- Direct SystemTime in hp41-core

**Status:** Locked 2026-05-24
**Owner:** Plan 38-03
**Requirement refs:** TIME-CLK-01, TIME-CLK-02, TIME-FW-04, Pitfall 34 (clock in core)
**Downstream consumer:** `hp41-core/src/ops/time/clock.rs` (TIME/DATE/T+X/CORRECT/SETIME/SETDATE);
`hp41-core/src/state.rs` (`time_offset_secs: i64`)
**ADR write-up prose:** Phase 40 / TIME-DOC-03

## Context

HP-41C Time Pac (HP 82182A, 1982) adds 33 callable functions to the HP-41CX. Of these,
`TIME`, `DATE`, `SETIME`, `SETDATE`, `CLKT`, `CLKTD`, `T+X`, and `CORRECT` all require
access to a real-time clock source. The emulator must produce accurate time-of-day and
calendar-date values that track wall time between sessions.

The `hp41-core` library has operated under a zero-I/O principle since v1.0: the core
must have zero console, filesystem, or network dependencies. This invariant is enforced at
compile time — `hp41-core/Cargo.toml` deliberately lists no I/O crates, and CI gates ensure
no such dependencies creep in. The invariant exists so that `hp41-core` remains a pure
computation library that can be embedded in any frontend (CLI, GUI, WebAssembly, test
harness) without dragging in unneeded subsystem dependencies.

The design question for v3.2 is whether accessing the system clock from inside `hp41-core`
violates this zero-I/O principle, and if not, how to architect the access cleanly.

### Why SystemTime is not "I/O" in the relevant sense

The zero-I/O principle was coined to prevent console output (`println!`/`eprintln!`),
filesystem reads/writes, and network calls from appearing in `hp41-core`. These operations
are excluded because they:

1. Produce side effects visible to the user or external systems
2. Depend on OS resources that may be unavailable in embedded or test contexts
3. Cannot be trivially mocked without injecting dependencies

`std::time::SystemTime::now()` is categorically different. It is a **value-returning
syscall** — equivalent to reading a hardware register — that returns a numeric timestamp.
It produces no visible side effects, writes no bytes to any I/O device, and is available
in all `std` targets. The call is semantically identical to reading a counter register, not
to writing to a file or sending a network packet.

**Precedent within hp41-core:** The core already uses time-adjacent machinery:
- `std::time::Instant` (via transitive dependencies in integration tests)
- `Arc<AtomicBool>` for `cancel_requested`, which is a form of cross-thread state sharing
- `rust_decimal::Decimal` arithmetic, which is far more complex than a syscall

Allowing `SystemTime::now()` in `hp41-core` does not weaken any meaningful isolation
guarantee. The zero-I/O principle never intended to prohibit reading monotonic values from
the OS; it intended to prevent `hp41-core` from becoming a mixed-concern library with
output logic embedded in the engine.

### The offset design problem

Even granting that `SystemTime` is acceptable, the emulator needs a way for the user to
**set** the HP-41 clock without requiring superuser access or modifying the system clock.
The HP-41CX's `SETIME` function sets the displayed time; on real hardware this programs the
RTC chip. In the emulator, the only reasonable implementation is to compute the delta between
the entered time and the actual wall clock, and store it as an offset applied on all reads.

This offset must survive save/load cycles (TIME-CLK-02): a user who sets the clock to
match their timezone on Monday should not need to re-set it on Tuesday after reopening the
emulator. The offset is therefore a persistent `CalcState` field.

### OS local time

The HP-41CX has no concept of UTC or timezones. `TIME` and `DATE` return local time as
displayed on the calculator's face, which the user adjusts with `SETIME` and `SETDATE`.
The emulator must produce local-time results, not UTC. On Unix, `localtime_r(3)` converts
a `time_t` (seconds since epoch, UTC) to a broken-down local time struct. On Windows,
`GetLocalTime` returns local time directly.

However, the emulator's `time_offset_secs` field already encodes the user's effective
local-time preference: `SETIME` computes `new_offset = entered_time_epoch - SystemTime::now()`.
If the user enters a local time, the offset captures the UTC→local delta. The decomposition
function (`decompose_epoch_secs` in `clock.rs`) works on `SystemTime::now() + time_offset_secs`
and produces local-time components without consulting OS timezone APIs. This avoids a
dependency on `libc` or platform-specific timezone facilities.

## Decision

**Direct `std::time::SystemTime::now()` in `hp41-core`** (Decision D-38.1).

The implementation:

1. `clock.rs::adjusted_epoch_secs(offset: i64) -> i64` — calls `SystemTime::now()`,
   converts to Unix epoch seconds, adds the user-configured `time_offset_secs` offset.
   Result is the HP-41's "apparent current time" as an epoch integer.

2. `clock.rs::decompose_epoch_secs(epoch: i64) -> (year, month, day, hour, minute, second)` —
   pure Gregorian calendar decomposition using the Fliegel–Van Flandern algorithm (1968).
   Zero runtime dependencies; ~30 lines of integer arithmetic.

3. `CalcState::time_offset_secs: i64` — single persistent field with `#[serde(default)]`.
   `SETIME` computes and stores the delta. All time/date reads apply the offset. Old save
   files (pre-v3.2) load cleanly; `serde(default)` falls back to `0` (no offset = system
   clock unchanged).

4. OS local time is achieved implicitly: users run `SETIME` with their local time, which
   stores `local_time_epoch - utc_epoch` as the offset. Subsequent `TIME` reads return
   `utc_now + offset = local_now`. No `libc::localtime_r` or `GetLocalTime` needed.

## Consequences

### Positive

- **Zero new runtime dependencies.** `std::time::SystemTime` is available in all `std`
  targets without adding any crate to `hp41-core/Cargo.toml`. The Free42 contamination
  guard and the zero-new-deps invariant (D-carried.1 from v3.2 research) are both preserved.
- **Testability via offset.** Tests that need deterministic time results set
  `state.time_offset_secs` to a known value and call `decompose_epoch_secs` with a fixed
  epoch. The `SystemTime` call is isolated to `adjusted_epoch_secs`; integration tests that
  care about calendar correctness can bypass the wall clock entirely.
- **Simple implementation.** `adjusted_epoch_secs` is two lines. The Fliegel–Van Flandern
  decomposition is ~30 lines of integer arithmetic with no branching on platform. The
  absence of platform-specific timezone code means the implementation is identical on
  Windows, macOS, and Linux.
- **Backward compatibility.** `time_offset_secs: i64` with `#[serde(default)]` means v3.0
  and v3.1 save files load without any migration step. Old saves produce `offset = 0`,
  which means TIME/DATE return the system clock directly — the most sensible default.

### Negative

- **hp41-core depends on system clock availability.** In a `no_std` target, `SystemTime`
  is unavailable. This is currently hypothetical — there is no `no_std` feature flag and
  no WebAssembly target — but it represents a future constraint if `hp41-core` ever needs
  to compile without `std`.
- **One-second resolution.** `SystemTime` gives second-level precision; centiseconds in
  TIME output are always `00`. The HP-41CX hardware resolved to 1/100 second via its
  crystal oscillator. This is a documented divergence (D-40-NN in `docs/hp41-time-divergences.md`).

### Neutral

- **No timezone database.** The emulator makes no attempt to auto-detect the user's
  timezone or apply DST transitions. This matches real HP-41CX behavior: the hardware
  has no timezone concept, and the user is responsible for setting the clock correctly.
  The `CORRECT` command (which on hardware trimmed an analog circuit) is a documented no-op.
- **`time_offset_secs` semantics.** The field is conceptually "seconds ahead of UTC to
  display as local time". This conflates timezone offset with user-entered time adjustment.
  The HP-41CX had the same property — `SETIME` simply set the displayed time, with no
  distinction between timezone and user correction. Matching hardware semantics is correct.

## Alternatives Considered

### Option B: Trait injection (clock trait abstraction)

This alternative would define a `Clock` trait in `hp41-core`:

```rust
pub trait Clock: Send + Sync {
    fn now_epoch_secs(&self) -> i64;
}
```

`CalcState` would hold a `Arc<dyn Clock>` (or similar), and frontends would inject a
`SystemTimeClock` implementation. Tests would inject a `MockClock`.

The relevant context decision (38-CONTEXT.md D-38.1) states verbatim:

> **D-38.1:** Direct `std::time::SystemTime::now()` in hp41-core — core calls the system
> clock directly. Precedent: core already uses `Arc<AtomicBool>` (cancel_requested) and
> `Instant` is a transitive dep. SystemTime is a value-returning syscall, not console I/O.
> The zero-I/O principle applies to console/filesystem/network, not to clock reads.

**Why rejected:** Trait injection adds a new generic parameter or dynamic dispatch to
`CalcState`, complicating its construction in every call site (tests, CLI, GUI). The
existing `CalcState::new()` API is zero-argument; adding a clock injection point would
require all existing tests to be updated. More importantly, it is over-engineering: the only
realistic "mock" use case is deterministic time in tests, which is already solved by setting
`time_offset_secs` to a known value in test setup. Trait injection buys zero additional
correctness and costs significant API complexity.

### Option C: Frontend callback (core requests time from caller)

This alternative would add a callback field to `CalcState`:

```rust
pub time_fn: Option<Box<dyn Fn() -> i64 + Send + Sync>>,
```

The core would call `(self.time_fn.as_ref().unwrap())()` wherever `TIME` or `DATE` is
needed. Frontends would register `|| SystemTime::now()...` during initialization.

**Why rejected:** This is a more invasive version of Option B. It introduces a non-serializable
field on `CalcState` (requiring `#[serde(skip)]`), and it makes every time-dependent
operation failable in a new way (panics if `time_fn` is `None`). It also couples dispatch
to frontend registration order — a frontend that forgets to set `time_fn` before calling
`TIME` would observe a panic rather than a compile error. The trait-injection critique
applies here with additional force: callbacks are harder to document, test, and reason about
than either trait objects or direct syscalls.

### Option D: `no_std` clock abstraction (feature flag)

This alternative would gate `SystemTime` behind a `std` feature flag:

```toml
[features]
default = ["std"]
std = []
```

In `no_std` mode, `op_time` and `op_date` would return `HpError::NotAvailable` or a
platform-provided stub. This preserves future `no_std` compatibility.

**Why rejected:** There is no concrete `no_std` requirement for `hp41-core` in the v3.2
roadmap or beyond. Feature-flagging the clock would require auditing all 35 Time Pac
operations for `std` dependency, and would produce a degraded "no-clock" build that is
not the same as the target hardware. The HP-41CX is not a `no_std` target — it has a
crystal oscillator. Emulating it faithfully requires a clock. Adding feature complexity
for a hypothetical future that may never materialize violates the project's "no unnecessary
abstraction" principle.
