# ADR-v3.3-003: Dual-XROM-ID Design -- XROM 22 (ADV_MATH_A) + XROM 24 (ADV_MATH_B)

**Status:** Locked 2026-05-25
**Owner:** Plan 43-01
**Requirement refs:** ADV-FW-01, ADV-FW-02
**Downstream consumer:** `hp41-core/src/ops/math1/xrom.rs` (`ADV_MATH_A: XromModule`,
`ADV_MATH_B: XromModule`, `adv_a_resolve`, `adv_b_resolve`, bit-3 and bit-4 arms in
`xrom_resolve`); `hp41-core/src/state.rs` (`default_xrom_modules()` returning
`0b0001_1111`, `migrate_after_load()` v3.2→v3.3 migration)
**ADR write-up prose:** Phase 45 / Plan 45-01

---

## Context

The HP Advantage Pac (HP 00041-90482, 1985) ships on two physical ROM chips. Each chip
has a hardware XROM ID assigned by HP:

- **Chip 1 (ADV CONV + ADV MTRX):** XROM ID 22. Contains base-conversion operations
  (BININ, BINVIEW, OCTIN, HEXIN, HEXVIEW, CVTVIEW) and named-matrix operations (MSTORE,
  MNAME?, MATDIM, DIM?, I+, J+, MR, MS, MATRX, MDET, MINV, MSYS, M*M, MAT+, MAT-, TRNPS,
  and additional matrix operations). 63 operations total.

- **Chip 2 (ADV MATH + ADV TVM):** XROM ID 24. Contains mathematical solvers (FSOLVE,
  FINTG, FDIFEQ, FROOT), complex number extensions (E^Z, LNZ, LOGZ, Z^N, Z^1/N, Z^W,
  |Z|, SINZ, COSZ, TANZ, A^Z, CINV, CPOLAR, CRECT and related), curve fitting (CFITX,
  CFITY, CFIT), vector operations (VPOLAR, VRECT, VANGLE, VMAG, VD, VX, V+, V-, V*R,
  VMAKE), and time value of money (TVM, N, PV, PMT, FV, *I). 51 operations total.

This is a hardware constraint, not a design choice — HP assigned XROM IDs 22 and 24 to
the two physical ROM chips. The emulator must model both chips as separate XROM modules
with separate resolver arms.

The existing XROM resolver chain (`xrom_resolve` in `math1/xrom.rs`) already handles
three modules with three bit-flag arms:
- bit-0 (`0b0000_0001`): MATH_1 (XROM 7, Math Pac I)
- bit-1 (`0b0000_0010`): STAT_1 (XROM 2, Stat 1 Pac)
- bit-2 (`0b0000_0100`): TIME_MODULE (XROM 26, Time Module)

The Advantage Pac requires two new arms (bit-3 and bit-4) and two new `XromModule`
constants.

**Known consequence: 12 intentional mnemonic overlaps with Math Pac I (XROM 7).**

ADV_MATH_B (XROM 24) includes complex number operations with identical mnemonics to
Math Pac I (XROM 7): E^Z, LNZ, LOGZ, Z^N, Z^1/N, Z^W, |Z|, SINZ, COSZ, TANZ, A^Z,
CINV. This overlap is hardware-faithful — both chips were independently designed and
happen to provide the same named functions. When both modules are loaded, the resolver
priority determines which implementation is invoked.

---

## Decision

**Two `XromModule` constants: `ADV_MATH_A` (id=22, bit-3) and `ADV_MATH_B` (id=24, bit-4).**

The complete implementation:

1. **`ADV_MATH_A: XromModule`** — `id = 22`, bit-3 arm in `xrom_resolve`, name
   `"ADV 22A"` (CATALOG 2 display string per Phase 44 discovery). Contains 63 ADV CONV
   + ADV MTRX operations.

2. **`ADV_MATH_B: XromModule`** — `id = 24`, bit-4 arm in `xrom_resolve`, name
   `"ADV 24B"` (CATALOG 2 display string). Contains 51 ADV MATH + ADV TVM operations.

3. **Resolver order:** bit-3 fires before bit-4 in the resolver chain. The full order
   is: bit-0 (MATH_1) → bit-1 (STAT_1) → bit-2 (TIME_MODULE) → bit-3 (ADV_MATH_A)
   → bit-4 (ADV_MATH_B). Lower-numbered XROM IDs take priority (hardware-faithful per
   HP-41C XEQ-by-name dispatch semantics). This means MATH_1 (XROM 7) wins the 12
   overlapping mnemonics over ADV_MATH_B (XROM 24) when both are loaded.

4. **`default_xrom_modules()` returns `0b0001_1111`** — all five bits set. v3.2 save
   files with `xrom_modules = 0b0000_0111` are auto-upgraded to `0b0001_1111` by
   `migrate_after_load()` at startup (same pattern as v3.0→v3.1→v3.2 migrations).

5. **12 MATH_1 alias overlaps in ADV_MATH_B.** When `xrom_modules = 0b0001_1111`, the
   following 12 mnemonics resolve to MATH_1 (bit-0 fires before bit-4):
   E^Z, LNZ, LOGZ, Z^N, Z^1/N, Z^W, |Z|, SINZ, COSZ, TANZ, A^Z, CINV.
   ADV_MATH_B's versions of these functions are only reachable when MATH_1 is unloaded
   (`xrom_modules = 0b0001_0000`, bit-4 only).

6. **XROM shadowing test isolation.** The `xrom_shadowing.rs` test for ADV_MATH_B uses
   `xrom_modules = 0b0001_0000` (bit-4 isolation, not `0b0001_1111`) specifically to
   verify that ADV_MATH_B's implementations of the 12 overlapping mnemonics work
   correctly when MATH_1 is unloaded. Using `0b0001_1111` would cause MATH_1 to
   intercept these calls, making it impossible to test ADV_MATH_B's implementations
   via the normal XEQ-by-name path. This was discovered during Phase 44 implementation
   and documented in 44-02-SUMMARY.md.

---

## Consequences

### Positive

- **Hardware-accurate module assignment.** XROM 22 and XROM 24 correspond to the actual
  hardware XROM IDs assigned by HP. A user familiar with the real HP-41C Advantage Pac
  hardware will see the same module IDs in CATALOG 2 (displayed as "ADV 22A" and "ADV 24B").
- **Resolver priority is hardware-faithful.** MATH_1 wins the 12 overlapping mnemonics
  when both modules are loaded, matching the real HP-41C's lower-XROM-ID-wins dispatch
  semantics.
- **Minimal footprint in `math1/xrom.rs`.** Adding two new `XromModule` constants and
  two new resolver functions (`adv_a_resolve`, `adv_b_resolve`) follows the established
  pattern of the three existing modules. The total edit footprint in the freeze carve-out
  is approximately 40 lines.

### Negative

- **Two resolver arms for one logical module.** From the user's perspective, "Advantage
  Pac" is a single product. The implementation requires two `XromModule` constants, two
  resolver functions, two bits in `xrom_modules`, and two CATALOG 2 entries. This adds
  cognitive overhead when reading or modifying the resolver chain.
- **12 alias overlaps require test isolation.** The `xrom_shadowing.rs` test for
  ADV_MATH_B must use `0b0001_0000` not `0b0001_1111`, which is a non-obvious requirement
  that could confuse future maintainers. The 44-02-SUMMARY.md deviation log and this ADR
  document the rationale.

### Neutral

- **12 overlapping mnemonics are hardware-faithful and documented.** The overlap (E^Z,
  LNZ, LOGZ, Z^N, Z^1/N, Z^W, |Z|, SINZ, COSZ, TANZ, A^Z, CINV) is documented in
  `docs/hp41-advantage-divergences.md` as D-45-09 (Behavioral Policy). The behavior
  matches real HP-41C hardware where XROM 7 won over XROM 24 for these names.
- **`xrom_modules` grows to 5 bits.** The `xrom_modules: u32` field can accommodate many
  more XROM modules in the future; 5 bits is well within the u32 capacity.

---

## Alternatives Considered

### Option A: Single XROM ID with unified 114-entry module

This alternative would combine all Advantage Pac operations into a single `XromModule`
with one XROM ID (e.g., XROM 22), containing all 114 operations.

The relevant context decision from 43-CONTEXT.md states verbatim:

> **D-43.1 (by implication from the Phase Boundary description):** Two new `XromModule`
> constants (ADV_MATH_A id=22, ADV_MATH_B id=24); `xrom_resolve` gains bit-3 and bit-4
> arms; `default_xrom_modules()` updated from `0b0000_0111` to `0b0001_1111`.

**Why rejected:** A single XROM ID violates hardware accuracy — the real Advantage Pac
uses two distinct XROM module IDs (22 and 24) that XEQ-by-name dispatches independently.
Using a single ID would cause the emulator's CATALOG 2 to show one entry where real
hardware shows two. More importantly, the 12 mnemonic overlaps between ADV_MATH_B and
MATH_1 require the resolver to distinguish between ADV_MATH_A (no overlaps with MATH_1)
and ADV_MATH_B (12 overlaps) when determining resolver priority. A unified single-ID
module cannot distinguish these two subsets.

### Option B: XROM 22 + XROM 23

This alternative would use XROM IDs 22 and 23 rather than 22 and 24.

**Why rejected:** HP assigned XROM IDs 22 and 24 to the two Advantage Pac ROM chips.
XROM 23 was assigned to a different HP product. Using 22 + 23 would produce incorrect
CATALOG 2 display and would make the emulator incompatible with HP-41C programs that
check XROM IDs via CATALOG 2 parsing. The hardware XROM ID assignments are not
negotiable — they are factory-assigned constants.

### Option C: Flattened op namespace with a single resolver

This alternative would use a single resolver function covering all 114 operations, with
the 12 MATH_1 alias overlaps handled by special-casing in the resolver rather than by
bit-flag priority.

**Why rejected:** The XROM shadowing test (Phase 44) confirmed that the 12 overlapping
mnemonics require independent resolver isolation — specifically, the `xrom_shadowing.rs`
test for ADV_MATH_B uses `0b0001_0000` (bit-4 only) not `0b0001_1111` to verify the
ADV_MATH_B implementations of the overlapping mnemonics are reachable when MATH_1 is
unloaded. A flattened resolver cannot provide this isolation because it cannot be
selectively disabled for one resolver while keeping the other active. The two-bit-flag
design (bit-3 for ADV_MATH_A, bit-4 for ADV_MATH_B) provides exactly the isolation
needed for correct shadowing behavior.
